# ADR-0015 Spring Security를 넣지 않음 (Origin 검사)

- **상태**: 채택 (2026-11-08. codex와 agy는 도입을 제안했고, 조율자가 결정했다)
- **맥락**: 로그인이 없다. 상태 변경(구독 확인, 수정, 해지)의 권한은 폼 안의 토큰(ADR-0008)이다.
- **선택지**: Spring Security(쿠키 CSRF + 보안 헤더) / **도입하지 않고 Origin 검사와 Caddy 헤더**
- **결정**: Spring Security를 넣지 않는다.
  - 상태를 바꾸는 모든 POST에 `Origin`(없으면 `Referer`) 호스트가 우리 도메인인지 확인하는 필터를 둔다
  - 보안 헤더(HSTS, `X-Content-Type-Options`, `Content-Security-Policy`, `Referrer-Policy`)는 Caddy가 붙인다
- **결과**
  - 세션 기반 권한이 없으므로 CSRF로 위조할 대상이 없다. 공격자는 토큰 없이 수정이나 해지를 못 하고, 신청은 공격자가 직접 해도 결과가 같다
  - 의존성과 설정이 줄어든다
  - **로그인 기능을 추가하면 이 결정을 다시 검토한다**

## 개정 (2026-11-16, #6 · 06~08)
- 상태를 바꾸는 요청은 우리 Origin, 또는 Origin이 없을 때 같은 출처 Referer만 받는다. **예외**: 요청에 실린 목적별 토큰이 권한인 POST(확인, 관리, 해지, RFC 8058 원클릭)는 `Origin: null`과 Origin 없음도 받는다. no-referrer 페이지와 메일 공급자가 그렇게 보내기 때문이다. 외부 Origin은 이 경로에서도 거부한다. 신청·재발송·웹훅 복구처럼 토큰이 없는 POST는 엄격 규칙 그대로다.
- 순서: Origin 규칙(거부는 토큰 실패로 세지 않음. 위조 폼이 피해자 IP를 잠그지 못하게) → `TOKEN_FAIL` 사전 확인(IP당 10분 30회를 넘으면 검사 없이 429) → 토큰 검사 → 실패마다 +1. 관리 GET도 토큰을 검사하므로 같은 순서를 따른다. 확인 GET은 토큰을 검사하지 않는다.
- Origin `null` 관측은 Chromium 루프백까지만 확인했다. 다른 브라우저와 실제 HTTPS 관측은 실사용 전 게이트다.
