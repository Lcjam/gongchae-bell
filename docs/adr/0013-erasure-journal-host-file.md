# ADR-0013 복원 후 해지 유지: 호스트 파일 대장

- **상태**: 채택 (2026-11-08, 사용자 결정)
- **맥락**: 백업은 하루 1회다. 백업에서 복원하면 마지막 백업 이후에 해지한 구독이 되살아나 다시 발송될 수 있다 (PRD §7 "백업 복원 후 해지 유지").
- **선택지**: (a) OCI Object Storage에 동기 기록 / **(b) 호스트 파일 대장** / (c) 복원할 때 구독 전부 폐기
- **결정**
  - 해지할 때 구독 행 잠금 아래에서 호스트 디렉터리(DB 볼륨과 분리)의 `erasure.log`에 `구독 UUID, 시각` 한 줄을 추가하고 fsync한 뒤 DB에서 삭제한다. UUID만 남기므로 개인정보가 아니다
  - `erasure.log`는 DB 덤프와 함께 restic으로 백업한다(ADR-0012)
  - 복원 절차: **발송을 멈춘 채** 덤프를 복원한다 → 대장의 UUID를 모두 다시 삭제한다 → 검증한 뒤 발송을 재개한다
- **결과**
  - 가장 흔한 사고(잘못된 마이그레이션, 실수 삭제, DB 손상)에서는 해지가 완전히 유지된다. 구현은 파일 쓰기 한 줄과 복원 명령 하나다
  - **한계**: VM 자체가 사라지면 마지막 백업 이후(최대 약 24시간)의 대장도 사라진다. 그 사이 해지한 사람에게 다시 발송될 수 있다 → 처리방침과 runbook에 이 한계를 적는다

## 개정 (2026-11-16, #6 · 06~08)
- **철회**: 결정의 "UUID만 남기므로 개인정보가 아니다"는 쓰지 않는다. 운영자가 가진 백업과 연결할 수 있기 때문이다.
- 쓰기: JVM 안 직렬화 → `FileChannel.lock()`(blue·green 두 컨테이너 직렬화) → 마지막 바이트가 줄바꿈이 아니면 줄바꿈을 먼저 쓴다(잘린 줄과 붙지 않게) → 모든 바이트를 쓰는 루프 → `force(true)` → 처음 만들었으면 디렉터리도 fsync(POSIX). 이 순서는 구독 행 잠금 아래에서 DB 삭제보다 먼저 일어난다. 쓰기에 실패하면 삭제하지 않는다.
- 복원: `--spring.main.web-application-type=none --alerts.erasure-reapply=true`로 실행한다. 대장 전체를 먼저 검사해, 잘리거나 형식이 틀린 줄이 하나라도 있으면 **아무것도 지우지 않고 실패**한다. 이때 알림은 계속 끈 채 운영자가 대장을 확인한다.
- 대장의 정리 시점은 아직 정하지 않았다. 해지 시각 이전의 백업 사본이 모두 지워진 것이 확인돼야 그 줄을 지울 수 있다. 그런데 NAS·PC 사본의 실제 삭제는 확인되지 않았다. 또 실행 중인 두 앱이 같은 파일에 쓰므로, 파일을 다시 쓰는 정리는 앱을 멈춘 상태에서만 안전하다. 그래서 #6은 자동 정리를 넣지 않았다(실사용 전 게이트).
