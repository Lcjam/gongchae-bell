# ADR-0013 복원 후 해지 유지: 호스트 파일 대장

- **상태**: 채택 (2026-11-08, 사용자 결정)
- **맥락**: 백업은 하루 1회다. 백업에서 복원하면 마지막 백업 이후에 해지한 구독이 되살아나 다시 발송될 수 있다 (PRD §7 "백업 복원 후 해지 유지").
- **선택지**: (a) OCI Object Storage에 동기 기록 / **(b) 호스트 파일 대장** / (c) 복원할 때 구독 전부 폐기
- **결정**
  - 해지할 때 구독 행 잠금 아래에서 호스트 디렉터리(DB 볼륨과 분리)의 `erasure.log`에 `구독 UUID, 시각` 한 줄을 추가하고 fsync한 뒤 DB에서 삭제한다. UUID만 남기므로 개인정보가 아니다
  - `erasure.log`는 DB 덤프와 함께 restic으로 백업한다(ADR-0012)
  - 복원 절차: **발송을 멈춘 채** 덤프를 복원한다 → 대장의 UUID를 모두 다시 삭제한다 → 검증한 뒤 발송을 재개한다
- **결과**
  - 가장 흔한 사고(잘못된 마이그레이션, 실수 삭제, DB 손상)에서는 해지가 완전히 유지된다. 구현은 파일 쓰기 한 줄과 복원 명령 하나다
  - **한계**: VM 자체가 사라지면 마지막 백업 이후(최대 약 24시간)의 대장도 사라진다. 그 사이 해지한 사람에게 다시 발송될 수 있다 → 처리방침과 runbook에 이 한계를 적는다

## 개정 (2026-11-16, #6 · 06~08)
- **철회**: 결정의 "UUID만 남기므로 개인정보가 아니다"는 쓰지 않는다. 운영자가 가진 백업과 연결할 수 있기 때문이다.
- 쓰기: JVM 안 직렬화 → `FileChannel.lock()`(blue·green 두 컨테이너 직렬화) → 마지막 바이트가 줄바꿈이 아니면 줄바꿈을 먼저 쓴다(잘린 줄과 붙지 않게) → 모든 바이트를 쓰는 루프 → `force(true)` → 디렉터리도 fsync(POSIX. 2026-11-17부터 매번, 잠금 안에서). 이 순서는 구독 행 잠금 아래에서 DB 삭제보다 먼저 일어난다. 쓰기에 실패하면 삭제하지 않는다.
- 복원: `--spring.main.web-application-type=none --alerts.erasure-reapply=true`로 실행한다. 대장 전체를 먼저 검사해, 잘리거나 형식이 틀린 줄이 하나라도 있으면 **아무것도 지우지 않고 실패**한다. 이때 알림은 계속 끈 채 운영자가 대장을 확인한다.
- 개정 (2026-11-17, PR #13 수정 C2·C3):
  - 대장 파일은 운영자가 처음 켜기 전에 빈 파일로 만든다. 앱은 대장을 만들지 않는다(쓰기에 `CREATE` 없음). 알림을 켰을 때 파일이 없으면 시작하지 않는다(`ALERTS_ERASURE_LOG_MISSING`). 그래서 "파일 없음"은 언제나 경로나 마운트 오류다. 복원 명령도 파일이 없으면 `ERASURE_LOG_MISSING`으로 실패하고 아무것도 지우지 않는다. 있는 빈 파일만 "해지 없음"이다.
  - 디렉터리 fsync(POSIX)는 처음 만든 경우만이 아니라 **쓸 때마다 OS 파일 잠금을 쥔 채로** 한다. 그래서 어느 프로세스가 먼저 썼든, 디렉터리 항목이 내구화된 뒤에야 잠금이 풀리고 DB 삭제가 커밋된다. Windows는 디렉터리를 열 수 없어 이 단계를 건너뛴다(배포는 Linux).
- 대장의 정리 시점은 아직 정하지 않았다. 해지 시각 이전의 백업 사본이 모두 지워진 것이 확인돼야 그 줄을 지울 수 있다. 그런데 NAS·PC 사본의 실제 삭제는 확인되지 않았다. 또 실행 중인 두 앱이 같은 파일에 쓰므로, 파일을 다시 쓰는 정리는 앱을 멈춘 상태에서만 안전하다. 그래서 #6은 자동 정리를 넣지 않았다(실사용 전 게이트).

## 개정 (2026-11-20, #17 · recovery 08 구현 1)
- **표지(marker)**: 같은 줄 문법 `<uuid>\t<Instant>`를 쓰되, UUIDv8·IETF variant·상위 48비트 `67636862-6172`인 UUID를 예약한다. 표지는 구독 ID가 아니며 재적용에서 지우지 않는다. 앱이 만드는 구독 ID는 v4라서 겹치지 않는다. 표지끼리의 고유성은 나머지 무작위 비트에 기댄다. 한 파일에 같은 표지가 두 번 있으면 strict 파싱이 실패한다. 표지를 쓰는 정비 도구와 초기 표지는 이 개정의 범위가 아니다(recovery 08의 후속 단계).
- **복원 coverage 게이트**: 재적용 명령은 적용할 대장 L과 덤프 snapshot에 동봉된 대장 B(`--alerts.erasure-bundle-log`, 필수)를 같은 strict 파서로 읽는다. B는 잠금 없이 읽어 읽기 전용 마운트에서도 동작하고, L은 기존 OS 잠금 아래 한 번에 읽는다. **DB 삭제 전에** 다음을 바이트로 비교한다. 시각 비교는 쓰지 않는다.
  - L 첫 줄이 표지가 아니면(S0: 표지 없음, S1: 표지가 있으나 첫 줄이 아님): B 전체가 L의 앞부분이어야 한다.
  - L 첫 줄이 표지 H이면(S2): H가 B에 있고, B의 H부터 끝까지가 L의 앞부분이어야 한다. H 이전에 만든 덤프는 거부한다.
  - 실패하면 고정 코드(`ERASURE_COVERAGE_NOT_PREFIX`, `ERASURE_COVERAGE_MARKER_ABSENT`, `ERASURE_BUNDLE_*`)로 끝나고 아무것도 지우지 않는다. 통과하면 `ERASURE_COVERAGE_VERIFIED`, 삭제를 마치면 `ERASURE_REAPPLY_COMPLETE`를 따로 남긴다. 명령에 B 생략 옵션은 없다. M1 전용 백업의 재적용 생략은 runbook의 기존 3조건 분기에만 있다.
- **한계(유지)**: 표지가 L 첫 줄에 오기 전(S0·S1)에는, B를 복사한 뒤 정상 형식 줄이 통째로 사라진 경우(꼬리 손실)를 잡지 못한다. 빈 B와 빈 L은 구별하지 못한다. 정상적인 과거 대장으로 통째 되돌린 경우와 VM 소실 뒤 마지막 백업 이후 해지 유실도 이 게이트로 막을 수 없다.
