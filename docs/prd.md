## 1. 문제와 차별점

**현재 상황 (2026-11-08 확인)**
- 공공기관 채용공고는 잡알리오에 모여 있다. 잡알리오에는 이미 NCS, 신입·경력, 고용형태, 지역, 기관명, 진행·마감 필터, 마감일순 정렬, 기관비교(연간 신규채용 인원, 초임, 보수, 직원수)가 있다.
- 하지만 공고, 그 기관의 공고 이력, 공고 시기는 **각각 다른 화면에서 따로 찾아야 한다.** 기관 상세 화면에는 공고 이력이 없다.
- 진행 중 공고의 원문 링크 일부는 개별 공고가 아니라 **기관 첫 화면**으로 연결된다 (표본 504건 중 101건). 일부 공고는 글자가 깨져 있다 (17건).

**우리가 제공할 가치 (가설, 첫 사용자로 검증한다)**
1. 조건에 맞는 공고에서 **그 기관의 최근 3년 공고 이력, 공고 시기 패턴, 직무 분포**로 바로 이어지는 흐름
2. **관심 조건의 새 공고와 마감 임박을 알림**으로 받기 (이메일, 디스코드)
3. **"신입 지원 가능"**(신입 + 신입·경력) 공고를 한 번에 보기
4. **데이터 기준 시각과 품질 한계 표시**, 개별 공고 링크 보완

새로운 데이터를 만드는 서비스가 아니라 **흩어진 정보를 한 흐름으로 묶고 먼저 알려 주는 서비스**다. 모든 개발 직군 공고, 채용 예측, 실시간 수정 추적은 약속하지 않는다.

**포트폴리오 목적**: 공개 배포 후 수집과 발송의 신뢰성, 무중단 배포, 관측, 백업·복구, 보안 유지보수를 **실제 기록**으로 남긴다.

## 2. 대상 사용자 (가설)
| 페르소나 | 상황 | 핵심 흐름 |
|---|---|---|
| P1 공공기관 IT 신입 준비생 | 정보통신 직무에 신입으로 지원할 수 있는 공고를 놓치지 않고 싶다 | 조건 목록 → 상세 → 원문. 같은 조건으로 알림 구독 |
| P2 지역·기관 중심 준비생 | 원하는 지역과 기관의 공고를 비교하고, 그 기관이 보통 언제 공고를 내는지 알고 싶다 | 지역 필터 목록 → 상세 → 기관 이력과 시기 패턴 |

부차 이해관계자: 포트폴리오를 보는 면접관. 서비스가 실제로 운영되고 있다는 증거(기준 시각, 운영 문서)를 볼 수 있어야 한다.

## 4. 범위 (MVP)
**기간은 정하지 않는다.** 1주 스프린트를 반복하며 마일스톤 순서로 진행한다: **M1 제품(수집, 웹) → M2 알림 → M3 운영 기반 → 공개 출시(커뮤니티 공개)**

**포함**: 공고 수집(최초 3년 적재, 1시간 주기 정기 수집, 상태 판정, 변경 관측, 품질 표시) · 웹(홈, 목록, 상세, 기관) · **마감 알림(이메일, 디스코드 웹훅. 구독 확인, 관리, 해지)** · **개인정보처리방침** · 기본 SEO · HTTPS 공개 배포 · CI/CD · 무중단 배포와 롤백 · 관측과 운영 알림 · 백업, OCI 밖 사본, 복원 리허설 · 운영 문서

**제외** (백로그로만): 로그인과 소셜 로그인 · 관심 공고 저장 · 카카오톡과 텔레그램 알림 · 공고 나란히 비교 · 후기와 댓글 · 공개 `/status` 페이지 · ICS · 다른 데이터 원천 · React · Redis · Spring Batch · 첨부 재호스팅 · 원문 페이지 크롤링 · 과거 공고 상세 일괄 수집 · 차트 시각화

## 5. 기능 요구사항

### 수집
| ID | 우선 | 요구사항 | 수용 기준 |
|---|---|---|---|
| FR-C1 | Must | **최근 3년** 공고 최초 적재 (공시 시작일 기준, 약 3.5만 건, 호출 약 36회) | 실행 기록에 기간, 페이지, 받은 건수, 고유 공고 수가 남는다. 같은 fixture를 두 번 적재해도 고유 공고 수가 같다. 과거 공고의 상세는 호출하지 않는다. 오래된 데이터의 코드와 품질 차이는 적재 후 표본으로 검수해서 기록한다 |
| FR-C2 | Must | 1시간 주기 정기 수집 (`ongoingYn=Y`, `numOfRows=1000`, 1회 호출) + 완결성 검사 | `resultCode=200`, 필수 식별자 존재, `totalCount` = 받은 건수일 때만 "완전 수집"이다. 오류, 빈 응답, 잘린 응답 fixture에서는 **공고 상태 변화 0건**이고 마지막 완전 수집 시각도 유지된다 |
| FR-C3 | Must | 상태 판정 | 마감은 마감일(KST) 경과 또는 `ongoingYn=N`으로만 판정한다. 완전 수집에서 마감일 전 공고가 빠지면 "확인 필요"로 표시한다 (마감 아님) |
| FR-C4 | Must | 변경 관측 | 비교 필드: 제목, 시작일, 마감일, 채용구분, 고용형태, NCS, 지역, 모집 인원, 원문 링크, 자격, 우대, 전형 설명. 동일 입력 → 기록 0건, 마감일 변경 → 1건, `decimalDay`만 변경 → 0건. 관측 시각은 "서비스가 변경을 확인한 시각"으로 기록한다 |
| FR-C5 | Must | 동시 실행 방지 | 앱 두 개가 동시에 떠 있어도(blue/green) 같은 수집과 같은 알림 작업은 1회만 실행된다 (통합 테스트) |
| FR-C6 | Must | 실패 처리와 호출 기록 | 타임아웃, 제한된 재시도. 모든 호출 시도를 저장해서 재시작 후에도 일 합계를 조회할 수 있다. 일 합계가 500이면 운영 알림, 900이면 자동 중단 |
| FR-C7 | Should | 신규 진행 공고 상세 수집 (`steps`, `files`) | 성공한 공고는 다시 호출하지 않는다. 목록의 빈 배열로 저장된 상세를 덮어쓰지 않는다. 미수집과 실패 상태를 구분한다 |
| FR-C8 | Must | 데이터 품질 | 원본 `srcUrl`은 보존한다. 개별 공고가 아니라고 판별되면 잡알리오 공고 링크(`recruitview.do?idx={sn}`)를 함께 제공한다 (판별 규칙은 fixture로 테스트). 깨진 문자가 있으면 복구하지 않고 품질 표시와 원문 안내만 한다 |

### 알림 *(3자 리뷰 반영: [collab/2026-11-08-alerts-review/final.md](../collab/2026-11-08-alerts-review/final.md))*
공통 규칙: **링크의 GET 요청은 화면만 보여 주고, 상태 변경(확인, 해지, 수정)은 POST로만 한다** (메일 보안 스캐너가 링크를 미리 열기 때문). 만료 시간, 재시도 횟수, 제한 횟수, 파기 시점의 구체 값은 ADR에서 정한다.

| ID | 우선 | 요구사항 | 수용 기준 |
|---|---|---|---|
| FR-A1 | Must | 이메일 구독 (로그인 없음) | 이메일, 조건(목록 필터와 같은 항목), 알림 종류(새 공고, 마감 임박)를 입력하고, FR-A6의 고지를 확인해서 동의해야 신청된다. **확인 메일의 링크 → 확인 버튼(POST)**을 거쳐야 활성화된다. 확인 토큰은 만료가 있고 한 번만 쓸 수 있다. 확인하지 않은 구독에는 발송하지 않고 정한 시점에 삭제한다. 이미 구독 중인 주소로 신청해도 같은 응답을 돌려주고, 기존 활성 구독을 덮어쓰지 않는다 |
| FR-A2 | Must | 디스코드 웹훅 구독 | URL을 파싱해서 https, 호스트(`discord.com` 또는 `discordapp.com`), 경로(`/api/webhooks/{숫자}/{토큰}`)를 정확히 검사한다. 리다이렉트는 따라가지 않고 사설, 루프백, 링크로컬 대역 연결은 차단한다. 유사 도메인, userinfo, IP 주소, 리다이렉트 입력 테스트에서 금지 대상으로 요청이 나가지 않는다. 등록할 때 테스트 메시지가 성공해야(`wait=true`로 생성 확인) 활성화된다. URL은 DB에 암호화해서 저장하고, 중복 판별용 해시를 따로 둔다. 화면과 로그에 노출하지 않는다 |
| FR-A3 | Must | 관리, 조건 수정, 해지 | 관리 링크(해당 구독만 다룰 수 있는 토큰)로 **조건을 수정**하고 해지할 수 있다. 관리 토큰은 해시로 저장하고, 관리 화면은 `Referrer-Policy: no-referrer`와 `Cache-Control: no-store`로 둔다. 이메일 구독자는 관리 링크를 다시 받을 수 있다. 디스코드 구독자는 관리 링크를 등록 완료 화면에서 한 번만 보고(채널 메시지에는 넣지 않는다), 잃어버리면 **웹훅 URL을 다시 입력해서**(해시 일치) 관리한다. 모든 이메일에 해지 링크를 넣는다. 조건을 수정하거나 해지하면 대기 중인 발송 작업에 즉시 반영된다 (FR-A4의 발송 직전 재확인) |
| FR-A4 | Must | 매칭과 발송 | **새 공고 알림**: 정기 수집에서 처음 관측된 공고(최초 적재 공고는 제외) 중 조건에 맞는 것을 **디스코드는 수집 회차마다, 이메일은 하루 1회** 묶어서 보낸다. **마감 임박 알림**: 하루 1회 정해진 시각에 D-3 공고를 묶는다 (이메일은 새 공고와 같은 한 통에 담는다). 발송 대상은 수집 반영과 같은 트랜잭션으로 DB에 기록해서, 중간에 멈춰도 누락되지 않는다. 발송 작업은 DB에서 원자적으로 선점한다 (`PENDING → SENDING`). 선점할 때 구독 상태와 조건을 다시 확인한다. (구독, 공고, 종류) 유니크 제약을 둔다. 디스코드 메시지는 `allowed_mentions`로 자동 멘션을 막는다. 본문이 길면 요약과 목록 링크로 보낸다. 중복은 0을 지향하지만 보장할 수 없으므로 **중복 건수를 지표로 관측**한다. 두 앱 동시 실행, 선점 후 종료, 발송 후 종료 상황을 테스트한다. 발송 시각에 서버가 꺼져 있었을 때의 만회 정책과 마감 연장 시 재알림 여부는 설계에서 정한다 |
| FR-A5 | Must | 발송 기록과 실패 처리 | 발송 시도와 결과를 기록한다. 디스코드 404(웹훅 없음)는 **즉시** 구독을 비활성화하고, 429는 `retry_after`가 지난 뒤 재시도한다. 이메일은 발송 API가 **수신 주소 오류를 즉시 돌려주면** 비활성화한다. **공급자 5xx와 연결 오류는 재시도만 하고 비활성화하지 않는다**(공급자 장애 때 멀쩡한 구독을 끄지 않기 위해). 비동기 반송 처리는 MVP 밖이다([ADR-0007](adr/0007-email-resend.md)). 발송 실패율과 적체는 운영 지표로 본다 |
| FR-A6 | Must | 개인정보 | 신청 화면에 **수집 항목(이메일, 조건), 목적(알림 발송), 보유 기간, 동의를 거부할 권리와 거부 시 알림을 받을 수 없다는 점**을 고지한다 (공고 조회는 동의 없이 가능하다). 만 14세 이상인지 확인한다. 동의문 버전과 동의·확인 시각을 기록한다. **개인정보처리방침**: 법 제30조 기재 사항, 열람·정정·삭제·철회 방법, 담당 연락처, 발송 위탁 수탁자와 업무, 국외 이전 여부(발송 서비스 ADR 뒤 확정). 상태별(미확인, 활성, 해지, 비활성) 파기 시점을 정하고, 해지하면 이메일과 연결된 발송 데이터까지 파기한다. 백업에서는 보관 기간(14일)이 지나면 사라진다는 점을 적는다. 이메일, 웹훅 URL, 토큰은 앱·프록시·HTTP 클라이언트 로그와 오류 화면에서 가린다 |
| FR-A7 | Must | 남용 방지 | 신청, 확인 메일 재발송, 웹훅 테스트, 관리 토큰 시도를 **IP 기준과 대상(수신 주소, 웹훅) 기준**으로 제한하고 전체 발송량에도 상한을 둔다. IP를 저장하면 목적과 보유 기간을 FR-A6에 반영한다. 이메일당 구독 수 상한은 Should |
| FR-A8 | Should | 원클릭 해지 헤더 | 이메일에 `List-Unsubscribe`와 `List-Unsubscribe-Post` 헤더를 넣는다 (RFC 8058, POST 방식) |

## 6. 비기능 요구사항
| 구분 | 요구사항 | 검증 |
|---|---|---|
| 성능 | 홈, 목록, 상세, 기관의 응답 p95와 오류율을 재현 가능한 조건(데이터 3년치, 필터, 동시성, 수집 동작 여부)으로 측정한다. **목표는 기준선 측정 후 설정한다** | 부하 측정 (외부 API는 부르지 않음) |
| 가용성·배포 | readiness 확인 후 전환, graceful shutdown, 실패 시 이전 버전으로 복귀. 단일 VM이므로 고가용성은 범위 밖이다 | G4 고정 외부 시험 (요청 간격과 기간은 runbook에 고정) |
| 감시·경보 | 웹 외부 HTTP 감시와 배치(수집, 알림, 백업) heartbeat를 분리한다. 초기 경보: 정기 수집 2회 연속 미완료, 알림 발송 적체 또는 실패 급증, 백업 미완료, 웹 감시 실패. 경보값은 초기 설정이며 실제로 발동해서 수신까지 확인한다 | 경보 발동 시험 |
| 보안 | HTTPS만 허용. DB, Actuator, Grafana는 외부에 열지 않는다. **서버 자격증명과 암호화 키**는 환경변수와 Secrets로만 다루고, **사용자가 등록한 웹훅 URL**은 DB에 암호화해서 저장한다(키는 DB, 백업과 분리. 키를 포함한 복구 가능성도 시험한다). API 키, 이메일, 웹훅 URL, 토큰은 로그에서 가린다. 의존성 취약점을 점검한다. 저장소가 공개이므로 비밀값 스캔을 켠다 | 외부 접근 시험, CI, 로그 점검 |
| 이메일 발송 | 기존 도메인에 발신 인증(SPF, DKIM, DMARC)을 설정한다. 발송 서비스와 무료 한도는 **설계 단계에서 검증한 뒤** 정한다 | 시험 발송과 수신함 확인 |
| 백업·복구 | 일 1회 DB 백업 + OCI 밖 사본, 보관 14일(초기 설정). 격리 환경에서 복원 리허설 1회 이상. RTO와 RPO 목표는 리허설 뒤 설정한다. 백업에 개인정보(이메일)가 있으므로 사본에도 접근 제한을 둔다 | `docs/ops/backup-restore.md` |
| 자원 | 정상 시, 수집 중, 배포로 앱이 겹칠 때 메모리, CPU, 디스크를 실측해서 기록한다 | 서버 실측 |
| 호환성 | Flyway 마이그레이션은 이전 버전 앱과 호환된다. ARM64에서 동작한다 | 배포 리허설 |
| 테스트 | 외부 API와 발송 서비스는 키를 제거한 fixture나 테스트 대역으로만 테스트한다 | CI |

## 7. 완료 기준 (공개 출시 조건)
- [ ] Must 기능 요구사항의 수용 기준을 모두 검증했다
- [ ] 3년치 최초 적재의 실제 조건, 건수, 표본 검수 결과가 기록돼 있다
- [ ] fixture로 재수집 중복, 변경 관측, 누락과 실패, 동시 실행, 호출 기록, 알림 중복 방지와 해지를 검증했고 CI가 통과한다
- [ ] 실제 이메일과 디스코드로 구독 확인 → 조건 수정 → 발송 → 해지 전 과정을 시험했다. 테스트 계정에서 SPF/DKIM 통과와 받은편지함 수신을 확인하고, 계정, 시각, 결과를 기록했다
- [ ] 대역(fixture)으로 미확인 구독 발송 차단, 토큰 재사용과 다른 구독 접근, SSRF 우회 입력, 동시 발송, 해지와 발송의 경합, 디스코드 404와 429, 백업 복원 후 해지 유지를 검증했다
- [ ] 공개 HTTPS에서 핵심 화면, 빈 결과, 404, 미수집, 지연 상태를 확인할 수 있다. 개인정보처리방침이 게시돼 있다
- [ ] `main`에 머지하면 자동 배포된다. 성공 배포와 실패 롤백 각각의 G4 외부 시험 기록이 있다
- [ ] 웹 감시 경보와 배치 경보를 따로 시험했고 실제로 수신했다
- [ ] 백업이 자동화돼 있고 OCI 밖 사본이 있다. 복원 리허설 기록(데이터 시점, 소요 시간)이 있다
- [ ] 성능과 자원 기준선, 장애 훈련 회고가 1건 이상 있다 (훈련이라고 표시)
- [ ] PRD, 설계, ADR, runbook, CHANGELOG, 스프린트 리뷰가 저장소에 있다
- [ ] 공개할 커뮤니티의 홍보 규정을 확인했다
