# M2 구현 전 교차 확인안 · codex

대상: agy 독립안과 정정, Claude 독립안과 교차 검토. M1 실제 적재·최종 테스트 PR 완료 전 M2 구현을 시작하지 않는다. 아래는 기존 요구를 만족하는 최소 계약으로 정리한 안이며 남은 기술 경계는 두 구현자가 확인한 뒤 설계·ADR에 반영한다.

## 유지할 최소 계약

1. 확인 토큰은 ADR-0008의 32바이트 무작위 + DB 해시·만료·일회 사용을 유지한다. 확인 메일은 DB 커밋 후 요청 메모리의 토큰으로 제한된 동기 시도를 한다(1회 10초, 최대 3시도, 2초/4초 대기). 내부 재시도에서는 같은 토큰·본문·멱등 키를 유지한다. 원문/암호문/파생 nonce를 DB에 새로 저장하지 않는다. 요청 중 종료되면 자동 재발송하지 않으며 다시 신청할 수 있다. 화면 응답은 존재 여부를 드러내지 않는다. 관리 링크는 기존 HMAC으로 다시 만들 수 있다.
   - 동기 확인의 각 시도·결과도 DB에 고정 코드로 기록한다. 토큰을 복원할 수 없는 동기 작업은 비동기 SENDING 회수·재발송 대상에서 제외한다. 재신청은 기존 활성 구독을 덮어쓰지 않으며 이전 세대의 확인 메일이 새 토큰을 잘못 보내지 않도록 재검증한다.
2. 실제 공고 알림은 기존대로 수집 반영과 같은 트랜잭션의 outbox다. 발송 1회 동안 구독 FOR SHARE와 조건 재확인을 유지하며 대기는 트랜잭션 밖으로 보낸다. 영구 수신자 오류의 DISABLED 전환은 잠금 승격을 피하는 별도 짧은 트랜잭션이다. 모든 경로는 구독→자식 잠금 순서를 지키고 선점 세대가 달라진 작업 결과는 반영하지 않는다.
3. 구독 조건은 채용 조건과 알림 종류만 저장한다. 목록의 정렬·페이지·상태는 저장하지 않는다. 빈 조건은 허용하고 비공백의 잘못된 코드는 오류로 거부한다. MVP는 한 목적지에 PENDING/ACTIVE 한 건으로 시작하며 활성 구독은 재신청으로 덮어쓰지 않는다. 복수 구독 기능을 추가하지 않는다.
4. 이메일 상한은 기존 공유 90통을 유지하되 공급자 기준인 UTC 날짜로 센다. 매 수신자·매 시도 직전에 원자 예약한다. 실제 공고 알림은 초과하면 다음 UTC 날짜로 RETRY한다. 메모리 토큰의 동기 확인 메일은 다음날 자동 재발송을 약속하지 않고, 일반 응답과 다음 발송 가능 시각에 재신청할 수 있는 안내를 준다. KST 08:00 묶음 일정은 바꾸지 않는다. 별도 몫이나 임의 48시간 lookback을 추가하지 않는다. 신규 알림은 활성화 후 처음 관측한 현재 유효 공고와 항목 중복키로 선택한다. EMAIL은 확인 POST, DISCORD는 웹훅 테스트 성공 시각을 공통 하한으로 기록한다. 과거·가입 이전 공고가 알림으로 섞이지 않아야 한다.
5. 해지 대장은 동일 JVM 직렬화 + OS 파일 잠금 아래 완전 쓰기 루프와 fsync 후 DB 삭제를 한다. 복원 때 비정상 줄은 조용히 무시하지 않고 실패로 보고하며 발송을 재개하지 않는다. 잘린 줄만으로 미완료 해지였다고 확정할 수 없으므로 기본은 fail closed다. 이후 정상 줄과 합쳐지지 않게 하는 쓰기 경계도 정한다. UUID가 항상 개인정보가 아니라는 문장은 처리방침에 옮기지 않는다.

## 토큰 POST 경계 확인안

PRD의 no-referrer를 유지하면서 정상 폼을 처리해야 한다. 쿠키 로그인 없이 기존 유효한 목적별 토큰이 권한인 확인·관리·해지 POST에 한해 Origin null/부재를 허용하는 ADR-0015 예외를 검토한다. 확인은 해시·만료·일회 사용, 관리·해지는 목적·구독 ID·token_version의 HMAC을 검증한다. 관리·해지 링크에 확인 토큰의 만료·일회 사용을 일괄 강제하지 않는다. 잘못된 실제 외부 Origin은 거부하고, 신청·재발송·웹훅 복구 등 토큰으로 인증하지 않는 POST에는 엄격한 같은 출처 검증을 유지한다. RFC8058도 토큰과 지정 본문을 확인하는 전용 예외다. GET은 상태를 바꾸지 않는다.

이 안은 Origin만 믿고 토큰을 생략하는 예외가 아니다. 브라우저 정상 폼, 가짜/재사용/타목적 토큰, 외부 Origin·null·헤더 부재를 조합해 테스트해야 한다. 다른 안전한 최소안이 더 적합하면 구현 전에 이유를 제시한다. PRD no-referrer를 바꾸거나 새 CSRF 프레임워크를 추가하는 것은 우선하지 않는다.

## 독립 확인한 외부 사실

root도 [Resend quotas](https://resend.com/docs/knowledge-base/account-quotas-and-limits)에서 무료 100통/일·3,000통/월 및 UTC 자정 초기화, 송·수신 모두 할당량 포함을 직접 확인했다. 따라서 위 공유 90은 해당 계정의 다른 송·수신이 없다는 전제다. 실제 계정 사용은 설정 때 확인한다.

root는 [Fetch Origin 알고리즘](https://fetch.spec.whatwg.org/#append-a-request-origin-header)의 비-CORS POST/no-referrer 분기를 확인했다. Claude의 Chromium 루프백 폼 관측과 일치한다. Firefox·Safari·실제 HTTPS의 관측까지 완료했다고 확대하지 않는다.

구현 분담은 #6의 구독/보안·확인 메일 기반을 먼저 닫고 #7의 매칭·발송기를 그 계약 위에 쌓는다. M1 실제 적재의 필수 수정에 V4가 필요할 수 있으므로 M2 마이그레이션 번호는 그 뒤 확정한다. 공통 파일과 마이그레이션은 한 명만 작성한다. 처리방침의 실제 법·공급자 보유 기간과 운영 연락처는 공개 전 별도로 검증·설정한다. 사용자 비밀값과 개인정보를 에이전트 프롬프트로 전달하지 않는다.
