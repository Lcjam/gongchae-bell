## 결론

**1순위: 취업 스터디용 "공고 변경·마감 알리미"**
공식 공공 API 하나에서 채용과 청년정책 공고를 주기적으로 수집해 신규, 변경, 마감 임박 공고를 디스코드로 묶어 보내는 서비스다. 실제 사용자는 취업 스터디 한 곳에서 시작한다.

세 에이전트 모두 이 군을 **25/30점**으로 채점했고, 셋 중 둘이 1순위, 하나(agy)가 2순위로 꼽았다. 이유는 하나로 모인다. **트래픽이 적어도 운영할 일이 제품 기능에서 계속 생긴다.** 외부 API의 점검, 필드 변경, 키 만료가 있고, 디스코드 429 응답이 있고, 데이터가 쌓이면 보관 정리가 필요하고, 배포와 복구도 해야 한다. 공식 API만 쓰니 크롤링 약관 리스크도 없다.

## 1순위 상세

### 범위 (MVP는 일부러 작게)
- **원천 1개**로 시작한다. 후보는 공공데이터포털 [`재정경제부_공공기관 채용정보 조회서비스`](https://www.data.go.kr/data/15125273/openapi.do)(잡알리오, JSON/XML)와 [온통청년 청년정책 API](https://www.youthcenter.go.kr/cmnFooter/openapiIntro/oaiGuide)(신청 후 담당자 심사)다. 스터디가 실제로 챙겨 보는 쪽을 고른다.
  - ~~잡알리오 API는 키워드 검색을 지원하지 않는다~~ → **정정**: 제목 포함 검색(`recrutPbancTtl`)과 신입·NCS·지역·고용형태 필터를 지원한다. 다만 수정시각 필드가 없어 변경 감지는 직접 해야 한다. 자세한 내용은 [03-feasibility.md](03-feasibility.md)
- **채널 1개**: 디스코드 웹훅. OCI Email Delivery는 문서끼리 무료 한도 표기가 엇갈리므로(월 3,000건 대 한도표 0) 필수 채널로 두지 않는다.
- 기능: 수집, 공고 목록, 관심 조건 구독, 신규·변경·마감 D-n 묶음 알림, 처리 이력, 수동 재처리.
- **MVP에서 뺄 것**: 원천 여러 개, 이메일, 카카오톡(알림톡은 심사와 비용이 따로 든다), 캘린더 피드(ICS), Redis, 메시지 큐.

### Spring 기술 포인트
- `@Scheduled` 또는 Spring Batch 기반 **재개 가능한 수집**: 마지막 성공 지점을 기록하고 실패 구간을 다시 처리한다.
- 외부 ID 기준 **upsert와 내용 해시로 변경 감지**: API가 증분 조회를 지원하는지는 확인 전까지 가정하지 않는다.
- 타임아웃, 재시도, 서킷브레이커(Resilience4j), 호출량 제한
- **DB 작업 테이블(아웃박스) 기반 발송**: 재시작해도 유실 없이 재개한다. 단 외부 발송 직후 프로세스가 죽으면 중복이 생길 수 있으니 "중복 0"이 아니라 "중복 완화"로 설명한다.
- 여러 인스턴스가 동시에 떠도 작업이 겹치지 않게 하는 선점과 만료 처리. blue/green 배포 중에 실제로 겹친다.
- Flyway, Testcontainers, Actuator(readiness), graceful shutdown

### 인프라 (2 OCPU / 12GB, 처음엔 최소 구성)
- **A1**: Docker Compose로 Nginx(또는 Caddy), Spring 앱(배포 순간에만 2개), PostgreSQL을 올린다. 관측 도구는 Actuator, Prometheus, Grafana부터 넣고, 부족하면 하나씩 추가한다. 메모리는 **배포 중 두 앱이 겹칠 때의 최대치를 측정**해서 예산을 잡는다.
- **CI/CD**: GitHub Actions로 테스트, ARM64 단일 플랫폼 이미지 빌드, GHCR 푸시, SSH 배포, readiness 확인, Nginx 전환, 실패하면 이전 버전으로 되돌린다.
- **외부 감시는 OCI 밖에서**: 같은 계정의 Micro는 독립된 감시 지점이 아니다. 수집·백업 배치는 Healthchecks.io 무료 플랜으로, 서비스 생존은 외부 업타임 서비스로 본다. **감시 도구를 직접 만들지 않는다.**
- **백업**: `pg_dump`를 Object Storage(20GB, 월 요청 5만 회)에 올리고 OCI 밖에도 사본 하나를 둔다. 보관 기한을 둔다. 복원 리허설에서 "마지막으로 복원 가능한 데이터 시점"과 "서비스 확인까지 걸린 시간"을 실측한다.
- 보안 유지보수: Dependabot 패치 배포, 비밀키 교체, 인증서 갱신 확인, Actuator와 DB 포트 외부 차단

### 이력서 증거 기록 원칙 (세 에이전트 공통 결론)
- **수치는 실측만 쓴다.** 1라운드 예시 수치(agy의 "304 88%", "가동률 99.95%", 다른 안의 "구독자 24명" 등)는 전부 가정이다. 그대로 옮기면 면접에서 무너진다.
- **실제 사건과 훈련을 구분해서 쓴다.** 훈련도 원인, 영향, 탐지 시간, 복구 시간, 재발 방지를 남기면 충분히 좋은 재료다.
- 함께 남길 것: 실사용(활성 구독, 원문 클릭, 집계 기간), 배포(버전, 전환 시각, 외부 연속 요청 결과, 롤백 원인), 복구(백업 시점, 복원 가능 시점, 소요 시간), 성능(같은 조건에서의 전후 p95, 쿼리 수)
- "단일 VM에서 무중단 교체"와 "고가용성"은 다른 말이다. 섞어 쓰지 않는다.

## 확인된 사실과 미확인 사항

**공식 문서로 확인** ([Oracle Always Free Resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/resourceref.htm))
- A1: Always Free 기준 **2 OCPU / 12GB** (월 1,500 OCPU시간, 9,000GB시간)
- Micro: 2대, 각 1/8 OCPU, 1GB, 50Mbps · 블록 스토리지 200GB(부팅 볼륨 포함), 백업 5개 · Object Storage 20GB, 월 요청 5만 회 · 아웃바운드 월 10TB
- 유휴 회수: 7일 동안 CPU p95, 네트워크, (A1은) 메모리가 **모두** 20% 미만이면 회수될 "수 있다"

**미확인 또는 문서끼리 충돌**
- **PAYG 전환 시 유휴 회수 면제**: 커뮤니티 근거만 있고 공식 문구는 없다 (agy 주장, Claude·Codex는 미확인으로 판정)
- **PAYG의 A1 무료량**: Oracle 가격표에는 유료 tenancy가 월 3,000 OCPU시간 / 18,000GB시간(4/24 상당)으로 나와 있다 (Codex 확인). 한도를 넘으면 과금된다
- A1 축소 시행일: 2026-06-15라는 보도(InfoQ)가 있지만 Oracle 문서에 날짜는 없다
- Email Delivery 무료 발송 가능 여부: 문서끼리 충돌한다
