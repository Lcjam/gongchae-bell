# 2라운드 교차 검토 · Codex

검토 대상: [Claude 1라운드](01-claude.md), [Codex 1라운드](01-codex.md), [agy 1라운드](01-agy.md). 확인일: 2026-11-08.

현재 정보로는 **1순위는 대상과 원천을 좁힌 공고 수집·알림, 2순위는 정원제 모임 신청·대기자 관리**다. 내 1라운드의 모임 도구 우선 추천은 수정한다. 실제 도입할 모임 운영자를 확보했다는 정보가 없기 때문이다. 반면 캘린더 봇이 트래픽과 유휴 회수 방지를 보장한다는 agy 안의 핵심 논거는 채택하지 않는다.

아래에서 ‘오류’는 공식 문서와 충돌하는 주장, ‘미확인’은 공식 근거를 확보하지 못한 주장, ‘설계 판단’은 조건에 따라 달라지는 평가를 뜻한다. 공식 문서의 문구를 확인했으며, 사용자의 OCI 콘솔·실제 API 키·Google/Apple 갱신 동작을 직접 시험하지는 않았다. 미확인을 반대 사실의 증명으로 취급하지 않는다.

유휴 회수 관련해서는 세 안 모두 논리를 더 엄격하게 다뤄야 한다. Claude의 ‘JVM과 DB면 메모리 2.4GB는 보통 넘는다’는 측정되지 않은 예상이다. agy의 ‘주기적 요청·배치가 있으므로 완벽히 회수를 방어한다’는 결론도 성립하지 않는다. **요청이 존재한다는 사실과 정책의 사용률 기준을 충족한다는 사실은 다르다.** 자원 낭비를 통해 임계값을 넘기는 방식을 운영 설계의 목표로 삼을 이유도 없다.

Claude가 제안한 관리형 DB 용량은 대체로 맞는다. 다만 Autonomous 무료 DB에는 별도의 제약이 있다. 전용 문서는 최대 2개·각 20GB 외에도 유휴 정지와 복원 기능 제한을 명시한다. ‘관리형 DB로 옮겨도 동일한 백업·복구 실습을 할 수 있다’고 가정하면 안 된다. [Autonomous Always Free 전용 문서](https://docs.oracle.com/en-us/iaas/autonomous-database-serverless/doc/autonomous-always-free.html)

또한 같은 OCI 계정·리전의 Micro는 **다른 VM에서의 감시 지점**은 되지만 계정·리전 장애까지 독립적인 감시 지점은 아니다. Micro 자체의 중단과 유휴 회수 가능성도 고려해야 한다. 서비스의 최종 생존 확인은 다른 사업자나 사용자의 외부 환경에서 수행하는 편이 낫다. 이는 장애 범위를 나누어 본 설계 판단이다.

### 1.2 Google/Apple iCalendar 구독

agy의 가장 큰 문제는 iCalendar 형식, URL 구독, 갱신 주기, 봇 트래픽을 한 묶음으로 확정한 것이다.

- **Google은 URL로 공개 캘린더를 추가하는 기능을 제공한다.** 그러나 확인한 공식 도움말에는 ‘2~6시간마다 갱신’이라는 보장이 없다. 신규 구독은 컴퓨터 웹브라우저에서 진행하도록 안내하므로 모바일 앱에서 링크 한 번으로 등록된다는 사용자 경험도 시험해야 한다. [Google Calendar 공식 도움말](https://support.google.com/calendar/answer/37100?hl=en)
- **Apple의 갱신을 글로벌 서버의 고정 주기로 일반화할 수 없다.** Mac Calendar 공식 안내에는 구독 캘린더의 자동 갱신 옵션을 사용자가 선택할 수 있다고 나온다. iCloud 등록 여부와 기기에 따른 동작도 구분해야 한다. [Apple의 캘린더 갱신 안내](https://support.apple.com/en-il/guide/calendar/icl1024/mac), [iCloud 캘린더 구독](https://support.apple.com/en-ie/102301)
- RFC 5545는 일정 데이터 형식을 정의한다. 이를 구현했다고 실시간 전달이나 특정 클라이언트의 폴링 간격이 보장되지는 않는다. **티켓 오픈 시각처럼 시의성이 중요한 알림은 직접 발송하고, ICS는 일정 열람의 보조 채널로 두어야 한다.** [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.html)

‘50명이 구독하면 매일 수백~수천 건’도 보장할 수 없다. 구독자와 서버 요청이 일대일이라는 공식 근거가 없기 때문이다. 심지어 원문의 가정을 그대로 적용해 50명이 각각 2~6시간마다 한 번 요청한다고 계산해도 **하루 200~600건**이다. 예시의 하루 8,000건은 별도의 이용자 수·URL 수·갱신 주기 근거가 필요하다. 8,000건/일도 평균 약 0.093요청/초이므로, 이 수치만으로 DB 커넥션 풀 고갈을 예상하는 것은 과장이다. 버스트와 응답 지연은 별도로 측정해야 한다.

ETag·Last-Modified와 304는 좋은 학습 소재다. 다만 304는 본문 전송을 생략한다는 HTTP 의미이며, **DB 조회 감소는 ETag를 어디서 계산하고 검증하느냐에 달린다.** ‘304 비율 88%’가 ‘DB 부하 80% 감소’를 자동으로 뜻하지 않는다. 조건부 요청 헤더를 실제 클라이언트가 보내는지도 확인해야 한다. [RFC 9110의 304 정의](https://datatracker.ietf.org/doc/html/rfc9110#section-15.4.5)

### 1.3 공공 API와 알림 서비스 조건

[ALIO 공식 Open API 사이트](https://opendata.alio.go.kr/new/main.do), [채용정보 조회](https://opendata.alio.go.kr/new/odaApiMng/recrutInquiryList.do) |

| 개발 행사·학교 공지 RSS | 세 문서에는 실제 사용할 피드 URL과 최신성·이용 조건 검증이 없다. ‘개발자 행사에 RSS가 있을 것’은 원천 확보가 아니다. 한 원천의 합법적 접근 경로와 필수 날짜 필드를 확인한 뒤 범위를 늘려야 한다. 공개 접근과 재이용 허용도 구분한다. |
| agy의 카카오톡 즉시 알림 | 기능 이름만으로 일반 사용자에게 서버 알림을 발송할 수 있다고 보면 안 된다. 카카오톡 메시지 API는 사용자 간 상호작용 기능이며 권한·동의·쿼터 조건이 있다. 서비스의 일방향 자동 안내는 별도 알림톡 제품 검토가 필요하다. MVP에서는 추가 심사·비용 조건을 검증하지 않은 카카오톡 연동을 약속하지 않는다. [카카오톡 메시지 이해하기](https://developers.kakao.com/docs/ko/kakaotalk-message/common), [공식 FAQ](https://developers.kakao.com/docs/ko/kakaotalk-message/faq) |
| Discord 웹훅 | 발송 채널로 적절하지만 무제한 채널은 아니다. 429가 발생하면 Retry-After 또는 retry_after에 따라 재시도해야 한다. 공급자 API의 성공 응답과 사용자의 실제 열람도 구분한다. [Discord Rate Limits](https://docs.discord.com/developers/topics/rate-limits) |
| GitHub 웹훅 | Codex의 ‘실패한 전달을 자동 재전송하지 않는다’는 설명은 맞다. 수신하지 못한 이벤트까지 복구하려면 권한 있는 사용자의 수동/API 재전송 경로가 필요하다. 공식 안내의 재전송 대상은 최근 3일이며 무기한 복구를 보장하면 안 된다. [실패 전달 처리](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries), [재전송 안내](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks) |
| Grafana Cloud 무료 플랜 | Claude의 무료 플랜 제안은 유효하다. 다만 사용량과 보존 기간 제한이 있으므로 몇 달의 원본 관측 데이터를 계속 보관한다고 가정해서는 안 된다. 장기 비교에 필요한 집계·실험 결과는 별도 보관한다. [Grafana 공식 가격·보존 조건](https://grafana.com/pricing/) |

공식 API를 택하면 실패 가능성이 사라진다는 뜻도 아니다. 반대로 외부 API를 택했다고 2~3개월 안에 실제 장애가 반드시 발생하는 것도 아니다. 데이터 변경·정기 발송은 정상 운영 이벤트로 기록하고, 의도적으로 차단한 상황은 장애 훈련으로 표시해야 한다.

### 1.4 구현·운영 동작에서 바로잡을 주장

| 문서의 주장 | 검토 |
|---|---|
| agy: Redis Pub/Sub로 티켓 오픈 알림 대량 발송 | Pub/Sub 자체는 영속 큐가 아니며 at-most-once 전달이다. 소비자가 끊긴 동안 메시지가 유실될 수 있다. 재처리가 필요한 알림의 원장은 DB 작업 테이블/Outbox에 남기는 편이 이 규모에 적합하다. [Redis 공식 문서](https://redis.io/docs/latest/develop/pubsub/) |

## 2. 네 후보군의 최선 변형과 채점

점수는 실측이나 채용시장 통계가 아닌 상대 평가다. 1은 불리, 3은 조건부로 적절, 5는 매우 적합이다. 기존 도입 확약·홍보 예산·유료 인프라는 없다고 가정한다. 운영 이벤트는 데이터 수정, 작업 지연, 배포, 정리·복구처럼 처리할 일이 생기는 정도를 말하며 장애나 대규모 부하의 발생을 보장하지 않는다.

각 군에서는 다음 변형을 고른다.

- **수집+알림:** 한 지역·한 관심 분야의 청년 지원정책/교육 모집 공고를 공식 원천 하나에서 수집하고 신규·수정·마감을 Discord 묶음 알림으로 전달한다. Claude의 파이프라인 운영과 Codex의 좁은 범위를 결합한다. agy의 ICS는 후속 읽기 기능으로 남긴다.
- **운영 감시 도구:** 실제 백업·배치의 성공/실패 신호를 받는 heartbeat 서비스다. 임의 URL 스캐너보다 SSRF·리다이렉트·대형 응답 처리 부담을 줄일 수 있다. 초기에는 단순 주기와 유예시간만 지원한다.
- **스터디/모임 도구:** 정원제 모임 신청·취소·대기자 승격·알림이다. 음성, 예치금·벌금 정산, 범용 과제 첨삭은 MVP에서 제외한다.

## 3. 다른 안의 약점과 과장

### Claude 안

1. **‘본인이 취준생이므로 실사용 보장’은 철회해야 한다.** 포트폴리오를 만드는 사람이 그 공고 원천의 실수요자인지, 기존 알림보다 나은지 확인되지 않았다. 본인 사용은 가치 있지만 외부 사용자 검증과 구분해야 한다.
2. **‘주변 취준생 대부분이 서버를 갖고 있다’, ‘사용자를 모으기 쉽다’는 근거가 없다.** 배포 경험이 없는 동료도 있을 수 있다. 실제 감시할 서버와 도입 의사를 먼저 조사해야 한다.
3. **‘트래픽이 거의 없으면 운영할 거리가 없다’는 기준은 너무 강하다.** 저트래픽에서도 인증서 갱신, 의존성 패치, 복구 리허설, 데이터 정리, 설정 변경과 배포를 운영할 수 있다. 트래픽은 성능 문제의 기회를 늘리지만 운영 경험의 필요조건은 아니다.
4. **실사용 없는 티켓팅과 실제 모임의 정원 관리를 같은 이유로 배제하면 안 된다.** 전자는 합성 부하 데모에 그칠 수 있지만 후자는 실제 참가자의 좌석과 운영자 업무가 걸린 기능이다. 기능 이름보다 사용 맥락을 봐야 한다.
5. **‘관리형 DB를 쓰면 직접 운영 서사가 약하다’는 일반화도 수정해야 한다.** OS·DB 엔진 관리 경험은 줄지만 마이그레이션, 권한, 쿼리, 데이터 보존, 복구 설계는 남는다. 어떤 운영 책임을 경험하려는지에 따라 선택하면 된다.
6. 수집 소스 7개, 스키마 변경 장애 3건, 유실 0건은 예시라고 밝혔더라도 미래에 확보할 수 있는 성과가 아니다. 원천 하나부터 시작하고 실제 기록을 바탕으로 문장을 만들어야 한다. ‘외부 의존성이 있으므로 자연 장애가 생긴다’도 사건의 시점·빈도까지 보장하지 않는다.
7. A1에 앱 2개·DB·Redis·Prometheus·Grafana·Loki를 한꺼번에 올리는 기본형은 시작 범위가 넓다. 배포 시 최대 사용량을 먼저 측정하고 관측 도구는 필요한 것부터 추가하는 편이 1인 운영에 맞다.

### agy 안

1. **평가 비율이 모두 근거 없다.** ‘상위 5%’, ‘흔한 정도 5% 미만·3% 미만·30%’는 조사 모집단과 자료가 없다. 숫자를 제거하고 차별성이 생기는 조건을 설명해야 한다.

5. **한도가 작은 상태와 최적화 필요성을 혼동했다.** 작은 ICS 파일에 스트리밍, 소수 모임에 Redisson 락, 마감 카운트다운에 SSE를 기본으로 넣을 이유가 제시되지 않았다. 카운트다운은 서버 기준 마감 시각을 전달해 클라이언트에서 표시할 수 있고, 정합성은 우선 DB 제약과 트랜잭션으로 검토할 수 있다.
6. **안전성을 단정했다.** 봇 요청으로 유휴 회수 ‘완벽 방어’, 200GB로 ‘평생 운영’, PAYG로 ‘영구 제외’, 측정 범위 없는 ‘다운타임 0초’는 삭제해야 한다. 소수 주기 요청이 정책의 사용률 기준을 충족한다는 근거는 없다.
7. **크롤링·감시의 보안과 허용 범위가 부족하다.** Jsoup와 지터는 접근 허용이나 IP 차단 해제를 보장하지 않는다. 임의 URL 감시는 사설망·메타데이터 주소·리다이렉트에 대한 SSRF 방어가 필요하다. 상대 서버의 HEAD 응답만으로 실제 GET 서비스의 정상 여부를 동일하게 판단해서도 안 된다.
8. **음성·첨삭·익명 매칭·출석·예치금은 운영 범위가 크다.** 1인이 개발과 모집·콘텐츠 운영·분쟁 처리를 동시에 해야 한다. 정산과 음성을 빼도 실제 사용자에게 유용한 텍스트 기반 기능을 먼저 검증할 수 있다.
9. **Heap Dump 자동 수집은 조건을 제한해야 한다.** Old Gen 80%만으로 무조건 덤프하면 일시적 사용량 상승에도 큰 파일이 반복 생성될 수 있다. 지속 시간·빈도 제한·잔여 디스크·민감정보 접근을 함께 설계해야 한다.

## 4. 내 1라운드에서 철회·수정할 점

1. **모임 도구를 무조건 1순위로 둔 순위를 수정한다.** 운영자 확보가 쉬울 것이라는 추론에 무게를 너무 많이 줬다. 현재는 좁은 수집·알림을 1순위로 두되, 실제 반복 모임의 도입 확약을 얻으면 모임 도구가 다시 우선할 수 있다.
2. **Object Storage 설명의 계정 구분을 보완한다.** 내 20GB 설명은 비유료 상태를 명시한 범위에서는 맞다. PAYG로 전환할 때 Standard 20GB가 그대로 유지된다고 오해하지 않도록 이번 표에 계층별 차이를 추가했다.
3. **Email Delivery 불일치는 유지하되 결론을 제한한다.** 일 발송량 0이라는 표를 근거로 모든 무료 계정에서 메일이 불가능하다고 확대 해석해서는 안 된다. 실제 콘솔 한도와 시험 발송 확인 전에는 제품의 필수 채널로 고정하지 않는다는 판단이다.
4. **Outbox를 설명하며 ‘알림이 중복되지 않는다’고 표현한 부분은 수정한다.** 작업을 유실 없이 재개하도록 만들 수 있어도 외부 발송 성공 직후 프로세스가 죽으면 재전송 시 중복이 생길 수 있다. 수신자가 멱등 키를 지원하지 않으면 시스템 전체의 exactly-once를 보장할 수 없다. ‘재시도 가능한 영속 작업과 중복 완화’로 표현하겠다.
5. **‘중복 0건’은 관측 결과로만 쓴다.** 내 문서는 수치를 가정이라고 명시했지만, 24명·240건·6분·p95 30초 같은 값을 그대로 이력서 문장으로 복사하게 만들 위험이 있다. 실제 결과가 쌓인 뒤 기간·건수·측정 위치를 넣어 작성하도록 바꾸는 편이 낫다.
6. **CSV 내보내기의 장애 대안을 명확히 한다.** 서비스가 내려간 뒤 같은 서비스에서 CSV를 받는 기능은 대안이 아니다. 운영자가 사전에 내려받거나, 접근을 제한한 별도 위치에 최근 명단을 보관해야 장애 시 사용할 수 있다.
7. **변경분 수집을 API가 지원한다고 가정하지 않는다.** 수정시각·증분 조회가 없으면 페이지 전체 재수집과 내용 해시 비교가 필요하다. 지원 여부를 확인하기 전 ‘변경분만 호출해 비용 절감’ 같은 성과를 약속할 수 없다.
8. **알림 지연과 복구 시간을 더 엄격히 정의한다.** API 수락, 공급자 전달, 사용자의 열람은 다른 시점이다. p95의 시작·끝 지점을 정하고, DB 복원 시간과 OCI VM 전체 재구축 시간을 구분한다. 백업 주기만으로 RPO를 증명할 수 없고 마지막 복원 가능한 데이터 시점을 확인해야 한다.
9. **도구가 문제를 만든 뒤 해결하는 서사는 피한다.** 소수 이용자에게 필요한 정합성과 복구를 먼저 구현하고, 실제 병목이 관측되면 그때 인덱스·캐시·병렬성 변경의 전후를 비교하겠다.

## 5. 최종 추천과 개선안

### 1순위: 한 집단을 위한 공고 변경·마감 알림

청년정책 전체를 다루기보다 **한 지역 취업 스터디가 실제로 확인하는 교육·취업 지원 공고**로 좁힌다. 원천은 허용 조건과 인증키를 확인한 공식 API 하나, 발송은 Discord 한 채널로 시작한다. 첫 검증은 ‘공고가 있느냐’와 ‘사람이 이 알림을 계속 받겠느냐’ 두 가지다.

사람이 적어도 데이터 변경과 처리 이력·알림·복구를 다룰 수 있고, 실패 지점을 구분하기 좋다. 다만 단순 수집 반복을 실사용 성과로 세지 않는다. 구독 유지, 원문 링크 클릭, 사용자가 제보한 누락·오알림을 별도로 기록한다.

### 2순위: 정기 모임 신청·취소·대기자 승격

실제 운영자가 확보되면 가장 일찍 사용자에게 배포하기 좋다. 정상 신청·취소와 좌석 배정이 제품 가치에 직접 연결되고, 외부 API 승인·원천 변경의 영향도 작다. 모임 두 번의 사용 약속을 확보하면 1순위로 올릴 수 있다.

운영 감시 도구와 동점이지만 사용자에게 필요한 기능을 작게 완성하기 쉽다는 이유로 2순위로 둔다. 감시 도구는 그 도구에 실제로 의존할 작업을 모으는 비용이 있고, 자신이 중단됐을 때를 감시할 별도 경로까지 필요하다.

### 개선안: ‘취업 스터디 공고 브리핑’ 하나에 읽기용 캘린더와 운영 이력을 붙인다

네 서비스를 각각 만들지 않고 수집·알림 서비스 하나에 필요한 장점만 가져온다.

| 가져올 장점 | 적용 범위 |
|---|---|
| Claude의 수집 파이프라인 운영 | 원천별 마지막 성공·수집 실패·재처리 기록을 내부 화면에서 확인한다. MVP 원천은 하나다. |
| Codex의 실제 집단 도입 | 스터디 한 곳과 정기적으로 피드백을 주고받는다. 신청·출석·벌금 기능은 추가하지 않는다. |
| agy의 캘린더 편의성 | 실제 사용 의사가 확인되면 확정 날짜만 ICS로 제공한다. 즉시 알림은 Discord로 보내고 캘린더 갱신 시간을 보장하지 않는다. |
| 웹훅 수신함의 추적·재처리 관점 | 자체 발송 작업의 이력과 수동 재시도를 구현한다. 범용 외부 웹훅 중계 서비스로 확장하지 않는다. |
| 감시 도구의 누락 탐지 | 수집·백업 작업이 예정 시간까지 성공했는지 확인한다. 독립된 외부 감시 경로도 둔다. |

**완성 범위와 진행 순서**

1. 1~2주: 공식 원천의 사용 승인·필수 필드를 확인하고, 시험 구독 의사를 받는다. 이용자를 확보하지 못하면 대상이나 문제를 바꾼다.
2. 3~5주: 수집·목록·관심 조건·묶음 알림·중복 완화·처리 이력을 배포한다.
3. 6~8주: 실제 이용 피드백, 마지막 수집 시각, 오류·알림 적체·디스크·백업 성공을 관측한다.
4. 9~12주: 수집 중단·429·발송 직후 종료·백업 복원을 격리된 조건에서 훈련하고, 필요가 확인된 경우에만 ICS와 캐시를 추가한다.

**2 OCPU·12GB에 맞춘 운영 원칙**

Spring 앱·PostgreSQL·리버스 프록시를 중심으로 구성하고, CI에서 ARM64 이미지를 만든다. 배포 시 두 앱이 겹쳐 실행될 때의 최대 메모리와 CPU를 확인한다. 작업 실행 주체가 겹쳐도 데이터가 꼬이지 않도록 DB에 작업 상태와 선점·만료 정보를 남긴다. 로그·이력·백업에는 보관 기한을 둔다. 단일 VM에서 앱 교체를 검증한 사실과 서버 전체 장애에 견디는 고가용성을 구분한다.

**이력서에 남길 증거**

|---|---|

낯선 기술이나 큰 요청 수가 없어도 이 증거가 쌓이면 운영 경험을 구체적으로 설명할 수 있다. 최종 선택 기준은 봇 트래픽을 늘릴 수 있느냐보다 **실제로 필요한 사람이 있고, 그 사람에게 약속한 동작을 계속 지키며 결과를 검증할 수 있느냐**다.
