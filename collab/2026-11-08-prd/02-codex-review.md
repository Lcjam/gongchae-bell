# PRD 2라운드 교차 비판 · Codex

작성: 2026-11-08

대상: [Claude 초안](01-claude.md), [Codex 초안](01-codex.md), [agy 초안](01-agy.md). 기준: [CLAUDE.md](../../CLAUDE.md), [03-feasibility.md](../03-feasibility.md), [04-plan-2weeks.md](../04-plan-2weeks.md), 이번 라운드의 조율자 공유 사실.

**최종 PRD는 Claude 안의 간결한 구성을 바탕으로, Codex 안의 데이터 안전성·측정 정의와 agy 안의 구현 흐름을 골라 합치는 것이 좋다.** 기관 채용 이력과 데이터 기준 시각은 최소 제품 범위에 남기고, 근거 없는 성능·가동률·복구 목표와 부가 화면은 덜어내야 한다. 수집 실패를 공고 마감으로 바꾸는 규칙은 출시 전 수정해야 한다.

아래의 판정은 사실 오류, 미검증 주장, 제품 설정 제안, 설계상 위험을 구분한다. 페이지당 표시 건수 같은 설계값을 고르는 것과, 측정 근거 없이 성능을 보장하는 것은 다른 문제다. 이번 작업에서는 지정된 리뷰 파일만 작성하며 구현·지침·세 초안을 수정하지 않는다.

## 1. 사실 오류와 근거 없는 수치

### 1.1 경쟁 서비스와 차별점

이번에 공식 공개 화면을 직접 확인했다.

| 확인 사항 | 근거와 해석 |
|---|---|
| 기관정보 화면이 이미 있다. 2026년 지정 기관 342개라고 안내한다. | [잡알리오 공공기관정보](https://job.alio.go.kr/orginfo.do). ‘기관 관점의 정보가 없다’는 넓은 주장은 사용할 수 없다. |
| 기관비교 화면이 이미 있다. | [잡알리오 공공기관비교](https://job.alio.go.kr/orgcompare.do). 화면의 존재를 확인했으며 JS로 열리는 실제 비교 결과 항목은 이번에도 검증하지 못했다. |

| 기관 소개 상세에서 채용 이력·통계를 보지 못했다는 조율자 확인 결과가 있다. | 이번 요청에서 공유된 관찰이다. 내가 모든 기관 상세를 별도로 재검증한 결과가 아니며, 서비스 전체에 채용 이력이 없다는 증명으로 확대하지 않는다. |

**문서별 수정**

- Claude 문제 정의·가정 A1의 ‘공고 단위로만 탐색’, ‘잡알리오에 없는 기관 관점 정보’는 너무 넓다. 기관정보·기관비교의 존재를 반영하고, 최근 1년 공고 집계를 바로 볼 수 있는 이용 흐름의 가치를 검증해야 한다.
- Claude Q1은 ‘기관 화면이 존재하는가’라는 질문으로 다시 사용자에게 넘길 단계가 아니다. 존재는 확인됐다. 남은 경쟁 조사 과제는 비교 결과 항목과 채용 이력 집계의 제공 범위다.
- agy 문제 정의의 ‘누적 이력과 통계를 제공하지 않는다’는 단정은 확인 범위를 넘는다. ‘필터링 한계’ 역시 원래 서비스의 필터 존재와 사용성 문제를 구분해야 한다.
- Codex가 기존 서비스의 기능 부재를 확정하지 않은 점은 유지한다. 다만 기관 이력을 제공한다는 것만으로 독자성을 얻었다고 암시하지 않아야 한다.
- 조율자가 확인한 342개 기관은 현재 지정 현황이다. 이를 채용 API의 최근 1년 기관 수나 우리 서비스에 반드시 생겨야 할 기관 페이지 수로 사용하면 안 된다.

권고 차별점 표현은 **‘조건별 공고 탐색에서 기관의 최근 1년 공고 집계로 바로 이어지고, 집계 범위·누락·데이터 기준 시각을 함께 확인하는 경험’**이다. 경쟁 우위와 실제 이용 가치는 아직 검증할 가설이라고 쓴다.

| Claude·agy: 링크 대체로 원문 연결 문제 해결 | **규칙 적용과 유효성 보장 혼동** | 이번에 03의 공고 ID로 [잡알리오 상세](https://job.alio.go.kr/recruitview.do?idx=306805)가 열리는 것을 확인했다. 템플릿은 후보로 채택할 근거가 생겼지만, 모든 ID의 유효성이나 모든 기관 홈 링크의 자동 판별까지 입증된 것은 아니다. |

원천 품질의 101/504건, 깨진 문자 17건 등은 03의 특정 표본 관측이다. 운영 중에도 같은 비율이라고 가정하거나 링크 보정 후 이탈률이 줄었다는 성과로 바꾸지 않는다.

기관 통계에서 모집 예정 인원 필드를 합산한 값은 실제 입사자 수가 아니다. 재공고·여러 직렬·해석할 수 없는 값의 처리도 정해야 한다. Claude FR-13과 agy의 ‘총 채용 인원’, ‘규모 예측’ 표현은 **‘공고상 모집 예정 인원의 집계 가능한 값’**으로 제한하거나 의미 확인 전 합계를 제외하는 결정을 받아야 한다.

| agy: 링크 유효 연결률 100% | URL 치환 로그만으로 목적지의 가용성과 올바른 공고 내용을 검증할 수 없다. | 알려진 fixture의 대체 규칙 검증과 실제 목적지 표본 확인을 나누고 실패·미확인을 공개한다. |
| agy: 배포 다운타임 0초 | 1초 간격 표본에서 5xx가 없었다고 모든 시점의 중단이 0초인 것은 아니다. | Claude·Codex처럼 ‘정의된 외부 연속 요청에서 실패 0건’으로 한정한다. 연결·DNS·TLS 실패·타임아웃·잘못된 내용도 실패에 포함한다. |

페이지당 20건, 화면 폭 360px, 재시도 3회, 종료 유예 20초, 새벽 4시 백업, 보관 14일 등은 사실 오류라기보다 **설정 제안**이다. 다만 세 안의 근거 문서에 이미 확정된 값처럼 쓰면 안 된다. 필요한 설정은 설계·운영 문서에서 선택 이유와 검증을 남기고, PRD에는 제품 결과와 한계를 적는다.

agy의 ‘Email Delivery 한도 0 이슈 때문에 완전 배제’는 이번 기준 문서 03의 검증 내용이 아니다. 2주 MVP에서 이메일을 빼는 근거는 이미 확정된 범위 결정으로 충분하다. 후속 기능의 영구 불가능 사유로 옮기지 않는다.

## 2. 각 초안에서 가져갈 강점과 버릴 약점

| 초안 | 최종 PRD로 가져갈 강점 | 버리거나 줄일 약점 |

## 3. 2주 범위 초과와 빠진 필수 항목

### 3.1 범위를 줄일 항목

- **Claude의 공개 /status는 04에 없는 추가 화면이다.** 데이터 기준 시각은 기존 화면에 표시하고, 원시 수집·오류·재시도는 보호된 관측 도구에서 확인한다. 공개 상태 화면은 후속 후보로 남긴다.
- **기관 직무 분포·풍부한 타임라인·차트는 추가 고도화다.** 최소 기관 페이지는 기간이 명시된 공고 수·공고 이력과 정확히 정의된 모집 예정 인원 집계다. 그래프나 소개·조직도를 더 만들지 않는다.
- **추적을 위한 원문 이동 전용 시스템·방문자 식별 기능**은 MVP에 필수인 사용자 기능이 아니다. 개인정보를 최소화한 집계와 직접 피드백부터 시작한다.
- **범용 상세 작업 큐·관리 화면·자동 대체 원천 전환**은 과하다. 미수집 작업의 상태와 재개는 필요하지만 별도 제품처럼 확장하지 않는다. API 장애 중에는 저장된 정상 데이터 제공이 우선이다.
- **모든 과거 공고의 상세 갱신과 완전한 변경 이력 복원**은 넣지 않는다. 기관 이력에 필요한 목록과 실제 진행 공고의 상세 준비를 구분한다.
- **Open Graph·검색엔진 등록·복잡한 sitemap/canonical 정책**은 제품·복구 Must보다 먼저 할 일이 아니다. 기본 title·설명·공개 정책을 넣고 추가 SEO는 Should로 둘 수 있다. 04 범위를 줄이는 부분은 최종 결정에 명시한다.
- **특정 인덱스·해시 알고리즘·첨부 정규화 방식·TLS 버전·종료 초수**는 설계 선택이다. 요구하는 성능·보안·복구 결과와 직접 연결되지 않는 선택은 PRD에서 빼도 된다.

이 제안이 기관 이력 자체나 배포·백업·관측을 미루자는 뜻은 아니다. 그것들은 확정 방향과 프로젝트 목적에 직접 연결돼 있다. 범위를 바꾸려면 사용자가 승인한 변경을 최종 PRD에 남겨야 한다.

## 5. 내 01 초안에서 철회하거나 수정할 점

1. **문서 길이와 중복을 줄인다.** FR·NFR·지표·위험·열린 질문에서 같은 안전 조건을 반복했다. 최종 본문은 제품 결과와 출시 차단 조건에 집중하고 설계 매핑은 관련 문서로 옮기겠다.
2. **원문 대체 링크의 미확인 상태를 갱신한다.** 1라운드에는 03에 명시되지 않았다는 이유로 검증을 보류했다. 이번에는 공식 상세 페이지가 열리는 것을 확인했다. 링크 템플릿의 후보 채택은 지지하되 전량 유효성이나 자동 분류가 검증됐다고는 말하지 않는다.
3. **‘비교’를 목록 비교로 단정한 부분을 제품 제안으로 내린다.** 04는 목록 중심이지만 사용자의 ‘부트텐트 같은 비교 웹’이 나란히 비교까지 뜻하는지는 명시되지 않았다. MVP는 공통 항목 목록 비교를 권고하고, 사용자에게 그 해석을 확인해야 한다.
4. **모든 기술 불확실성을 사용자 질문으로 만들지 않는다.** 기관코드·필터 표시명·API 일 예산 경계는 개발자가 확인해야 할 사실이다. 잘못된 공고 마감을 허용할지 역시 사용자 취향으로 묻지 않는다. 다만 수집 정책이나 범위 변경의 최종 승인은 사용자에게 남긴다.
5. **작업 상태 관리를 범용 큐처럼 읽히게 하지 않는다.** 재시작 후 재개, 불필요한 상세 중복 호출 방지, 호출 예산과 배포 중 실행 겹침 방지는 유지한다. 이를 위한 별도 작업 관리 제품을 만드는 뜻은 제거한다.
6. **‘완결 수집’의 검증 한계를 밝힌다.** 현재 API가 시점 일관 스냅샷을 제공한다고 확인되지 않았다. 고정 fixture의 완결 검증과 실제 API 실행의 페이지·건수 관측 기록을 분리한다.
7. **필수 데이터와 표시용 누락을 나눈다.** 잘못된 최상위 응답·식별자·잘린 목록과 단순 표시값 누락을 같은 정도의 실패로 취급하지 않겠다. 깨진 문자만으로 모든 수집이 계속 실패하는 설계를 요구하지 않는다. 구분 기준은 필드 계약에서 정한다.
8. **기관 페이지의 합격선을 더 작게 쓴다.** 정확한 기관 범위와 이력은 유지하되 코드의 존재 자체를 제품 가치로 삼지 않는다. 식별 방식은 검증한 계약을 토대로 ERD에서 결정한다.
9. **기준선 전에도 운영 가능한 초기 정책을 둔다.** 성능·가용성 성과 목표는 측정 후 정하되, 첫날 경보·재시도·백업 보관 같은 설정이 무기한 미정이면 안 된다. 초기 설정과 그 이유를 문서화하고 시험한 뒤 조정한다.
10. **SEO 전체를 한 묶음으로 미룬 부분을 나눈다.** 기본 페이지 설명·공개 접근 정책과 고도화·검색엔진 등록을 분리한다. 나의 ‘Should’와 04의 포함 범위가 다르므로 조율자의 최종안에 변경 제안임을 명시해야 한다.

## 6. 최종 PRD 권고안

### 6.1 문제 정의와 차별점

**권고 문제 정의**

공공기관 신입 준비자가 직무·지역·고용형태에 맞는 진행 공고를 좁혀 보고, 지원을 검토하는 기관의 최근 1년 공고 맥락까지 같은 흐름에서 확인하도록 돕는다. 원문 링크·누락·수집 지연 때문에 정보를 과신하지 않게 한다.

기존 잡알리오에도 필터·기관정보·기관비교가 있다. 우리 제품의 빠른 경로와 기관별 공고 집계가 더 유용한지는 첫 사용자 과업으로 확인한다. ‘모든 개발자 공고’, ‘기관별 채용 예측’, ‘실시간 수정 추적’을 약속하지 않는다.

**차별점 후보는 두 층으로 분리한다.**

- 사용자 가치: 조건을 유지한 목록 공유, 신입 지원 가능 바로가기, 기관별 기간 집계와 이력으로 이어지는 짧은 흐름, 데이터 기준 시각과 한계 표시.
- 포트폴리오 가치: 실패 시 상태 보존, 호출 예산, 변경 관측, 앱 교체·롤백, 외부 감시, 복원 리허설의 재현 가능한 기록.

운영 도구를 많이 설치했다는 사실을 사용자 차별점으로 설명하지 않는다.

### 6.2 Must 목록

04의 핵심 화면과 운영 목적을 유지한 최소안이다. 상세한 구현 방식은 설계에서 정한다.

| ID | Must 결과 | 최소 수용 기준 |
|---|---|---|
| M-01 | /jobs 조건별 목록 | NCS·지역·고용형태·채용구분·상태·제목·정렬·페이징이 함께 동작하고 URL에 유지된다. 신입 지원 가능은 R2010 또는 R2030이며 클릭이 외부 API 호출을 만들지 않는다. |
| M-02 | 홈의 마감 임박·오늘 공고·바로가기 | 날짜 기준과 ‘오늘’의 의미를 명시한다. 초기 이력 적재 시각 때문에 과거 공고가 오늘 신규로 나오지 않는다. 빈 상태와 데이터 기준 시각을 확인할 수 있다. |
| M-03 | /jobs/{sn} 상세와 원문 | 준비된 자격·우대·전형·첨부를 정확히 보여 주고 상세 미수집·실패를 구분한다. 검증한 링크로 이동하며 없는 공고는 404다. |
| M-04 | 최소 기관 이력 페이지 | 최근 1년의 집계 기간·기관 범위·고유 공고 수·이력이 일치한다. 인원 합계는 의미·형식이 확인된 모집 예정 인원만 집계하고 불명확한 값은 분리한다. 차트·소개 복제는 없다. |
| M-05 | 최초 목록 적재와 신규 상세 준비 | 날짜·조건·페이지·실제 건수를 기록하고 재실행 중복을 막는다. 과거 전체 상세와 초기 진행 상세의 준비 정책을 구분한다. |
| M-06 | 정기 수집과 상태 안전성 | 정상 주기당 목록 요청 한 번을 기본으로 하고 완결성을 검사한다. 제한된 재시도도 예산에 포함한다. 실패·잘린 응답·단순 누락으로 공고를 일괄 마감하지 않는다. |
| M-07 | 변경 관측·상세 보존·품질 표시 | 비교할 목록 필드를 정의하고 동일 입력·파생값 변경은 제외한다. 목록의 빈 배열이 상세를 지우지 않으며 변경 관측과 상세 최신성을 구분한다. |
| M-08 | 운영 가시성·안전한 호출 | 실행 결과·마지막 완전 성공·상세 대기·호출 시도 수를 확인하고 수신 경로가 검증된 운영 알림이 있다. 재시작·겹친 앱 때문에 예산과 작업이 중복 소비되지 않는다. |
| M-09 | 공개 배포와 운영 증거 | HTTPS, CI/CD, 앱 교체·롤백 시험, 웹 외부 감시, 작업 누락 감지, 백업·외부 사본·격리 복원, 장애 훈련과 문서가 있다. |

Should: 추가 SEO·검색엔진 등록, 공개 수정 배지, 구체적 사용자 피드백에서 나온 화면 보완. Could를 채우기 위한 모호한 기능은 만들지 않는다.

로그인·개인 알림·북마크·댓글·다른 원천·ICS·React·Redis·Spring Batch·첨부 재호스팅은 기존 제외 범위를 유지한다. 사용자 알림과 운영자 알림을 구분한다.

### 6.3 비기능 요구사항과 지표

| 분야 | 최종 PRD에 둘 요구 | 측정·출시 판정 |
|---|---|---|
| 성능 | 목록·상세·기관의 응답 시간과 오류율을 재현 가능하게 측정한다. | 데이터 크기·필터·동시성·수집 동작·장비를 남긴다. p95 목표는 기준선 측정 후 설정한다. |
| 수집 신뢰성 | 예정 실행 대비 완전 완료, 마지막 완전 성공 이후 경과, 상세 대기와 예산 소진을 관측한다. | 실행 누락과 재시도를 분리한다. 주기는 계획의 1시간이며 지연 상한을 보장하지 않는다. 초기 경보 정책을 명시하고 실제 발동을 검증한다. |
| 가용성·배포 | 단일 VM의 앱 교체 중 요청 유지와 실패 시 기존 버전 복귀를 검증한다. | 고정한 외부 시험에서 실패 0건을 목표로 하고 조건·결과를 기록한다. 월 99.9%·절대 0초라는 미검증 목표는 두지 않는다. |
| 보안 | 비밀값·관리 엔드포인트·DB 비공개, 안전한 출력·링크, HTTPS, 의존성 점검 | 코드·fixture·로그·외부 접근 시험과 CI 결과로 확인한다. 비밀값은 환경변수·GitHub Secrets로만 관리한다. |
| 자원·보존 | 정상·수집·배포 겹침의 메모리·CPU·디스크를 관측하고 로그·백업 보관 정책을 둔다. | 03의 자원 추정을 보장으로 쓰지 않는다. 실제 한계와 조정 이유를 기록한다. |
| 복구 | 백업·외부 사본이 복원되고 필요한 데이터와 화면을 확인할 수 있다. | 복원된 데이터 시점과 단계별 소요 시간을 남긴다. RTO·RPO 수치 목표는 첫 리허설 후 설정한다. |
| 문서·운영 | 실행 결과와 결정이 저장소 증거로 남고 다른 사람이 절차를 재현할 수 있다. | PRD·설계·ADR·runbook·스프린트 리뷰·릴리스·관측·복원·사건 기록을 연결한다. |

목표 지표는 사용자 과업·이용, 수집, 웹 성능, 배포, 복구 정도로 묶는다. 사용자 요청·봇·내부 점검·시험을 가능한 범위에서 분리하고, 식별이 불가능한 요청을 사용자 수로 바꾸지 않는다.

### 6.4 2주 MVP 완료 기준

- 사용자가 확정한 Must 범위와 위 수용 기준을 검증한다. 기관·상세가 필수라면 수집 의존성도 필수로 두고 본문·우선순위·체크리스트를 맞춘다.
- 최근 1년 목록 적재의 실제 조건·건수·검증 결과와 초기 상세 준비 범위가 기록돼 있다.
- 실제 응답 기반의 비밀값 없는 fixture로 재수집·변경·누락·실패·상세 분리·예산과 실행 겹침을 검증하고 CI가 통과한다.
- 공개 HTTPS에서 핵심 화면과 빈 결과·404·상세 대기·지연 상태를 확인할 수 있다.
- 커밋·이미지·배포 버전이 연결되고 성공 배포와 실패 롤백의 외부 연속 요청 기록이 있다.
- 웹 외부 감시와 수집·백업 누락 경보를 구분해 시험하고 운영자가 알림을 실제로 받았다.
- OCI 외부 사본을 포함한 백업과 격리 환경 복원에 성공했으며 데이터 시점·서비스 확인·소요 시간이 있다.
- 성능·자원 기준선과 선택한 장애 훈련 회고가 있다. 개선이나 실제 장애가 없으면 그 수치를 만들어 넣지 않는다.
- 프로젝트의 DoD 다섯 항목과 저장소 산출물 조건을 충족한다. 두 스프린트 리뷰와 배포·관측·복구 문서를 남긴다.
- 미완료 Must는 완료로 간주하지 않는다. 범위 변경은 사용자가 승인한 내용과 이유를 최종 PRD·계획에 반영한다.

월 가동률·검색 색인·방문자 목표는 2주 출시 체크리스트에 넣지 않는다. 후속 운영에서 기간을 확보한 뒤 평가한다.

## 7. 사용자 결정이 필요한 열린 질문

중복을 제거하고 제품·일정·비용·개인정보에 영향을 주는 것만 남긴다. 아래 권고는 승인된 결정이 아니다.

| ID | 질문 | 권고·영향 |
|---|---|---|
| U-01 | ‘비교’의 MVP 의미는 공통 항목 목록 비교인가, 선택한 공고의 나란히 비교까지인가? | 이번에는 목록·필터 공유와 기관 이력 연결을 권고한다. 나란히 비교가 필수면 다른 범위를 조정해야 한다. |
| U-02 | 기관 이력의 출시 최소 범위와 공개 기간을 어디까지로 할 것인가? | 최근 1년 공고 수·이력을 필수로 하고, 모집 예정 인원은 의미가 확인된 집계와 한계를 함께 표시한다. 직무 분포·차트·무기한 공개는 후속으로 둔다. 기존 계획에서 줄이는 항목은 명시적으로 승인한다. |
| U-03 | 초기 진행 공고 상세를 준비하는 범위와 기존 상세 변경의 보장 수준은 무엇인가? | 과거 전체 상세는 제외한다. 초기 진행 공고를 예산 내 준비하고 미수집을 표시한다. 기존 상세의 자동 재조회까지 요구하면 ‘신규만’ 정책·호출 예산·일정을 수정해야 한다. |

| U-05 | 서비스 이름과 도메인은 무엇을 쓰며 새 비용을 허용할 것인가? | 무료 또는 보유 도메인으로 시작하는 안을 권고한다. 유료 구매는 별도 결정하며 MVP에서 결제부터 진행하지 않는다. |
| U-06 | 방문 측정에서 외부 분석 서비스나 사용자 식별을 허용할 것인가? | 최소 집계와 직접 피드백을 우선한다. 외부 도구·식별을 원하면 필요한 고지·보관 정책과 측정 한계를 정한다. |
| U-07 | 첫 사용성 검증을 어느 집단에, 어떤 방식으로 요청할 수 있는가? | 접근 가능한 취업 스터디·커뮤니티를 정한다. 사용자 모집이나 메시지 전송은 별도 허가 없이 수행하지 않으며 근거 없는 인원 목표는 두지 않는다. |
| U-08 | 지침을 바꿔야 하는 수집 정책 확대를 지금 허용할 것인가? | 정기 목록 추가 페이지와 공개 JSON 자동 대체는 지침·계획과 함께 결정한다. 기존 상세 재조회는 U-03에서 결정한다. 현 규칙을 유지하면 불완전 수집을 알리고 마지막 정상 데이터를 제공한다. |

**배포 전 받아야 할 사용자 입력**: 실제 OCI shape·자원, 사용할 도메인의 소유·DNS 접근, 운영 알림 수신 경로, OCI 외부 백업 사본 위치. 이미 검증된 API 키를 다시 파일로 받거나 저장하지 않는다.

**개발자가 확인할 과제**: 기관 식별 필드와 표시명 매핑, 상세 필드 계약, 원문 링크 판별·대체의 검증 범위, 일 호출량의 집계 경계, 기관비교의 실제 항목, 적절한 JDK·CSS·재시도·관측 설정. 기술 사실과 합리적인 구현 선택을 사용자 취향 질문으로 넘기지 않는다.

조율자는 합의되지 않은 제품 범위와 정책 변경만 사용자에게 결정받고, 근거가 없는 경쟁 우위·수치 보장·잘못된 상태 판정은 최종 PRD에서 정리해야 한다.
