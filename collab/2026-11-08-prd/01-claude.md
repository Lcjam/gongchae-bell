# PRD 1라운드 · claude 독립 초안

> codex와 agy의 01 초안을 읽기 전에 썼다. 수치는 [03-feasibility.md](../03-feasibility.md)에서 검증된 값만 썼다.

## 1. 문제 정의
- 공공기관 채용공고는 잡알리오에 모여 있지만 **공고 단위로 탐색하게 되어 있다.** "이 기관은 1년에 몇 번, 몇 명을, 어떤 직무로 뽑는가" 같은 **기관 관점의 정보**를 보려면 공고를 하나씩 열어야 한다. *(가정: 잡알리오에 기관별 이력이나 통계 화면이 없다고 봤다. 확인 필요, 아래 열린 질문 Q1)*
- 진행 중 공고 504건 중 **20%(101건)는 원문 링크가 개별 공고가 아니라 기관 첫 화면**으로 연결된다 (실측). 지원 페이지를 찾는 데 시간이 든다.
- 공고가 **정정되거나 변경되어도 추적하기 어렵다.** *(가정)*
- 포트폴리오 측면의 문제: 이 서비스는 **실제로 운영되는 공개 웹**이어야 배포, 관측, 복구 경험을 증거로 남길 수 있다.

## 2. 대상 사용자
| 페르소나 | 상황 | 원하는 것 |
|---|---|---|
| P1 공공기관 신입 준비생 | 여러 기관에 지원할 계획. 직무와 지역이 정해져 있다 | 조건에 맞는 진행 중 공고와 마감 임박 공고를 한 화면에서 보기. 기관이 얼마나 자주 뽑는지 알기 |
| P2 IT 직군 신입 준비생 (사용자 본인 포함) | 정보통신 직무 신입 공고가 연 954건(정규직 230건) 있어서 흩어져 보인다 | 정보통신 + 신입 필터를 바로 적용한 목록과 링크 공유 |

부차 이해관계자: **포트폴리오를 보는 면접관.** 이 서비스가 실제로 운영되고 있다는 증거(최신성, 상태)를 볼 수 있어야 한다.

## 3. 목표와 측정 지표
| 목표 | 지표 | 측정 방법 | 목표값 |
|---|---|---|---|
| G1 데이터 신뢰성 | 수집 성공률, 마지막 성공 이후 경과 시간, 반영 지연(API에 공고가 생긴 뒤 사이트에 보일 때까지) | `collect_run` 테이블, Prometheus 지표 | 반영 지연 ≤ 수집 주기(1시간). 이건 **설계값**이다. 성공률은 2주 운영 후 기준선을 보고 설정 |
| G2 실제 사용 | 주간 방문자 수, 페이지뷰, 검색 유입 비율 | 방문 분석 도구 (Q2) | **기준선 측정 후 설정** |
| G3 배포 안전성 | 배포 횟수, 배포 중 외부 연속 요청 실패 수, 롤백 횟수 | CI 기록, 배포 중 외부 요청 스크립트 | 배포 중 실패 **0** (무중단 설계 검증 기준) |
| G4 복구 능력 | 복원 리허설 소요 시간, 복원된 데이터 시점 | 리허설 기록 | **첫 리허설에서 기준선 측정** |

## 4. 범위 (2주 MVP)
**포함**: 공고 수집(최초 1년 적재, 1시간 주기 정기 수집, 변경 감지, 정제) · 웹(홈, 목록, 상세, 기관 페이지, 상태 페이지) · SEO 기본 · CI/CD · 무중단 배포 · 관측과 알림 · 백업과 복원 리허설 · 운영 문서

**제외** (백로그로만 남긴다): 로그인 · 관심 공고 · 알림 구독 (디스코드, 이메일) · 후기와 댓글 · 관리자 화면 · React와 SPA · Redis · Spring Batch · 첨부파일 저장 (링크만 둔다) · 다중 데이터 원천 (온통청년 등)

## 5. 기능 요구사항
### 수집
| ID | 우선순위 | 요구사항 | 수용 기준 |
|---|---|---|---|
| FR-01 | Must | 최근 1년 공고 최초 적재 | 적재 후 공고 수가 같은 조건의 API `totalCount`와 일치한다. 다시 실행해도 중복이 없다 |
| FR-02 | Must | 1시간 주기 정기 수집 (`ongoingYn=Y` 1회 호출, 공고번호 기준 upsert) | 실행마다 `collect_run`에 결과(받은 건수, 신규, 변경, 오류)가 남는다 |
| FR-03 | Must | 변경 감지 (내용 해시) | 필드가 바뀌면 `posting_change`에 1건이 생긴다. 안 바뀌면 생기지 않는다 |
| FR-04 | Must | 마감 처리 | 마감일이 지났거나 진행 중 목록에서 빠진 공고는 상태가 "마감"으로 바뀐다 |
| FR-05 | Should | 신규 공고만 상세 조회 (전형 단계, 첨부 목록) | 상세 호출 수가 그 회차의 신규 공고 수를 넘지 않는다 |
| FR-06 | Must | 정제: 기관 첫 화면 링크를 `job.alio.go.kr/recruitview.do?idx={sn}`로 대체, 깨진 문자 공고 표시 | 대체 규칙을 테스트로 검증한다 |
| FR-07 | Must | 실패 처리: 타임아웃, 재시도(`@Retryable`), 실패 기록, 운영 알림 | API 오류를 주입하면 재시도 후 실패가 기록되고 알림이 간다 |

## 6. 비기능 요구사항
| 구분 | 요구사항 | 측정과 검증 |
|---|---|---|
| 성능 | 목록과 상세의 서버 응답 p95 | Sprint 2에서 k6로 **기준선을 측정한 뒤** 목표를 설정한다 |
| 가용성 | 배포 중 외부 연속 요청 실패 0. 단일 VM이므로 고가용성은 범위 밖이라고 명시한다 | 배포마다 외부 요청 스크립트 결과를 기록 |
| 데이터 신선도 | 마지막 수집 성공 후 2시간이 지나면 알림 | Healthchecks.io와 Grafana 알림 |
| 외부 API 사용량 | 하루 호출 수가 한도 1,000회의 10% 미만 (설계상 약 54회) | 호출 카운터 지표 |
| 보안 | HTTPS만 허용. Actuator, DB, Grafana는 외부에 열지 않는다. 비밀값은 환경변수와 Secrets로만. 의존성 취약점 점검 | 외부 포트 스캔 결과와 Dependabot |
| 운영성 | 구조화 로그, HTTP와 수집 지표, 대시보드, 디스코드 운영 알림, 일 1회 백업과 보관 기간, 런북 | `docs/ops/`, `docs/runbook.md` |
| 이식성 | ARM64(OCI A1)에서 동작. 서버를 문서만 보고 다시 구성할 수 있다 | 런북 |

## 7. 완료 기준 (2주 MVP)
- [ ] Must 기능 요구사항을 모두 충족하고 HTTPS 공개 URL로 접속할 수 있다
- [ ] `main`에 머지하면 자동 배포되고, 무중단 검증 결과(배포 중 실패 0)가 기록돼 있다
- [ ] 대시보드, 운영 알림, 외부 감시가 동작한다
- [ ] 백업이 자동화돼 있고 복원 리허설 기록이 1회 이상 있다
- [ ] 포스트모템이 1건 이상 있다 (훈련이면 훈련이라고 표시)
- [ ] PRD, 설계 문서, ADR, 런북, 스프린트 리뷰 2건이 저장소에 있다

## 8. 가정과 리스크
| 구분 | 내용 | 대응 |
|---|---|---|

| 리스크 R1 | 같은 API를 쓴 공개 프로젝트가 여럿 있다 | 기관 정보와 운영 기록으로 차별화 |
| 리스크 R2 | 화면 작업 때문에 일정이 밀린다 | Should와 Could는 미룬다. 디자인은 CSS 프레임워크 기본값 |
| 리스크 R3 | 검색 유입이 생기지 않는다 | G2는 기준선만 잡는다. 운영 목표(G1, G3, G4)는 트래픽과 무관하게 달성할 수 있다 |

## 9. 열린 질문 (사용자 결정 필요)
- **Q1**: 잡알리오에 기관별 이력이나 통계 화면이 이미 있는가? 있으면 차별점을 다시 잡아야 한다 → 조사를 먼저 한다
- **Q2**: 방문 분석 도구: 웹 서버 로그 집계로 할지, 외부 경량 분석 서비스를 쓸지 (개인정보 고지 범위가 달라진다)
- **Q3**: 서비스 이름과 도메인: DuckDNS 무료 서브도메인으로 할지, 유료 도메인을 살지
- **Q4**: Java 21과 25 중 무엇으로 할지
- **Q5**: 마감 공고를 사이트에 얼마나 오래 보여 줄지 (1년? 전체?)
- **Q6**: 첫 사용자를 어디서 모을지 (스터디, 커뮤니티)
