# PRD 독립 초안 · 공공기관 채용 비교 웹

작성: Codex · 2026-11-08 · PRD 1라운드

이 문서는 3자 검토를 위한 제안이다. 다른 에이전트의 독립안은 읽지 않았다. 제품 방향과 2주 범위는 [확정 계획](../04-plan-2weeks.md), 프로젝트 규칙은 [CLAUDE.md](../../CLAUDE.md)를 따른다. 외부 사실과 검증 수치의 근거는 [실현 가능성 검증](../03-feasibility.md)으로 한정한다. 문서 간 차이와 미확인 항목은 아래에 명시했으며, 새 API 호출이나 외부 재검증은 수행하지 않았다.

## 1. 제품 정의와 문제

### 한 줄 정의

공공기관 채용공고를 자동 수집해 직무·지역·신입 지원 가능 여부로 좁혀 비교하고, 마감 임박 공고와 기관별 최근 1년 공고 이력을 보여 주는 웹 서비스다.

### 해결할 문제

- 공고를 찾는 과정에서 직무·지역·고용형태·채용구분을 반복해서 확인해야 한다. 같은 조건으로 여러 공고를 한 화면에서 살펴볼 수 있어야 한다.
- 현재 모집 공고만으로는 기관이 언제 어떤 직무를 모집했는지 파악하기 어렵다. 기관별 공고 이력과 집계 범위를 함께 제공한다.
- 공고를 발견해도 마감일, 지원 자격, 전형, 원문 경로를 다시 확인해야 한다. 마감 임박 모음과 상세 화면에서 다음 행동으로 이어질 수 있어야 한다.
- 외부 데이터에는 불완전한 링크와 깨진 문자가 있다. 잘못된 내용을 임의로 보정해 신뢰를 떨어뜨리지 않고, 수집 시각·확인 가능한 원문·누락 상태를 알려야 한다.

위 불편의 빈도와 시간 절감 효과는 아직 사용자 조사로 검증하지 않았다. 기존 서비스에 어떤 기능이 ‘없다’는 경쟁 우위 주장도 이 PRD에서 확정하지 않는다.

### 프로젝트의 목적

제품 목표는 조건에 맞는 공고를 발견하고 지원 여부를 판단하기 쉽게 하는 것이다. 개발자의 목표는 공개 배포 후 수집 신뢰성, 배포, 관측, 백업·복원, 보안 유지보수를 실제 기록으로 남기는 것이다. 제품 이용 지표와 내부 배치·운영 지표는 따로 집계한다.

## 2. 대상 사용자와 핵심 이용 흐름

두 페르소나는 실존 사용자의 조사 결과가 아닌 검증할 가설이다.

| 페르소나 | 상황과 목적 | 핵심 흐름 | 확인할 가설 |
|---|---|---|---|
| 신입 IT 취업 준비자 | 공공기관 채용 중 정보통신 분야와 신입 지원 가능 공고를 빠르게 찾고 싶다. | 홈의 바로가기 → 조건을 적용한 목록 → 공고 상세 → 공식 원문 확인 | NCS 정보통신 분류와 신입 지원 가능 필터가 실제 공고 탐색에 도움이 되는가 |
| 기관·지역 중심 취업 준비자 | 원하는 지역·기관의 모집 기회를 비교하고 기관의 과거 공고도 보고 싶다. | 지역·고용형태로 목록 조회 → 공고 상세 → 기관 이력 → 다른 공고 확인 | 기관별 공고 이력이 지원 계획을 세우는 데 도움이 되는가 |

‘정보통신’은 데이터 원천의 NCS 분류다. 이를 소프트웨어 개발자 채용과 동일하게 취급하거나 모든 개발자 공고를 포괄한다고 약속하지 않는다.

초기 이용자는 취업 스터디·커뮤니티에 서비스를 소개해 모집한다. 모집 인원이나 검색 유입을 보장하지 않으며, 소개 여부·관찰 기간·실제 피드백을 기록한다.

## 3. 근거, 제품 결정, 미확인의 구분

### 3.1 03-feasibility.md에서 가져온 사실

| 항목 | 검증된 내용 | PRD에서의 사용 |
|---|---|---|
| 원천 | 공공기관 채용정보 API의 list·detail, 개발계정 일 1,000회 | 공식 API만 기본 수집 경로로 사용하고 모든 시도를 호출 예산에 포함한다. |
| 공식 list 실호출 | 진행 중 공고 504건이 numOfRows=1000 요청 한 번에 반환됨 | 당시의 관측값이다. 이후에도 한 번에 모든 공고가 온다는 보장이나 최대 페이지 크기 보장으로 확대하지 않는다. |
| 공식 detail 실호출 | 공고 sn=306805에서 steps·files가 채워짐. 목록에서는 두 배열이 비어 있음 | 상세 데이터와 목록 데이터를 분리해 취급한다. 목록의 빈 배열로 저장된 상세를 지우지 않는다. |
| 식별·기간·필터 관련 필드 | recrutPblntSn, recrutPbancTtl, instNm, pbancBgngYmd, pbancEndYmd, decimalDay, ongoingYn, recrutSe, hireTypeLst, ncsCdLst, workRgnLst, recrutNope, srcUrl | 이름이 확인된 필드만 계약의 근거로 삼는다. 나머지 상세 필드의 매핑은 fixture 확인이 필요하다. |
| 필터 의미 | R2010 신입, R2030 신입+경력, R600020 정보통신, R1010 정규직. recrutSe는 코드 하나만 요청 가능 | 신입 지원 가능의 OR 조건은 저장된 데이터에서 처리한다. |
| 날짜·검색 | 요청 날짜 YYYY-MM-DD, 응답 날짜 YYYYMMDD. 제목 포함 검색 지원 | 날짜 변환을 명시적으로 검증한다. 화면 검색은 저장된 데이터에서 수행한다. |
| 변경 감지 | 수정시각 필드가 없음 | 변경 시각은 원천의 수정 시각이 아닌 서비스의 변경 관측 시각으로 표현한다. |
| 데이터 품질 | 공개 경로 표본에서 원문 링크가 기관 첫 화면인 사례와 깨진 문자 확인 | 개별 공고 링크·데이터 누락·깨짐에 대한 수용 기준을 둔다. 표본 비율을 전체 데이터의 고정 품질로 쓰지 않는다. |
| 정상 운영 호출량 | 1시간 주기 목록 24회와 신규 상세 약 30회를 합한 약 54회/일이라는 계산 | 계산에 기초한 예상이다. 초기 적재·재시도·복구를 포함한 실제 일 호출량은 별도로 기록한다. |

03에 나온 응답 시간은 해당 실호출의 관측값이다. 서비스 페이지 성능 목표나 외부 API 응답 시간 보장으로 사용하지 않는다.

### 3.2 확정 계획에서 가져온 제품 결정

Thymeleaf 서버 렌더링, 2주 MVP, 홈·공고 목록·공고 상세·기관 이력, 마감 임박 D-3 이내, 정기 수집 1시간 주기, 신규 공고 상세 수집, 사용자 로그인과 마감 알림 제외는 04-plan-2weeks.md를 따른다. 이들은 외부 서비스에 관한 사실이나 이미 달성한 성과가 아니다.

### 3.3 문서 차이와 확인 필요 사항

- 04의 최초 적재 11,784건은 03에 같은 조건으로 검증된 수치가 없다. 03의 다른 기간·필터별 집계와 섞지 않는다. 초기 적재의 실제 기간·필터·응답 건수를 기록하고 고정 건수를 완료 기준으로 삼지 않는다.
- 04의 기관코드와 이름 목록 필드들은 03의 명시된 필드 목록만으로 안정성과 전체 매핑을 확정할 수 없다. 기관 식별 기준과 필터 코드의 표시명 매핑을 fixture로 확인해야 한다. 기관명이 같다는 이유만으로 같은 기관이라고 단정하지 않는다.
- 04의 잡알리오 상세 링크 템플릿은 계획의 후보 경로로 취급한다. 03에는 그 템플릿의 동작 검증이 명시돼 있지 않으므로, 여기서 검증 완료 사실로 옮기지 않는다.
- ‘진행 중 목록에서 빠졌으므로 마감’이라는 04의 규칙은 보완을 제안한다. 불완전 수집·원천 오류·공고 철회와 정상 마감을 구분해야 한다.
- 사용자의 실제 OCI shape와 자원은 03에서 검증 범위 밖이다. A1 2 OCPU·12GB는 배포 계획의 가정이며 메모리 예산도 추정이다.

## 4. 목표와 측정 지표

수치 성과는 현재 없다. 근거 없는 방문자 수, 응답 시간, 가동률, 복구 시간의 목표는 **기준선 측정 후 설정**한다. 정확성·보안의 수용 조건과 계획에 명시된 수집 주기는 별도로 적용한다.

| ID | 목표·지표 | 정의와 측정 방법 | 측정 시점 | 목표·판정 |
|---|---|---|---|---|
| G-01 | 조건에 맞는 공고 탐색 | 대상 사용자에게 실제 희망 조건으로 탐색을 부탁하고 목록·상세·원문 확인 과정의 완료 여부, 막힌 지점, 피드백을 기록한다. | 첫 공개 배포 후, Sprint 2 리뷰, 후속 운영 중 | 완료율·탐색 시간의 수치 목표는 기준선 측정 후 설정 |
| G-02 | 실제 이용과 유입 | 홈·목록·상세·기관 화면의 요청과 원문 이동을 관측한다. 내부 점검·시험·식별 가능한 봇 요청을 분리하고 집계 기준을 명시한다. 요청 수를 곧 사용자 수로 표현하지 않는다. | 첫 배포부터, 각 스프린트 리뷰와 후속 운영 | 방문·재방문·클릭 목표는 기준선 측정 후 설정 |
| G-03 | 수집 지속성과 최신성 | 예정된 실행 대비 목록 수집 완료 비율, 마지막 완전 수집 시각으로부터 경과 시간, 실패 사유를 기록한다. 상세 수집 대기는 별도 집계한다. | 정기 수집 시작부터 매 실행, Sprint 2 리뷰 | 1시간 주기로 실행 시도. 지연 허용·알림 임계값은 기준선 측정 후 설정 |

| G-08 | 호출 예산 준수 | 초기 적재·목록·상세·재시도·수동 실행의 일별 호출 시도 수와 결과를 기록한다. 재시작·배포 후에도 합계를 잃지 않는다. | API 연동 시작부터, 매 실행 전후 | 03의 개발계정 일 1,000회 내에서 동작. 약 54회/일은 정상 운영 예상치이며 실측 목표가 아님 |
| G-09 | 운영 사건의 설명 가능성 | 배포·실패·훈련 기록에 영향, 탐지·복구 시각, 원인, 후속 조치를 남긴다. | 사건 발생 시, 각 스프린트 종료 | 증거가 연결된 기록 존재. 실제 장애 건수의 목표는 두지 않음 |

## 5. 2주 MVP 범위

### 포함

- 비회원이 사용하는 Thymeleaf 웹: 홈, 공고 목록, 공고 상세, 기관별 최근 1년 공고 이력·통계.
- NCS 직무, 지역, 고용형태, 신입/경력, 진행/마감 상태, 제목 검색, 마감일·공고 시작일 정렬, 페이징.
- 마감 임박과 오늘 시작한 공고, 신입 지원 가능·정보통신 바로가기.
- 공식 API 기반 최초 이력 적재, 정기 목록 수집, 신규 진행 공고의 상세 수집.
- 공고 ID 기반 중복 방지, 의미 있는 목록 변경 관측, 수집 결과·마지막 성공 시각 기록.
- 출처·수집 시각·누락 정보·개별 원문 링크의 품질 처리.
- 공개 HTTPS 배포, CI/CD, 앱 교체 배포·롤백 검증, 관측과 운영자 알림, 외부 생존 감시.
- DB 백업 자동화, OCI 외부 사본, 복원 리허설, 실패 주입 훈련과 회고.
- 기본 메타 정보와 검색엔진 접근 정책. 사이트맵·검색엔진 등록의 우선순위는 아래 FR을 따른다.

### 제외

- 로그인·OAuth2, 개인 프로필, 관심 공고 저장, 사용자별 구독과 마감 알림, 이메일·개인 DM.
- 후기·댓글·음성 제출·스터디 운영·예치금 정산.
- ICS 구독, 청년정책 등 다른 데이터 원천, 범용 웹훅 중계·감시 SaaS.
- React, Redis, Spring Batch, 별도 메시지 브로커.
- 지원 자격 자동 판정, AI 추천, 공고 전문 재작성, 모든 개발 직군의 정밀 분류.
- 원천 전체 변경 이력 복원, 과거 모든 상세의 일괄 수집, 상시 최신 상세 보장.
- 원문 페이지의 서버 측 크롤링·첨부파일 재호스팅.
- 기관의 실제 채용 실적·입사자 수 추정과 미래 채용 일정 예측.

운영자 Discord 알림은 포함하되, 구직자 대상 알림 기능과 구분한다. 제외 범위가 필요해지면 백로그 이슈로만 남기고 이번 스프린트에 추가하지 않는다.

## 6. 기능 요구사항

Must는 2주 MVP 출시 조건이다. Should는 Must 이후 적용하고 미완료 시 이유를 남긴다. Could는 출시 조건이 아니며 여유가 있을 때만 한다. 아래 수용 기준은 실제로 달성했다고 주장하는 값이 아닌 검증할 요구사항이다.

### FR-01 · 공고 목록과 비교 · Must

**요구:** 사용자는 /jobs에서 주요 조건을 함께 보며 공고를 좁힐 수 있다.

**수용 기준**

- 목록에 제목, 기관, 직무, 지역, 채용구분, 고용형태, 공고 시작일, 마감일과 날짜 기준 잔여일을 표시한다. 누락값은 ‘정보 없음’으로 구분한다.
- 직무·지역·고용형태·채용구분·진행/마감·제목 조건을 함께 적용하고 새로고침·페이지 이동 후에도 조건과 정렬을 유지한다.
- ‘신입 지원 가능’은 R2010 또는 R2030을 포함하며 ‘신입만’과 구분한다. 단일 코드만 받는 외부 API 필터 때문에 R2030을 누락시키지 않는다.
- 마감일·공고 시작일 정렬은 같은 값의 순서도 안정적으로 유지한다. 결과 없음, 마지막 페이지, 유효하지 않은 필터 값·페이지 요청을 처리한다.
- 화면 요청은 저장된 데이터를 조회한다. 이용자의 필터·페이지 클릭이 외부 API 호출로 이어지지 않는다.
- ‘비교’는 목록의 공통 항목 비교를 뜻한다. 별도의 공고 선택·나란히 비교 기능은 포함하지 않는다.

### FR-02 · 홈과 바로가기 · Must

**요구:** /에서 지금 확인할 공고를 발견할 수 있다.

**수용 기준**

- 확인된 진행 공고 중 날짜 기준 D-0부터 D-3까지를 마감 임박으로 표시하고, 이미 기한이 지난 공고는 제외한다.
- 한국 날짜 기준 오늘 공고가 시작된 항목과 신입 지원 가능·정보통신 목록으로 이동할 수 있다.
- ‘오늘’의 판단은 공고 시작일 기준이다. 1년치 최초 적재로 first_seen_at이 오늘인 과거 공고를 ‘오늘 등록’으로 올리지 않는다.
- 정확한 접수 종료 시각을 모르면 날짜 기준 안내임을 알리고 원문 확인 경로를 제공한다.
- 해당 항목이 없거나 수집이 지연된 경우 빈 상태와 데이터 기준 시각을 보여 준다.

D-3 범위와 한국 날짜 기준은 제품 규칙 제안이며, 정확한 시간 단위 마감 보장은 아니다.

### FR-03 · 공고 상세와 원문 이동 · Must

**요구:** /jobs/{sn}에서 공고 정보를 검토하고 공식 원문으로 이동할 수 있다.

**수용 기준**

- 저장된 목록 정보와 상세 정보가 있을 때 자격·우대·전형 단계·첨부 안내를 보여 준다. 상세 필드 매핑은 03의 검증 사실을 넘어 추정하지 않고 실제 fixture에서 확인한다.
- 목록의 빈 steps·files를 상세 없음의 증거로 취급하거나, 이미 저장한 상세 배열에 덮어쓰지 않는다.
- 상세 수집 대기·실패·과거 이력의 상세 미수집을 정상 데이터와 구분한다. 미수집을 ‘자격 제한 없음’, 빈 첨부를 ‘첨부 없음’으로 단정하지 않는다.
- 상세 수집 시각을 표시하고 목록 변경 관측만으로 기존 상세가 최신이라고 표시하지 않는다.
- 원문 링크가 개별 공고가 아니면 그 성격을 표시한다. 검증된 대체 링크가 확보된 경우에만 대체하고, 확인되지 않은 URL을 정상 원문처럼 제시하지 않는다.
- 없는 공고는 명확한 404 안내를 제공한다. 원문·첨부는 안전한 링크로 연결하며 사용자 요청 때 서버가 임의 URL을 대신 가져오지 않는다.

### FR-04 · 기관별 이력과 통계 · Must

**요구:** /institutions/{code}에서 해당 기관의 최근 1년 공고를 볼 수 있다.

**수용 기준**

- 실제 응답으로 검증한 기관 식별 기준을 사용한다. 기관명 중복·변경을 어떻게 다룰지 설계 문서에 명시한다. 기관코드 매핑이 확인되지 않은 상태에서는 완료 처리하지 않는다.
- 조회 기준일과 집계 기간, 데이터 수집 범위를 표시한다. 정한 기간의 공고 수·목록·공고상 모집 예정 인원의 집계 가능한 값 합계를 제공한다.
- 같은 공고 ID는 통계에서 중복 계산하지 않는다. 인원이 누락됐거나 합산할 수 없는 공고는 별도 표시하고 0명으로 바꾸지 않는다.
- ‘실제 채용 인원’이나 ‘기관의 전체 채용 실적’이라고 표현하지 않는다. 상세를 과거 전량 수집한 것처럼 표시하지 않는다.
- 이력이 없거나 최초 적재가 미완료이면 그 상태를 구분한다. 통계와 목록의 기간·기관 조건이 일치한다.

### FR-05 · 최초 이력 적재 · Must

**요구:** 최근 1년 공고를 페이지 단위로 가져와 목록과 기관 이력의 기반을 만든다.

**수용 기준**

- 요청의 시작·종료일, 필터, 페이지 크기, 받은 건수·고유 ID 수, 시작·종료 시각과 결과를 기록한다.
- 요청 날짜와 응답 날짜를 명시적으로 변환하고, 잘못된 날짜·깨진 문자·누락값을 임의로 채우지 않는다.
- 모든 대상 페이지의 정상 응답과 완결 여부를 확인한다. 중복·응답 건수 변동·파싱 실패 등으로 완결을 확인할 수 없으면 미완료로 남긴다.
- 재실행해도 공고 ID 기준으로 중복 적재되지 않는다.
- 과거 마감 공고의 상세를 전량 호출하지 않는다. 초기 진행 공고의 상세 준비는 FR-07의 예산·우선순위 정책을 따른다.
- 04의 11,784건이나 03의 과거 스냅샷과 일치한다는 이유로 성공을 판정하지 않는다. 해당 실행의 실제 응답과 검증 결과로 판정한다.

### FR-06 · 정기 목록 수집과 안전한 상태 반영 · Must

**요구:** 1시간마다 진행 중 목록 수집을 시도하고, 외부 장애가 있어도 기존 조회 서비스를 유지한다.

**수용 기준**

- 프로젝트 지침에 따라 ongoingYn=Y와 numOfRows=1000으로 정기 목록 요청을 원칙적으로 한 번 수행한다.
- HTTP 성공뿐 아니라 응답의 업무 결과·형식·필수 식별 정보와 받은 목록의 완결성을 확인한다.
- totalCount가 반환 목록보다 크거나 필수 정보가 깨진 경우 불완전 수집으로 기록한다. 추가 페이지 자동 호출은 별도 결정 전까지 활성화하지 않는다.
- 실패·불완전 수집 때 기존 정상 데이터와 마지막 성공 시각을 보존한다. 빈 배열을 받아 기존 전체를 일괄 마감시키지 않는다.
- **목록 누락만으로 마감을 확정하지 않는다.** 원천의 확인된 상태와 날짜 기준 표시를 구분하고, 예정 마감 전에 사라진 공고는 확인 필요 대상으로 기록한다.
- 일정 시점에 실행이 겹치거나 배포 중 앱이 함께 떠 있어도 같은 수집이 중복 실행·반영되지 않도록 한다. 중단 뒤 다음 실행을 재개할 수 있다.
- 조회 화면은 마지막 완전 수집 데이터와 기준 시각을 사용한다.

누락 시 마감 처리에 대한 보완과 한 번의 응답을 초과하는 경우의 정책은 04 대비 변경 제안으로, 합의 후 계획·설계에 반영해야 한다.

### FR-07 · 신규 진행 공고 상세와 호출 예산 · Must

**요구:** 신규 진행 공고의 상세를 수집하되 개발계정 예산과 조회 서비스의 안정성을 지킨다.

**수용 기준**

- 최초 과거 이력 적재를 모두 ‘신규 상세 대상’으로 간주하지 않는다. 초기 진행 공고와 운영 중 새로 발견한 진행 공고의 상세를 준비하는 정책을 구분한다.
- 상세 수집은 저장된 작업 상태로 관리하며 성공한 공고를 매 주기 불필요하게 다시 호출하지 않는다. 실패·미수집 작업은 예산이 허용할 때 재개한다.
- 외부 API의 모든 호출 시도는 예산에 포함한다. 초기 적재, 정기 요청, 상세, 타임아웃 후 재시도, 운영자 실행을 합산하고 일 한도에 도달하기 전에 중단·지연시킨다.
- 호출 예산과 작업 상태가 앱 재시작·blue/green 겹침 때문에 초기화되거나 중복 소비되지 않는다.
- 재시도 종료와 실패 원인을 기록하고 무제한 재시도하지 않는다. 고정 시간·횟수 설정은 기준선과 실패 유형을 근거로 문서화한다.
- 초기 상세 준비가 덜 됐거나 기존 상세 재수집을 하지 않은 상태를 화면과 운영 기록에서 숨기지 않는다.

기존 공고의 상세 변경을 계속 재확인하는 기능은 현행 ‘신규 상세만’ 정책 밖이다. 목록 변경 시 재조회할지는 열린 질문으로 둔다.

### FR-08 · 변경 관측과 수집 기록 · Must

**요구:** 수집 결과를 운영자가 검증하고 변경 발생을 추적할 수 있다.

**수용 기준**

- 비교할 목록 필드를 정규화하고 의미 있는 값이 바뀐 경우 변경 필드와 관측 시각을 남긴다.
- 수집 시각·decimalDay 같은 주기적으로 바뀌는 파생값이나 배열 순서만으로 불필요한 수정 사건을 만들지 않는다.
- 동일 입력 재수집은 신규 변경 기록을 만들지 않는다. 목록 변경과 상세 수집 결과를 혼동하지 않는다.
- 실행별 시작·종료·성공/실패/불완전, 받은 건수, 신규·변경·오류, 호출 시도 수를 확인할 수 있다.
- 운영자는 공개 관리 화면 없이도 보호된 로그·대시보드·운영 절차로 실패 원인을 확인하고 안전하게 재실행할 수 있다.
- 사용자에게 변경 시각을 보여 준다면 ‘서비스에서 변경을 확인한 시각’으로 표시한다.

### FR-09 · 데이터 기준 시각과 품질 안내 · Must

**요구:** 사용자는 공고의 누락·지연을 정상 정보와 구분할 수 있다.

**수용 기준**

- 목록·상세·기관 화면에 해당 데이터 기준 시각을 제공한다. 수집 실패 중에는 마지막 성공 시각을 최신 성공처럼 갱신하지 않는다.
- 깨진 문자는 임의 추론으로 복구하지 않는다. 원문 확인 안내와 운영 검수 대상으로 남긴다.
- 날짜 누락·해석 불가 공고를 임의로 마감 임박 모음에 포함하지 않는다.
- 원천의 제공 정보와 서비스가 계산·집계·관측한 값을 구분한다.
- 수집 지연 표시의 임계값은 운영 기준선 확인 후 정하고, 공개 운영 전 설정값과 근거를 문서에 남긴다.

### FR-10 · 검색엔진 접근과 페이지 설명 · Should

**요구:** 공개 페이지를 검색엔진과 사용자가 이해할 수 있게 한다.

**수용 기준**

- 페이지 제목·설명·canonical 정책과 robots.txt를 제공한다. 필터 조합의 무한 색인이나 운영 경로 공개를 피한다.
- sitemap.xml에는 실제 공개 가능한 정상 URL만 포함하며 데이터 변경과 함께 갱신한다.
- 외부 검색엔진 등록을 수행하면 결과와 시점을 기록하되, 색인·검색 순위·유입을 출시 성공으로 보장하지 않는다.

### FR-11 · 비교·탐색 사용성 보완 · Could

**요구:** 실제 이용 피드백에 따라 정보 밀도와 읽기 편의성을 개선한다.

**수용 기준**

- 새 제품 기능을 늘리지 않고 기존 화면의 필터 요약·날짜 설명·좁은 화면 표시를 보완한다.
- 수정 이유를 피드백 또는 관찰 결과에 연결한다. Could를 위해 Must나 운영 검증을 미루지 않는다.

## 7. 비기능 요구사항

모든 수치는 실제 측정 조건과 함께 기록한다. 성능·가용성·복구의 미정 목표는 기준선을 얻은 뒤 합의하며, 여기서는 측정 방법과 실행해야 할 검증을 완료 조건으로 둔다.

| ID · 분류 | 요구와 측정 가능한 수용 기준 | 검증 시점 |
|---|---|---|

코드와 테스트는 프로젝트의 Java 21+·Spring Boot 4.1.x·PostgreSQL 17·JPA·Flyway·Testcontainers·Compose·Caddy·GitHub Actions 방향을 따른다. 버전 세부값과 러너 사용 자격은 03에 기록된 조건을 벗어나 가정하지 않는다.

## 8. 완료 기준과 단계별 검수

### Sprint 1: 제품 기능과 첫 배포

- FR-01~09의 주요 이용 흐름이 동작한다. 미확인 필드·기관 식별·링크 검증 사항을 해결하거나 사용자 승인으로 범위를 조정한다.
- 최근 1년 최초 적재의 실제 범위·건수·완결 검증 결과를 기록하고 정기 수집을 실행한다.
- 홈·목록·상세·기관 화면의 정상·빈 결과·미수집·실패·없는 항목을 확인한다.
- HTTPS로 외부에서 접근 가능하고 기본 비밀값·관리 경로 보호를 확인한다.
- 첫 수집·웹 기준선을 기록하기 시작하고 Sprint 1 리뷰·미완료 항목을 남긴다.

### Sprint 2: 2주 MVP 완료

- 모든 Must 기능과 NFR의 정합성·보안·운영 검증을 통과한다. Should·Could 미완료는 별도 기록하며 Must 미완료를 운영 중 개선으로 넘기지 않는다.
- 신규 로직은 실제 응답에서 만든 비밀값 없는 fixture와 Testcontainers 기반의 필요한 검증으로 확인하고 CI가 통과한다.
- 재수집 중복, 의미 있는 목록 변경, 목록 누락·부분 실패, 상세 수집 분리, 호출 예산, 배포 중 실행 겹침의 수용 기준을 확인한다.
- ARM64 자동 배포, readiness·요청 마무리, 외부 연속 요청과 실패 롤백 검증의 결과가 있다.
- 성능 기준선과 쿼리 실행계획을 기록한다. 개선을 하지 않았으면 개선 비율을 만들지 않는다.
- 대시보드·운영자 알림·외부 생존 감시·수집 완료 신호가 실제로 동작한다.
- 백업 자동화와 OCI 외부 사본, 격리된 환경의 복원 성공 및 소요 시간·데이터 시점 기록이 있다.
- 장애 훈련과 회고가 있고 실제 사건·훈련을 구분한다.
- 이슈 완료 기준, 테스트·CI, 호환 마이그레이션, 변경 결정의 문서 반영, 비밀값 미포함이라는 프로젝트 DoD를 모두 충족한다.
