## 2. 각 초안에서 가져갈 것과 버릴 것

**codex**: 정확성 설계를 가장 잘 짚었다. 가져간다.
- 진행 중 목록에서 **빠졌다는 이유만으로 마감을 확정하지 않는다.** 마감은 마감일로 판정하고, 마감일 전에 사라진 공고는 "확인 필요"로 표시한다
- **"오늘 신규"는 공고 시작일 기준.** 1년치 최초 적재 때문에 과거 공고가 신규로 뜨는 걸 막는다
- **응답이 비었거나 불완전하면 기존 데이터를 그대로 둔다.** `totalCount`가 받은 건수보다 크면 불완전 수집으로 기록한다
- **blue/green 배포 중 앱이 겹칠 때 수집이 중복 실행되지 않게 한다** (DB 잠금)
- 화면의 필터 클릭이 외부 API 호출로 이어지지 않는다
- "신입 지원 가능"(R2010 + R2030)과 "신입만"(R2010)을 구분한다
- "모집 예정 인원"이라고 쓰고 "실제 채용 실적"이라고 쓰지 않는다
- 출력 보안: 원천 문자열을 이스케이프하고, 링크는 http(s)만 허용한다
- 기관 페이지를 **Must**로 둔다

버릴 것: 분량과 세부 절차가 2주 PRD로는 과하다. 호출 예산을 영속 저장하는 장치, 상세 작업 상태 머신, 11개의 열린 질문은 줄인다. 수용 기준 일부("의미 있는 값", "안전하게")는 그대로는 검증할 수 없다.

**agy**: 구조, ID 체계, 구체적인 수용 기준이 좋다. 가져간다.
- 수집 이력 필드 목록 (시작, 종료, 소요, 상태, 건수, 신규, 변경, 오류)
- 실패 처리 방식: 재시도 3회와 지수 백오프. 이건 **설정값**이니 근거를 ADR에 남긴다
- 공고 상세에서 기관 페이지로 가는 링크
- Actuator 민감 엔드포인트와 DB 포트를 외부에 노출하지 않는 구체적 기준
- 백업 보관 14일 (설정값. Object Storage 20GB 한도 안)
- 열린 질문으로 CSS 프레임워크 선택

버릴 것: 근거 없는 목표치 전부, 잘못된 문제 정의, 유휴 회수 대응 방법, 서버 관련 질문.

## 3. 2주 범위 판단
- **범위를 넘는 것**: codex의 호출 예산 영속 관리와 상세 작업 재개 상태 머신. 하루 54회 호출이면 한도 대비 여유가 크다. MVP는 **"호출 수 카운터 지표 + 한도의 50%에서 경고"**면 충분하다.
- **빠진 필수 항목**:
  - 세 초안 모두 **수집 스케줄러의 동시 실행 방지**가 있어야 한다 (codex에만 있음)
  - **필터 파라미터 검증** (허용 목록 밖의 값은 무시하거나 400을 돌려준다)
  - **출력 이스케이프**

## 5. 내 01 초안에서 고칠 점
- 문제 정의의 "기관 관점 정보가 없다" → **"기관 소개와 비교는 있지만 기관별 채용 이력과 통계는 없다"**로 고친다
- FR-04 "진행 중 목록에서 빠지면 마감" → 철회. codex 방식으로 바꾼다
- FR-13 기관 페이지를 Should에서 **Must**로 올린다. 사실 확인 결과 이게 유일하게 남은 차별점이다
- "오늘 신규"를 공고 시작일 기준으로 명시한다
- FR-14 `/status` 공개 페이지는 Could로 내린다. "마지막 수집 시각" 표시는 Must로 올린다 (codex FR-09와 같은 방향)

## 6. 최종 PRD 권고
- **문제 정의**: 잡알리오에 이미 있는 필터와 마감순 정렬은 차별점에서 뺀다. 남는 가치는 세 가지다.
  ① **기관별 채용 이력과 통계** (잡알리오에 없음, 확인함)
  ② **신입 지원 가능 공고 바로 보기** (R2010 + R2030을 합쳐서 보는 기능. 잡알리오는 체크박스를 여러 개 골라야 한다)
  ③ **데이터 품질 보정** (기관 첫 화면 링크 대체, 깨진 데이터 표시)
- **Must**: 수집 4종 (최초 적재, 정기 수집, 변경 감지, 실패·불완전 처리) · 화면 4종 (홈, 목록, 상세, 기관) · 마지막 수집 시각 표시 · 동시 실행 방지 · 입력 검증과 출력 이스케이프
- **Should**: 신규 공고 상세 조회 · SEO (sitemap, 메타 태그) · 모바일 레이아웃
- **Could**: `/status` 공개 페이지 · 변경 이력 배지
- **비기능 요구사항**: 목표값은 **두 가지만 확정**한다. 배포 중 관측 요청 실패 0, 외부 API 호출이 한도의 10% 미만. 성능, 가용성, RTO는 기준선을 잰 뒤 정한다. 백업 주기(일 1회)와 보관(14일), 재시도(3회)는 설정값으로 ADR에 남긴다.
- **완료 기준**: 01-claude의 6개 항목에 codex의 Sprint 1과 2 검수 항목을 합친다.

3. 서비스 이름과 도메인 (DuckDNS 또는 유료)

5. 방문 측정 방식 (서버 로그 집계 또는 외부 경량 분석)
