# #17 표지 게이트 보완: 첫 초기화와 표지 고유성 · claude

2026-11-19 · 종합 전 한정 보완 · 요청: root codex, [`2026-11-19-resume/claude-barrier-refinement-request.md`](../2026-11-19-resume/claude-barrier-refinement-request.md) · 대상: 내 [`03-claude-counterexamples.md`](03-claude-counterexamples.md) §4

- **범위:** §4 내용 게이트의 두 경계만 다룬다. 백업 보유는 사용자 결정 [`04`](04-user-retention-decision.md)를 전제로 하고 다시 다루지 않는다.
- **하지 않은 것:** 온라인 정리, 새 영속 시스템·의존성, 정리 주기·다운타임 정책 확정, source·시험·설정·서버 변경.
- **source 대조(main `48f6878`):** 구독 ID는 두 생성 경로 모두 Java `UUID.randomUUID()`다(`SubscriptionService.java:188`, `:411`). V5 `id uuid PRIMARY KEY`에는 DB 기본값이 없다.
- **외부 사실:** [RFC 9562 §5.8](https://www.rfc-editor.org/rfc/rfc9562.html)
  - UUIDv8은 version `0b1000`(octet 6의 bits 48–51), variant `0b10`이다. 나머지 122비트(`custom_a` 48 + `custom_b` 12 + `custom_c` 62)는 구현이 채운다.
  - "UUIDv8's uniqueness will be implementation specific and MUST NOT be assumed."
  - [Java `UUID.randomUUID()`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/UUID.html): "type 4 (pseudo randomly generated) UUID".
- **직접 실행:** 기존 `readStrict` 판정(36자, `fromString` 뒤 `toString` 정규형 일치, `Instant.parse`)을 그대로 옮긴 작은 Java 검사를 로컬 JDK 17로 돌렸다.
  - v8 표지 줄 `67636862-6172-8a1b-9c3d-4e5f60718293\t2026-11-19T10:00:00Z`는 **받는다**(version 8, variant 2).
  - `randomUUID()` 10만 개는 모두 version 4였다.
  - 앱이 쓰는 JDK 21에서는 다시 돌리지 않았다.

## 0. 결론

1. **"`head -n1 L` = 가장 오래 남은 표지"는 처음으로 줄을 지운 뒤에만 성립한다.** 처음 지우는 때는 둘째 barrier다. 예외로 표지로 시작하게 만든 대장(새 설치, 빈 대장)은 처음부터 성립한다. 그 전에는 줄을 지운 적이 없으므로 게이트를 **바이트 prefix 규칙**으로 바꾼다. 상태를 셋으로 나눠 판정한다(§1).
2. **nil UUID + 시각 표지는 철회한다.** ID가 모두 같아 고유성을 시각에 기대게 된다. 시계가 되풀이되면 옛 줄과 같아질 수 있다.
   - 대신 **고정 태그를 둔 UUIDv8 + 74비트 난수**를 쓴다.
   - 앱 ID는 v4라 버전 비트로 결정적으로 구별된다. 기존 판독기와 재적용은 이 줄을 받고 0행을 지운다.
   - 표지끼리의 고유성은 난수에 기댄다. 확률적이지만 시계와 무관하다(§3).
3. 게이트는 여전히 **시각 비교를 하지 않는다.** 남는 가정은 셋이다: barrier 때 앱과 백업이 정말 멈췄는가, 표지 난수가 겹치지 않는가, 재적용 전에 게이트를 실제로 돌리는가(§4).

## 1. 대장 상태와 게이트

| 상태 | `L`의 모양 | 줄을 지운 적 | 게이트(덤프와 같은 snapshot의 `B` 기준) |
|---|---|---|---|
| **S0 기존** | 표지 없음. 파일 없음(M1), 빈 파일, 해지 줄만 있음 | 없음 | `B`가 `L`의 **바이트 prefix**다. 파일이 없거나 비어 있는 `B`는 빈 문자열로 본다 |
| **S1 표지 있음, 지운 적 없음** | 표지가 하나 이상 있지만 **첫 줄은 해지 줄** | 없음 | S0과 같은 prefix 규칙 |
| **S2 정리됨** | **첫 줄이 표지 `H`** | 있을 수 있음 | `B`에 `H`와 같은 줄이 정확히 한 번 있다. **그리고** `B`에서 그 줄부터 끝까지가 `L`의 바이트 prefix다 |

**왜 첫 줄로 상태를 가르는가:** 줄을 지우는 정리는 항상 표지 바로 앞에서 자르고, 그 표지를 첫 줄로 남긴다. 그래서 **첫 줄이 표지가 아니면 지운 적이 없다**(S0·S1). 지운 적이 없으면 `L`이 모든 줄을 갖고 있으므로, `B`가 prefix인지만 보면 된다. 예외는 빈 대장이나 새 설치를 표지 한 줄로 시작한 경우다. 이때는 아무것도 지우지 않았어도 S2로 분류된다. 이 경우 처음 표지 이전 덤프를 거부하는 쪽으로 틀린다. 이것은 안전하고, 대가는 복원점 손실뿐이다.

**fail closed:**
- `L`이나 `B`가 strict 검사에 실패하면 거부한다.
- 같은 표지 ID가 한 파일에 두 번 나오면 거부한다.
- **`B`에 표지가 있는데 `L`에는 표지가 하나도 없으면 거부한다.** 표시된 대장이 빈 파일이나 옛 파일로 바뀐 경우다.
- **S2에서 `L`의 첫 줄이 아닌 다른 표지 뒤가 잘린 것**은 prefix 검사가 잡는다.

**예외(게이트와 무관하게 안전):** 복원한 덤프의 `subscription` 행이 0개면 되살아날 구독이 없다. 재적용과 게이트 결과와 상관없이 안전하다. M1 백업(대장 없음)이 S2 시기에 거부되는 문제를 이 규칙이 풀어 준다.

## 2. 전환과 실제 순서

**불변식 (INV):** 표지 `M_j`보다 파일에서 앞에 있는 모든 줄은 barrier `j` 전에 쓰였고, 그 해지 트랜잭션은 barrier `j`까지 끝났다.
- 표지는 barrier 동안에만, 파일 끝에만 붙인다. 예외는 앞에 아무 줄도 없는 표지(새 설치 생성, 빈 대장)다.
- 정리는 줄 순서를 바꾸지 않는다.
- 그래서 INV는 시각과 무관하게 유지된다.

| 전환 | 언제·무엇을 | 정지 필요 | 그 직후 받는 덤프 |
|---|---|---|---|
| (새 설치) 파일 생성 = `[M_1]` | 알림을 켜기 전, 운영자가 빈 파일 대신 표지 한 줄로 대장을 만든다 | **불필요**(쓰는 프로세스가 없고, `M_1` 앞에 줄이 없다) | `B`에 `M_1`이 있는 덤프. 그 전 덤프는 M1이라 구독 0행 → 예외 규칙으로 안전 |
| S0 → S1 (해지 줄이 있는 기존 대장) | barrier 1: 끝에 `M_1`을 붙인다 | 필요(INV, 붙이는 동안 다른 writer 없음) | 모든 덤프(prefix 규칙, 아무것도 지우지 않았다) |
| S0(빈 파일) → S2 | barrier 1: `[M_1]` | 필요 | `B`에 `M_1`이 있는 것만. 그 전 덤프는 구독 0행이 아니면 거부(안전하지만 복원점 손실) |
| S1 → S2 | barrier 2: `M_1` 앞의 줄을 지우고, 끝에 `M_2`를 붙인다 | 필요 | `B`에 `M_1`이 있는 것(barrier 1 이후). barrier 1 이전 덤프는 이제 거부 |
| S2 → S2 | barrier k: `M_{k-1}` 앞을 지우고 `M_k`를 붙인다 | 필요 | barrier k−1 이후 덤프 |

**barrier 실행 순서 (제안, 운영 도구로):**
1. 백업 타이머를 멈춘다. 실행 중인 백업이 끝났는지 확인한다(`backup.lock`, 서비스 상태). 백업 한 번이 barrier를 걸치면 "`B`에 새 표지가 있지만 덤프는 barrier 전"이 되어 INV가 깨진다.
2. 두 색 앱을 멈춘다. DB(`postgres` 컨테이너는 유지)의 `pg_stat_activity`에 앱 사용자 세션이 0인지 확인한다.
3. `L`을 strict하게 검사하고 상태를 판정한다. 표지 ID 중복도 검사한다.
4. 같은 디렉터리의 임시 파일(`1000:1000 0600`)에 새 내용을 쓴다. 새 내용은 지울 앞부분을 뺀 나머지 + `M_k` 한 줄이다. 그 뒤 fsync, rename, 디렉터리 fsync를 한다. S0 → S1처럼 끝에 붙이기만 하는 경우도 같은 경로로 하면 도구가 하나로 단순해진다.
5. 다시 strict 검사를 하고 확인한다: 남긴 부분이 원본 해당 부분과 바이트로 같은지, 마지막 줄이 `M_k`인지.
6. **(빈 대장 → S2와 새 설치 다음에는 권장, 그 밖에는 선택)** 앱을 멈춘 채로 `backup.sh run`을 한 번 돌린다. 이 백업은 barrier 뒤의 덤프이고 `B`에 `M_{k-1}`과 `M_k`가 모두 있어, 다음 두 주기 동안 받아들여진다. S1 → S2나 S2 → S2에서는 직전 주기의 일일 백업이 이미 받아들여지므로 필수가 아니다. 대가는 다운타임이 덤프와 업로드 시간만큼 늘어나는 것이다.
7. 백업 타이머와 앱을 다시 켠다.

**사용자 14일 정책과의 관계:** 게이트의 안전은 백업이 몇 개 남았는지와 무관하다. 다만 정리 주기 C가 14일보다 짧으면 restic에는 남아 있어도 게이트가 거부하는 덤프가 생긴다. 사용자 정책상 남은 사본이 0개일 수 있으므로, 도구는 "받아들일 덤프가 있다"를 전제로 하지 않는다. C는 정하지 않는다.

## 3. 표지 고유성과 예약 namespace

- **nil UUID + 시각의 문제(철회):** 모든 표지의 ID가 같아 줄을 구별하는 것은 시각뿐이다. 시계가 되돌아가 같은 초를 다시 쓰면 새 표지가 옛 표지와 같은 줄이 된다. 그러면 옛 epoch의 `B`가 "새 표지를 포함한다"고 판정된다. root 지적이 맞다.
- **제안 형식(기존 줄 문법 유지):** `<표지 UUID>\t<ISO 시각>`.
  - 표지 UUID는 UUIDv8이다. `custom_a` 48비트는 고정 태그(예: `67636862-6172`)이고, version은 8, variant는 `10`이다. `custom_b` 12비트와 `custom_c` 62비트, 합계 **74비트는 `/dev/urandom`의 난수**다.
  - 정규형(소문자, 36자)으로 쓴다.
  - 셸에서 `od`·`printf`로 만들 수 있어 새 의존성이 없다.
- **판별:** 새 판독기는 "version 8이고 태그 일치"면 표지, 그 밖은 해지 줄로 본다. 판별 정규식 예: `^67636862-6172-8[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}\t`.
  - 앱의 구독 ID는 `UUID.randomUUID()` v4라 버전 비트가 다르다. 그래서 **실제 해지 줄이 표지로 오인되거나, 표지가 실제 구독을 지우는 일은 앱이 만든 ID에 대해 결정적으로 없다.**
  - 수동 SQL로 v8 ID를 넣은 구독은 모델 밖이다. 막으려면 DB CHECK가 필요하지만 이번에는 제안하지 않는다.
- **시각 필드:** 정보용이다. 게이트는 쓰지 않는다. 기존 판독기가 `Instant.parse`를 요구하기 때문에 둔다. 시계가 되풀이되어 같은 시각이 들어가도 ID가 다르므로 줄이 다르다.
- **표지끼리의 고유성:** RFC는 v8의 고유성을 보장하지 않는다(구현 책임). 여기서는 74비트 CSPRNG 난수가 그 근거다. 표지 n개가 우연히 겹칠 확률은 대략 n²/2⁷⁵이다(n=100이면 약 3×10⁻¹⁹). **확률적 근거이지 증명이 아니다.** 도구는 새 표지를 쓰기 전에 `L` 안의 중복을 검사해서 확인할 수 있는 범위는 막는다.
- **복사와 손상:** 표지는 barrier 동안 앱과 백업이 멈춘 상태에서만 쓰인다. rename은 원자적이므로 백업의 `cp`는 옛 파일이나 새 파일 전체를 본다. 줄이 손상되면 strict 실패나 ID 불일치로 거부된다(fail closed). 손상이 우연히 다른 유효 표지 줄이 되는 경우도 불일치로 거부된다.
- **구버전 재적용:** 기존 JAR는 표지 줄을 UUID로 읽고 `DELETE … IN (표지)`를 실행한다. 결과는 0행이다(v4 ID만 있으므로). **그러나 기존 JAR는 게이트를 검사하지 않는다.** 그래서 "기존 JAR 정상 종료"는 게이트 통과가 아니다. 게이트는 재적용 **전**에 운영 도구로 돌리는 runbook 필수 단계여야 한다. 지금도 게이트 없이 재적용하는 경로가 있으므로, 이 제안이 상황을 더 나쁘게 하지는 않는다. Java 판독기가 표지와 게이트를 직접 처리하면 이 우회로가 닫힌다. 그 경우 같은 판정을 앱 안에서 하게 된다.
- **혼합 버전 writer:** 표지와 정리는 앱이 모두 멈췄을 때만 실행한다. 옛 앱과 새 앱이 함께 쓰는 문제가 생기지 않는다.

## 4. "시계 가정 없이"의 정확한 범위

**시계 없이 성립하는 것:**
- 덤프 수락 판정(줄 일치와 바이트 prefix).
- 지운 줄의 삭제가 받아들인 덤프에 반영돼 있다는 점(INV + 백업이 barrier를 걸치지 않음).
- 표지 ID의 구별(난수).

**남는 가정:**
1. barrier 때 앱 세션 0과 실행 중인 백업 없음을 **실제로 확인했다.** 확인하지 않은 운영자 수동 세션은 막지 못한다.
2. 74비트 난수가 겹치지 않는다(확률).
3. 재적용 전에 게이트를 돌린다(절차 강제).
4. S0·S1의 prefix 규칙은 **마지막 백업 뒤에 붙은 정상 형식 줄이 통째로 사라진 것**을 잡지 못한다(root #2의 남은 부분). 두 대장이 모두 비어 있으면 구별하지 못하는 한계는 표지가 생기기 전 구간에만 남는다.

**다시 들이지 않은 것:** 시각 여유 `m`, 별도 메타파일(두 파일 원자성), 온라인 정리.

## 5. 최소 변경과 trade-off

| 변경 | 형태 | 필수 여부 |
|---|---|---|
| 표지 줄 정의(v8 태그 + 난수) | 기존 줄 문법 그대로, 문서로 정의 | 필수 |
| 운영 도구: 표지 생성, barrier 정리, 게이트 판정 | 셸 스크립트와 runbook. strict 판정 규칙을 그대로 옮긴다 | 필수 |
| 새 설치 대장 생성을 "빈 파일" 대신 `[M_1]`로 | runbook 한 줄, ADR-0013·`alerts.md`의 "빈 파일" 문구 갱신 | 권장. 지금 서버는 M1이고 대장 파일을 아직 만들지 않았다 |
| Java 판독기가 표지를 인식(재적용에서 제외, 게이트 내장) | source | 선택. 구버전 우회로를 닫는다 |

**trade-off:**
- barrier마다 웹을 포함한 다운타임이 생긴다. 6단계 백업까지 하면 덤프와 업로드 시간만큼 더 길다.
- barrier k−1보다 오래된 덤프는 restic에 남아 있어도 재개용으로 쓸 수 없다.
- 빈 대장을 처음 표시하는 순간에는 그 전 덤프가 거부된다(구독 0행이면 예외).
- 표지 고유성은 확률적이다.
- 주기 C와 다운타임 허용은 정하지 않는다.

## 6. 확인 범위

- **직접 한 것:**
  - main `48f6878`의 구독 ID 생성 경로와 V5 정의 대조.
  - RFC 9562, Java UUID 공식 문서 확인.
  - 로컬 JDK 17에서 기존 strict 규칙으로 v8 표지 줄이 받아들여지는지, `randomUUID()`의 버전 확인.
