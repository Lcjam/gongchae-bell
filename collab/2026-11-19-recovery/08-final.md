# 복원 대장 정책 종합과 구현 순서 · Codex

2026-11-20. 01 독립안→02 교차 비판→03 반례→사용자04→Claude05→agy06→Sol07을 읽고 실제 main eb903017의 journal/CLI/worker/Compose와 대조했다. 사용자 보유기간 선택04는 확정이며 다시 묻지 않는다. 이 문서는 합의된 복원 검사부터 구현하기 위한 조율 결과다. 운영 M2·백업 전체 완료나 아직 미정인 정비 일정을 확정한 문서가 아니다.

## 합의한 검사

- 시각 상한 m이나 '덤프가 충분히 늦다'는 추정으로 해지의 DB commit 완료를 보장하지 않는다. 원래 줄 문법과 원문 바이트 순서를 사용한다.
- 표지는 기존 `<uuid>\t<Instant>\n` 문법 안에서 UUIDv8·RFC variant2·상위48비트 `67636862-6172`를 예약한다. 예시 모양은 `67636862-6172-8xxx-[89ab]xxx-xxxxxxxxxxxx`다. 실제 구독 UUIDv4와 구별하고 무작위74비트로 식별한다. marker는 삭제할 구독 ID가 아니다. timestamp를 유일성/커버리지 근거로 쓰지 않는다.
- Java의 공통 strict 파서로 B(덤프 동봉 대장)와 L(적용할 최신 대장)을 모두 검증한다. 날짜/가변 소수초는 기존 Instant 파서를 재사용하며 잘린 행·비정규 UUID·중복 표지는 거부한다. B는 불변 파일을 읽기 전용으로 읽고 L은 기존 OS 잠금 아래 일관된 바이트를 읽는다. shell 정규식으로 두 번째 파서를 만들지 않는다.
- S0(L에 표지 없음), S1(L에 표지가 있으나 첫 행이 일반 해지): **B 전체가 L의 byte prefix**여야 한다. S2(L 첫 행이 표지 H): H가 B에 정확히 한 번 있고 **B의 H부터 끝까지가 L의 prefix**여야 한다. 순서 역전·B가 L보다 긴 경우·표지 누락/중복/파손은 실패다. 표지 구간 이전의 옛 덤프를 새 대장에 무조건 적용하지 않는다.
- `ErasureReapplyCommand` 자체가 B를 필수 입력으로 받고 DELETE 전에 이 검사를 강제한다. 별도 shell 검사나 오래된 COMPLETE 로그만을 신뢰하는 우회로를 남기지 않는다. 검사 성공 로그와 재적용 완료 로그를 구별하고 실패 메시지에 UUID/대장 내용은 노출하지 않는다.
- **SUB=0은 M2 검사를 면제하지 않는다.** 유일한 자동 M1 생략은 SUB0 + meta.erasure_included=false + M2 미개시 근거/호스트 대장 부재라는 기존3조건이며, 실제 운영 runbook의 분기다. 이 CLI에 SUB0 우회 옵션은 추가하지 않는다.

S0/S1은 기존 표지 없는 자료의 prefix 검사이지 완전한 tail 손실 탐지 보장이 아니다. 새 M2는 활성화 전에 초기 표지[M1]을 생성·검증하는 운영 게이트를 반드시 거친다. B의 초기 표지와 L의 빈 재생성/표지 유실은 실패해야 한다. 정상 과거 대장으로 통째 되돌린 손실, 마지막 백업 뒤 VM 영구 소실 구간은 현 설계로 항상 탐지/복원할 수 없으며 그 한계를 유지한다.

## 정지·권한·정리의 확정 조건

정비 도구는 기존 deploy.lock과 backup.lock을 앱 정지 전부터 잡는다. 양색 앱과 수동 writer의 정지, 검사 세션을 뺀 DB client0·prepared xact0을 확인하고 교체/검증 동안 배타성을 유지한다. lock에 참여하지 않는 직접 docker/JVM/수동 writer를 정비 중 시작하지 않는 운영 전제를 명시한다. 태그는 deploy/state에서 읽어 기존 Compose 보간·프로젝트 규약을 따른다. 명령 실패를 빈 stdout으로 취급하지 않는다. profile명시 여부와 서비스명 명시 stop의 실제 의미는 Sol07 정정을 따른다.

앱1000이 쓸 수 있고 ubuntu 백업 주체는 읽기만 가능한 그룹 권한을 검증한다. ubuntu 감독 프로세스의 lock 유지와 sudo helper의 대장 교체 권한을 분리하며, root가 ubuntu lock 파일 소유권을 바꾸거나 sudo가 fd를 보존한다고 가정하지 않는다. fsync→원자 rename→dir fsync·mode/owner 보존, 교체 실패 뒤 자동 정상 재개 금지, 검사 뒤 기동 경쟁 차단이 필요하다.

tail이 marker라는 이유만으로 다음 주기를 거부하지 않는다. `[M1,u1,M2]`에서 새 해지가 없어도 다음 정상 주기는 u1을 정리할 수 있어야 한다. 삭제할 일반 해지 줄이 없는 구간의 불필요한 절단은 하지 않는다. 같은 작업의 즉시 재시도와 정상 다음 주기를 구별하는 도구 계약, 정비 주기와 downtime은 도구의 구체안 검토에서 확정한다. 이번 검사 PR에 추정으로 스케줄러/compaction을 추가하지 않는다.

## 백업·발송 복구

- PR30의 실행시각 기준14일·0개 허용 정책을 OCI와 관리 PC에 적용한다. PC는 네트워크 copy 전에 로컬 만료/prune/확인, copy 뒤 재정리/확인을 한다. 실패/오프라인 동안 실제 삭제 지연을 완료로 기록하지 않는다.
- 복원 DB의 미완료 작업은 full 앱 기동 전에 UNCERTAIN으로 마감하고 item을 보존하는 방향을 유지한다. `ALERTS_ENABLED=false`는 HTTP 해지도503으로 막으며 maintenance 전체나 DB를 동결하는 스위치가 아니다. 파일 env 수정만으로 기존 JVM이 바뀌지도 않는다.
- 덤프 밖의 발송/item은 재구성할 수 없다. 같은 날 DIGEST 슬롯만 막아 익일 NEW 중복이 사라진다고 주장하지 않는다. 중복/추가 누락 중 운영 선택을 구체적으로 검토하고 일괄 backfill/item 선채우기를 자동 적용하지 않는다.

## 구현 분리와 완료 증거

1. **지금 배정:** 공통 strict 파서·marker 구별·S0/S1/S2 coverage·B 필수 CLI와 실제 DELETE 이전 실패 회귀. 별도 PR로 두 비작성자 검수/CI를 받는다. CLI 예제는 새 입력과 읽기 전용 B mount로 업데이트한다. 현재 운영에는 적용하지 않는다.
2. **이어서:** 정지/초기표지/권한/barrier·재시도 도구와 그 경쟁/실패 검증, PC pull/정리 스케줄, 실제 OCI 저장소/키 분리·계정 한도, 격리 복원 리허설. 이 단계가 끝나기 전 M2를 활성화하지 않는다.
3. **최종:** privacy·ADR·runbook 고지, 실측 RTO/RPO·잔류/소실 구간·발송 중복 한계, 실제 역할별 권한/복원 증거를 저장소에 남긴다. 공개 출시 전체 DoD를 따로 감사한다.

이 분리는 기존 #17 목표를 줄이는 결정이 아니다. 독립적으로 확정된 검사 코드를 먼저 검증하고 남은 실제 운영·정리·복구 조건을 계속 이행하는 순서다.
