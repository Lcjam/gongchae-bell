# 백업 보유기간 사용자 결정

2026-11-19 사용자가 비동기 질문에 다음 선택지를 명시적으로 선택했다.

> 보유기간 우선: 다음 실행 때 14일 초과분을 전부 삭제하며 복원 사본 0개도 허용

질문에는 PC가 꺼져 있는 동안 자동 삭제가 실행되지 않는다는 한계를 함께 설명했다. 이 응답으로 장기 실패 때 최후 사본을 남길지의 쟁점은 해소됐다. 기존 restic의 성공한 날짜 14개/최신 snapshot 기준14일 정책을 사용자가 정한 wall-clock14일 정책으로 대체해야 한다.

## 구현과 고지에 반영할 조건

- 정리 실행의 현재 UTC 시각을 기준으로 snapshot 시각이 14일을 **초과한** 대상 사본을 모두 삭제한다. 최신1개·가장오래된1개·마지막성공일 예외를 두지 않는다. 조건에 맞으면 남은 snapshot0개도 정상 결과다.
- 이 정책은 OCI와 OCI 밖 관리 사본(첫 대상PC)에 모두 적용한다. restic 기본 keep-daily·keep-within의 의미만으로 구현됐다고 세지 않는다. 명시적 snapshot ID 선정/삭제와 실제 prune 결과를 검증한다.
- PC 복귀 시에는 다음 실행에서 오래된 사본을 정리한다. 오래된 OCI 사본을 copy한 뒤 그대로 다시 보관하는 결과도 피한다. 실패한 백업/네트워크 상태에서도 로컬 정리를 실행할 수 있는 순서와 실패 관측이 필요하다.
- PC 오프라인·자격/백엔드 오류·prune 실패 중에는 물리 삭제가 지연될 수 있다. 그 상태를 삭제 완료로 기록하지 않고 경보·재실행/복구 절차와 고지에 반영한다. snapshot 목록에서 빠진 것과 팩 물리 정리는 구분한다.
- 실제 선택 기준·오류/빈저장소·경계직전/정각/초과·다른태그/저장소보존을 테스트한다. 원천 API나 실제 provider 발송은 정리 검증에 쓰지 않는다.

이 응답은 백업의 잔류 우선순위 결정이다. 별도의 해지 대장 정리 주기·운영 downtime·새 유료 자원·사용자 메일 수신 동의를 포함하지 않는다. 해당 부분은 기존 범위에서 검수·설계와 실제 운영 근거를 이어간다.
