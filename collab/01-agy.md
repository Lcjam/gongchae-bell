# 1라운드 · agy(Antigravity) 독립 제안

Oracle Cloud Always Free(이하 OCI 프리티어) 환경을 백엔드 운영 실습장이자 포트폴리오의 실서비스 인프라로 활용하는 전략은 **신입 포트폴리오 중 상위 5% 이내의 설득력**을 갖습니다. 

OCI 최신 제약 사항(Ampere A1 ARM64 4 OCPU / 24GB RAM, 스토리지 200GB, **7일 유휴 시 인스턴스 회수 정책**, 방화벽 이중 구조 등)을 실전 운영 시나리오에 완벽히 녹여낸 3가지 프로젝트 주제를 제안합니다.

---

### [공통 전제] OCI Always Free 실전 운영 체크리스트 (설계 반영 사항)
1. **아키텍처 스펙**: Ampere A1(ARM64) 1대에 4 OCPU, 24GB RAM, 100GB Boot Volume을 몰아주어 단일 고스펙 노드로 구성 (Docker Compose 또는 k3s 운영에 최적).
2. **ARM64 빌드**: GitHub Actions CI 파이프라인에서 `docker buildx`를 통해 `linux/arm64` 멀티 아키텍처 빌드 필수.
3. **유휴 인스턴스 회수(Idle Reclamation) 방어**: 7일 연속 CPU·네트워크·메모리(Ampere) 사용률이 20% 미만이면 OCI가 VM을 회수합니다. 따라서 **주기적인 백그라운드 배치, 모니터링 데몬(Prometheus 등), 실제 외부 트래픽**이 필연적으로 발생하는 구조여야 합니다. (가장 안전한 방법은 카드 등록 후 'Pay As You Go'로 업그레이드하는 것이며, 무료 한도 내 사용 시 요금은 0원 청구되면서 회수 대상에서 영구 제외됩니다.)
4. **네트워크/방화벽**: OCI Console의 VCN Security List(Ingress 80/443)뿐 아니라 Ubuntu/Oracle Linux 인스턴스 내부의 `iptables`/`firewalld`도 함께 열어주는 자동화 스크립트 작성 필수.

### 주제 1: IT 컨퍼런스·해커톤 통합 캘린더 구독(iCal) 및 티켓 오픈 알림 서비스 (DevEvent iCal)

#### ① 한 줄 요약
흩어져 있는 IT 행사·웨비나·해커톤 일정을 자동 수집·정제하여, Google/Apple 캘린더에 실시간 자동 동기화(iCal/RFC 5545)하고 인기 행사의 티켓팅 오픈 웹훅 알림을 전송하는 서비스.

#### ② 실제 사용자 및 트래픽 유입 근거 (매우 강력)
- **자연 발생 봇 트래픽**: 사용자가 서비스에서 제공한 `webcal://.../events.ics` URL을 Google Calendar나 Apple Calendar에 등록하면, **Google/Apple의 글로벌 크롤러 서버가 2~6시간 주기로 365일 24시간 내 서버로 GET 요청을 보냅니다.** (사용자 50명만 모여도 매일 수백~수천 건의 지속적 인바운드 트래픽 발생).
- **실제 유저 니즈**: 개발자 단톡방, 디스코드, 벨로그 등에 링크를 공유하면 "캘린더 연동 한 번으로 일정 자동 갱신" 기능은 즉각적인 바이럴을 탑니다.

#### ③ Spring 기술 포인트
- **RFC 5545 (iCalendar) MIME 스트리밍**: 대용량 ics 파일 생성 시 WAS 힙 메모리 점유를 막기 위한 `StreamingResponseBody` 또는 청크 기반 응답.
- **HTTP 조건부 요청(ETag / Last-Modified)**: 수많은 캘린더 봇이 찔러댈 때 데이터 변경이 없으면 DB 조회를 최소화하고 `304 Not Modified`를 즉시 반환하는 캐싱 아키텍처.
- **Spring Batch + Resilience4j**: 외부 사이트 크롤링 시 장애 격리(Circuit Breaker, Exponential Backoff Retry) 및 정기 수집 파이프라인.
- **Redis Pub/Sub & WebClient**: 행사 티켓 오픈 시점 디스코드/슬랙 웹훅 대량 발송(비동기 I/O).

#### ④ 배포/운영 시나리오 & 이력서 문장 예시
- **시나리오**: Google Calendar 봇 수십 대가 동시 인입될 때 DB 커넥션 풀 고갈 발생 ➡️ ETag 기반의 HTTP 캐싱 레이어와 Redis 인메모리 버퍼를 적용하여 DB I/O 부하 제거.
- **이력서 문장 1**: *"Google/Apple Calendar 수집 봇의 주기적 폴링(일평균 8,000건)에 대응하여 ETag 기반의 조건부 GET 처리 및 Redis 캐싱을 구축, 전체 트래픽의 88%를 304 응답으로 처리하며 DB 부하를 80% 이상 절감."*
- **이력서 문장 2**: *"GitHub Actions와 Docker Compose를 연계한 Blue/Green 무중단 배포 환경을 OCI Ampere A1에 구축하여, 배포 중 발생하던 캘린더 동기화 끊김 현상(다운타임 0초) 해결."*
- **이력서 문장 3**: *"Prometheus & Grafana 메트릭 수집 및 Alertmanager를 연동하여 JVM Old Gen 메모리 사용량 80% 초과 시 디스코드 알림 발송 및 Heap Dump 자동 수집 체계 구축."*

#### ⑤ Oracle 프리티어에서의 리스크
- **크롤링 IP 차단 리스크**: OCI 공인 IP 대역이 외부 행사 사이트에서 봇으로 인식되어 차단당할 위험 ➡️ Selenium 같은 무거운 도구 대신 순수 HTML 파서(Jsoup) + 적절한 Request Interval(지터 포함) 적용 필수.
- **ARM64 바이너리 호환**: 크롤러 빌드 시 x86 전용 라이브러리가 포함되지 않도록 순수 Java 기반 의존성 유지.

#### ⑥ 신입 포트폴리오로서 흔한 정도와 차별성
- **흔한 정도**: 5% 미만 (극히 드묾). 대부분의 신입이 흔한 쇼핑몰/SNS를 만듭니다.
- **차별성**: RFC 웹 표준 프로토콜 구현, HTTP 캐싱 메커니즘에 대한 깊은 이해, 외부 수집 봇의 트래픽을 핸들링해 본 경험은 면접관에게 기술적으로 압도적인 인상을 줍니다.

### 주제 2: 취준생 포트폴리오 전용 업타임 헬스체커 및 SSL 만료 알림 SaaS (UptimeGuard)

#### ① 한 줄 요약
취준생 및 주니어 개발자들의 포트폴리오 웹사이트와 API 서버를 1~5분 주기로 헬스체크(Ping, HTTP 응답, SSL 인증서 잔여일)하고 장애 시 디스코드/카카오톡으로 즉각 전송해 주는 경량 모니터링 SaaS.

#### ② 실제 사용자 및 트래픽 유입 근거
- **명확한 타겟 불안감 해소**: "면접관이 내 포트폴리오를 볼 때 서버가 죽어있으면 어쩌지?"라는 취준생들의 실질적 공포를 해결해 줌.
- **동료 기반 트래픽**: 부트캠프 동기, 스터디원 20~30명만 유치해도 모니터링 대상 엔드포인트가 100개 이상 등록됨. 1분마다 100회 이상의 외부 I/O가 24시간 끊임없이 발생하여 **자체적인 시계열 데이터와 부하가 계속 생성됨**.

#### ③ Spring 기술 포인트
- **Spring 6 / Java 21 가상 스레드(Virtual Threads) 또는 WebClient**: 등록된 수백 개 엔드포인트를 1분마다 병렬 체크할 때 스레드 풀 고갈을 방지하는 Non-blocking/ 경량 스레드 I/O 아키텍처.
- **대량 시계열 데이터 파티셔닝**: 1분마다 쌓이는 수만 건의 응답시간/상태코드 로그를 관리하기 위한 MySQL 파티셔닝 및 7일 경과 데이터 롤링 롤오버(배치 삭제/아카이빙).
- **SSL 핸드셰이크 커스텀 소켓**: Java `SSLSocketFactory`를 활용한 만료일자 추출 및 만료 D-7일 사전 알림 로직.

#### ④ 배포/운영 시나리오 & 이력서 문장 예시
- **시나리오**: 외부 모니터링 대상 서버의 무응답(Hung) 상태로 인해 톰캣 워커 스레드가 고갈되어 전체 체크 작업이 중단되는 장애 ➡️ 타임아웃 격리(Bulkhead) 패턴 및 Java 21 Virtual Thread 적용으로 격리.
- **이력서 문장 1**: *"150여 개 외부 서버 대상의 1분 주기 헬스체크 배치에서 Java 21 Virtual Thread를 도입, 블로킹 I/O 대기 시간을 해소하여 스케줄러 처리량을 4배 개선하고 메모리 점유율을 60% 절감."*
- **이력서 문장 2**: *"일일 20만 건씩 누적되는 헬스체크 시계열 로그로 인한 쿼리 성능 저하를 방지하기 위해 RDB 월별 파티셔닝 및 스프링 배치를 통한 14일 롤링 아카이빙 구현."*
- **이력서 문장 3**: *"OCI 블록 스토리지 자동 스냅샷 백업 쉘 스크립트를 작성하고 Crontab으로 등록, 실서버 DB 드롭 상황을 가정한 복구 리허설(RTO 15분, RPO 24시간) 수행 및 장애 복구 가이드 문서화."*

#### ⑤ Oracle 프리티어에서의 리스크
- **아웃바운드 패킷 스팸 오인**: 초당 수십 건의 HTTP GET 핑을 무차별 발송하면 OCI 네트워크 단에서 이상 징후로 감지될 수 있음 ➡️ `HEAD` 메서드 우선 활용, 타임아웃 3초 제한, Jitter(무작위 분산 지연)를 통한 트래픽 스무딩 필수.
- **유휴 회수 자동 방어**: 이 서비스는 24시간 지속적으로 네트워크 아웃바운드와 CPU 배치를 돌리므로 OCI의 '7일 유휴 인스턴스 회수 정책'을 완벽하게 자연 우회할 수 있습니다.

#### ⑥ 신입 포트폴리오로서 흔한 정도와 차별성
- **흔한 정도**: 3% 미만 (신입 포트폴리오에서 보기 힘든 인프라 중심 SaaS).
- **차별성**: "백엔드 개발자가 인프라와 네트워크를 어떻게 이해하고 모니터링하는가"를 직접 보여줌. SRE, DevOps 및 플랫폼 백엔드 팀 지원 시 치트키 수준의 어필 가능.

### 주제 3: 개발자 취준 스터디용 CS 면접 답변 음성·텍스트 상호 첨삭 플랫폼 (PeerReview)

#### ① 한 줄 요약
매일 아침 CS/기술 질문이 자동 출제되면 60초 음성 녹음 또는 텍스트로 답을 제출하고, 스터디원 간 익명으로 상호 피어리뷰를 진행하며 출석과 예치금을 관리하는 플랫폼.

#### ② 실제 사용자 및 트래픽 유입 근거
- **직접 운영 가능한 스터디**: 본인이 면접 스터디장(또는 부트캠프 프로젝트)이 되어 2~3개 기수(기수당 10~20명)를 실제로 이 서비스로 운영.
- **특정 시간 트래픽 스파이크**: "매일 밤 11시 마감" 규칙으로 인해 **마감 10분 전 트래픽 스파이크(Spike Traffic)**가 인위적으로 발생함. 이를 통해 성능 튜닝 및 동시성 제어의 실측 데이터를 확보할 수 있음.

#### ③ Spring 기술 포인트
- **OCI Object Storage 연동 & Presigned URL**: 음성(WebM) 녹음 파일 업로드 시 WAS 서버의 네트워크 대역폭과 디스크 I/O를 아끼기 위해, WAS에서는 Presigned URL만 발급하고 클라이언트가 OCI Object Storage로 직접 업로드하도록 오프로딩.
- **동시 제출 및 피어리뷰 매칭 동시성 제어**: 마감 시점에 동시에 쏟아지는 제출 처리와 1:1 매칭 알고리즘에서의 동시성 제어 (Redis Redisson 분산 락 또는 DB 비관적/낙관적 락).
- **SSE(Server-Sent Events)**: 피어리뷰 도착 및 실시간 마감 카운트다운 푸시.

#### ④ 배포/운영 시나리오 & 이력서 문장 예시
- **시나리오**: 마감 직전 다수 사용자의 대용량 오디오 파일 동시 업로드로 OCI 단일 인스턴스 네트워크 대역폭 포화 및 톰캣 스레드 잠식 ➡️ Presigned URL 직접 업로드 방식으로 아키텍처 개편.
- **이력서 문장 1**: *"마감 직전 동시 제출 트래픽 집중(순간 TPS 평소 대비 8배) 시 WAS 병목을 해결하기 위해 OCI Object Storage Presigned URL 방식을 적용, WAS 인바운드 트래픽 90% 오프로딩."*
- **이력서 문장 2**: *"Flyway를 도입하여 무중단 배포 시 스키마 변경 이력을 코드 레벨에서 버전 관리하고, 롤백 테스트 절차를 확립하여 DB 배포 리스크 제어."*
- **이력서 문장 3**: *"실제 스터디원 25명을 온보딩하여 8주간 운영하며 수집된 Sentry 에러 로그 42건을 분석·개선, 비정상 세션 끊김 오류율을 0%로 수렴시킴."*

#### ⑤ Oracle 프리티어에서의 리스크
- **스토리지 용량 관리**: OCI 프리티어의 Object Storage 무료 한도는 10GB/월입니다. 음성 파일이 쌓이면 용량 초과 과금 위험이 발생 ➡️ 오디오를 WebM 32kbps 경량 포맷으로 압축 강제 및 30일 경과 파일 자동 삭제 수명주기(Lifecycle Rule) 정책 적용 필수.
- **야간 피크 외 유휴 문제**: 스터디 서비스 특성상 낮 시간대에 트래픽이 없어 OCI 유휴 회수 대상이 될 수 있으므로, 주기적인 통계 산출 배치 스케줄러를 낮 시간대에 분산 실행해야 함.

#### ⑥ 신입 포트폴리오로서 흔한 정도와 차별성
- **흔한 정도**: 30% (스터디/커뮤니티 류는 비교적 흔함).
- **차별성**: 단순 게시판이 아닌 "Presigned URL을 통한 인프라 비용/대역폭 최적화", "실제 25명의 유저를 통한 VOC 수집 및 장애 회고"라는 실제 운영 데이터로 흔함을 극복.

### [최종 추천] 1순위: **주제 1 (IT 컨퍼런스·해커톤 통합 캘린더 구독 및 티켓 오픈 알림 - DevEvent iCal)**

#### 선정 이유:
1. **운영 증거(트래픽) 확보의 확실성**:
   주제 3은 '사람을 모으고 유지하는 운영'의 피로도가 큽니다. 반면 주제 1은 한 번 배포하고 개발자 커뮤니티 몇 곳에 등록 링크를 뿌려두면, **Google과 Apple의 크롤러 봇이 24시간 내내 365일 실트래픽을 만들어줍니다.** 면접관 앞에서 "일평균 N천 건의 실트래픽이 들어왔고, 봇들의 폴링을 ETag 304로 방어했다"는 증거(Grafana 대시보드 캡처, 로그 수치)를 가장 확실하게 보여줄 수 있습니다.
2. **OCI 프리티어와의 궁합 (유휴 회수 자동 방어 & 비용 0원)**:
   텍스트 기반 데이터 중심이므로 200GB 블록 스토리지로 평생 운영 가능하며, 주기적 봇 인입 덕분에 OCI의 악명 높은 '유휴 인스턴스 회수(Idle Reclamation)' 조건을 아무런 편법 없이 합법적인 실트래픽으로 완벽히 방어합니다.
3. **면접관을 사로잡는 기술 키워드**:
   흔한 "Spring Security + JWT + 장바구니" 조합 대신, **"RFC 5545 표준 규격", "HTTP ETag/캐싱 헤더를 활용한 네트워크 대역폭 최적화", "Resilience4j 기반 크롤링 장애 격리", "ARM64 멀티 아키텍처 CI/CD"** 등 백엔드 엔지니어로서 기본기와 인프라 감각을 동시에 증명할 수 있는 독보적인 스토리가 나옵니다.
