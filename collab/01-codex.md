# 1라운드 · Codex 독립 제안

이 조건에서는 **첫 사용자를 직접 확보할 수 있고, 반복해서 이용할 이유가 있는 서비스**를 고르는 것이 좋습니다. 운영 경험을 남기려면 가입자 수뿐 아니라 배포 중 요청 실패, 알림 누락, 복구 시간, 데이터 정합성 같은 문제를 측정할 수 있어야 합니다.

추천 주제는 아래 네 가지입니다. 사용자 확보 경로는 제안이며, 실제 수요가 확인됐다는 뜻은 아닙니다. **이력서 문장의 숫자도 모두 가정한 예시**입니다. 실제 운영, 부하 테스트, 장애 훈련을 구분해서 기록해야 합니다.

**먼저 확인한 Oracle Always Free 제약**

2026년 11월 8일 확인한 공식 문서 기준입니다. 특히 현재 **비유료 Always Free 계정의 A1 한도는 총 2 OCPU·12GB**로 안내됩니다. 과거 자료의 4 OCPU·24GB를 그대로 적용하면 안 됩니다. [Oracle Always Free 공식 문서](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)

| 항목 | 현재 공식 안내와 설계에 미치는 영향 |
|---|---|
| Ampere A1, ARM64 | 월 1,500 OCPU시간·9,000 GB시간. 총 2 OCPU·12GB를 계속 사용하는 규모이며 인스턴스 전체 합산입니다. ARM64 이미지와 네이티브 라이브러리 호환성을 확인해야 합니다. |
| AMD Micro | 최대 2대. 각각 메모리 1GB, CPU 기본 배분 1/8 OCPU, 인터넷 대역폭 최대 50Mbps입니다. Spring·DB·관측 도구를 함께 올리는 기본 구성으로는 여유가 적습니다. |
| 블록 스토리지 | 부팅 볼륨까지 합쳐 200GB. 기본 부팅 볼륨 50GB도 차감됩니다. 무료 볼륨 백업은 합계 5개입니다. |
| Object Storage | 비유료 Always Free 상태에서 합계 20GB, 월 API 요청 5만 회입니다. 백업 보관 기간과 오래된 파일 정리가 필요합니다. |
| 유휴 인스턴스 | 7일 동안 CPU 사용률의 95백분위가 20% 미만이고 네트워크 사용률도 20% 미만이면 회수 대상이 될 수 있습니다. A1은 메모리 사용률 20% 미만 조건도 함께 적용됩니다. |
| 확보 가능성 | 무료 Compute는 홈 리전에 생성해야 하며, 용량 부족으로 생성이 실패할 수 있습니다. 회수 후 즉시 같은 서버를 확보한다는 보장은 없습니다. |
| 무료 Flexible LB | 대역폭은 10Mbps입니다. 월 전송량과 순간 처리 대역폭을 따로 봐야 합니다. |

위 자원·회수 조건은 [Always Free 리소스 문서](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm), 아웃바운드 **월 최초 10TB 무료**는 [공식 가격표](https://www.oracle.com/cloud/price-list/)에서 확인했습니다.

두 가지는 추가로 주의할 만합니다.

- **PAYG와 비유료 계정의 A1 안내가 다릅니다.** 공식 가격표에는 유료 tenancy의 무료 사용량이 월 3,000 OCPU시간·18,000 GB시간으로 기재돼 있습니다. 본인 계정 유형과 콘솔의 실제 한도를 함께 확인해야 합니다. 여기서는 보수적으로 2 OCPU·12GB를 기준으로 추천합니다. [Oracle 가격표](https://www.oracle.com/cloud/price-list/)
- **메일 발송을 무조건 사용할 수 있다고 가정하면 안 됩니다.** 리소스 문서는 월 3,000건 무료라고 안내하지만, 서비스 한도표에는 Always Free의 24시간 발송 한도가 0으로 표기돼 있습니다. 콘솔에서 실제 발송 가능 여부를 먼저 검증하고, MVP에는 서비스 내 알림이나 Discord 웹훅 같은 대안을 준비하는 편이 좋습니다. [무료 리소스 안내](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm), [서비스 한도표](https://docs.oracle.com/en-us/iaas/Content/General/service-limits/default.htm)

무료 계정에는 SLA와 정식 기술 지원도 없습니다. 따라서 백업과 재구축 절차는 이 프로젝트의 중요한 운영 과제가 됩니다. [Oracle Free Tier FAQ](https://www.oracle.com/cloud/free/faq/)

**1. 정원제 스터디·동아리 모임 신청과 대기자 자동 승격**

① **한 줄 요약**  
정기 모임의 참가 신청·취소를 받고, 빈자리가 생기면 대기자를 순서대로 승격시키는 서비스입니다. MVP는 운영자 화면, 모임 생성, 신청·취소, 대기 순번, 승격 알림까지로 잡습니다.

② **실제 사용자가 생길 근거**  
도입할 사람과 사용 시점이 명확합니다. 스터디장이나 동아리 운영자 한 명이 다음 모임의 신청 링크를 공유하면 참가자가 들어옵니다. 정기 모임을 확보하면 매주 이용할 이유도 생깁니다.

개발 전 확보 목표는 **운영자 1명과 실제 모임 2회** 정도가 적절합니다. 현재 구글폼·채팅방으로 신청을 받으며 취소자와 대기자를 수작업으로 관리하는 모임을 찾는 것이 좋습니다.

③ **Spring 기술 포인트**

- Spring MVC·Security로 회원과 운영자 권한 구분
- JPA 트랜잭션과 조건부 갱신 또는 잠금으로 정원 초과 방지
- 모임·회원 조합의 유니크 제약으로 중복 신청 방지
- 신청 변경과 알림 작업을 같은 트랜잭션에 기록하는 Outbox
- 배포 중 두 앱이 함께 실행돼도 승격·알림이 중복되지 않는 작업 처리

④ **배포·운영 시나리오와 이력서 예시**  
신청을 받는 도중 배포하고, 중복 클릭과 취소·신청 경합을 확인합니다. 승격 처리를 마친 직후 프로세스를 종료해 알림이 재개되는지도 검증할 수 있습니다.

> “스터디 참가자 32명의 신청 180건을 8주간 운영했다. 별도 동시 신청 100건 테스트에서 정원 초과와 중복 신청이 발생하지 않도록 트랜잭션을 개선했다.”

주요 지표는 실사용 신청 건수, 정원 초과 건수, 승격 알림 지연, 신청 API의 p95 응답 시간입니다.

⑤ **Oracle 프리티어 리스크**  
신청 시작 시 요청이 몰리는 동안 이미지 빌드나 백업이 CPU·디스크를 점유할 수 있습니다. 빌드는 CI에서 수행하고 백업 시간을 조정해야 합니다. 서버 장애로 신청이 멈추었을 때 운영자가 참가자 명단을 확인할 수 있도록 CSV 내보내기도 유용합니다.

⑥ **흔한 정도와 차별성**  
예약·선착순이라는 소재는 흔합니다. 차별성은 **실제 모임에서 발생한 취소·대기자 승격·배포 문제와 해결 기록**에서 나옵니다. 소수 사용자 서비스인 만큼 대규모 처리량을 주장하기보다 정합성과 운영 결과를 설명하는 편이 설득력 있습니다.

**2. 특정 지역 취준생을 위한 청년 지원정책 구독·마감 알림**

① **한 줄 요약**  
한 지역의 취업·교육·주거 지원정책을 모아 관심 분야를 구독하고, 신규·변경·마감 예정 정책을 알려주는 서비스입니다. MVP는 한 지역, 공식 데이터 원천 하나, 관심 분야 필터, 알림 채널 하나로 제한합니다.

② **실제 사용자가 생길 근거**  
본인과 취업 스터디원이 첫 사용자가 될 수 있고, 지역 취업 커뮤니티에 제공할 이유도 있습니다. 처음에는 취준생 10명에게 기존 확인 방식과 놓쳤던 공고를 물어보고, 실제로 알림을 받아볼 사람을 확보하는 것이 좋습니다.

데이터 확보 경로도 있습니다. 한국고용정보원 온통청년은 청년정책 Open API를 제공하며, 인증키는 신청·심사를 거쳐 발급됩니다. API 존재와 실제 구독 수요는 별도로 검증해야 합니다. [온통청년 Open API 이용 안내](https://www.youthcenter.go.kr/cmnFooter/openapiIntro/oaiGuide)

③ **Spring 기술 포인트**

- 스케줄러 또는 Spring Batch를 이용한 주기적 수집
- 외부 정책 ID 기준 upsert와 내용 변경 감지
- 타임아웃·재시도·호출량 제한, 실패 작업 재개
- 정책·사용자·알림 종류별 중복 발송 방지
- 마지막 동기화 시각과 데이터 변경 이력 관리

④ **배포·운영 시나리오와 이력서 예시**  
외부 API 응답 지연, 필드 누락, 일부 페이지 수집 실패를 재현합니다. 중간 실패 이후 이어받기와 밀린 알림 처리를 검증하기 좋습니다.

> “실구독자 24명을 대상으로 정책 알림을 운영했다. 외부 API를 30분 차단한 장애 훈련에서 미처리 240건을 복구 후 6분 이내 처리했고, 중복 발송은 발생하지 않았다.”

주요 지표는 활성 구독자, 알림의 원문 링크 클릭, 수집 성공률, 마지막 성공 이후 경과 시간, 알림 처리 지연입니다. 주기적 API 호출량은 사용자 트래픽과 따로 집계해야 합니다.

⑤ **Oracle 프리티어 리스크**  
전체 데이터를 자주 재수집하거나 모든 구독자에게 개별 알림을 보내면 자원·발송 한도를 소모합니다. 변경분 위주 처리와 묶음 알림이 필요합니다. 외부 데이터가 오래됐을 때 이를 표시하고, 신청 전 원문을 확인할 수 있게 해야 합니다.

⑥ **흔한 정도와 차별성**  
공공 API 검색 서비스는 흔한 편입니다. **변경 이력, 실패 후 재수집, 알림 누락 방지, 데이터 최신성 공개**까지 운영하면 설명할 내용이 생깁니다. API 데이터를 화면에 보여주는 단계에 머물면 포트폴리오의 깊이가 얕아집니다.

**3. 백업·배치 작업의 실행 누락 감지 서비스**

① **한 줄 요약**  
정기 작업이 완료될 때 HTTP 신호를 보내고, 정해진 시각까지 신호가 없으면 담당자에게 알리는 서비스입니다. MVP는 작업 등록, 주기·유예시간 설정, 성공·실패 신호 수신, 알림, 이력 조회입니다.

② **실제 사용자나 트래픽이 생길 근거**  
자신의 DB 백업부터 연결할 수 있습니다. 이후 스터디원의 데이터 수집, 정기 보고서 생성, 홈서버 백업 같은 실제 작업을 연결합니다. 사람이 매일 화면을 열지 않아도 실제 작업의 성공 여부를 감시하는 이용이 계속됩니다.

이 방식은 Healthchecks.io도 사용하는 운영 모델입니다. 다만 기존 대안이 있으므로, 동료 개발자 2~3명이 자기 작업을 연결할 의사가 있는지 먼저 확인해야 합니다. [Healthchecks.io 공식 설명](https://healthchecks.io/docs/)

③ **Spring 기술 포인트**

- API 키 인증과 작업별 접근 제어
- 예정 시각·유예시간·시간대 처리
- 정상·지연·실패·복구 상태 전이
- 여러 실행 인스턴스 사이의 알림 중복 방지
- 수신 이력 집계와 보관 기간별 데이터 정리

④ **배포·운영 시나리오와 이력서 예시**  
백업 작업 중단, 지연 신호, 중복 신호, 서비스 재시작 후 밀린 판정 등을 훈련합니다. 알림이 너무 자주 울리는 문제도 실제 운영 과제가 됩니다.

> “실제 정기 작업 30개를 연결해 운영했다. 장애 훈련에서 유예시간 종료부터 알림 발송까지의 지연을 p95 30초 이내로 측정하고, 동일 장애의 반복 알림을 제한했다.”

작업 수와 수신 요청 수 외에 오탐률, 알림 지연, 복구 알림 누락을 기록할 수 있습니다.

⑤ **Oracle 프리티어 리스크**  
이 서비스와 감시 대상이 같은 서버에 있으면 함께 중단될 수 있습니다. 서비스 자체의 생존 확인은 OCI 밖에서 해야 합니다. 수신 이력을 무기한 저장하면 디스크가 증가하므로 원본 이력과 장기 집계를 구분해야 합니다.

⑥ **흔한 정도와 차별성**  
일반적인 CRUD 포트폴리오보다 덜 흔한 소재입니다. 다만 기존 제품을 재현하는 성격이 강합니다. 차별성은 실제 작업 연결, 오탐 조정, 알림 실패 대응, 감시 서비스 자체의 장애 대응에서 만들어야 합니다.

**4. 소규모 개발팀용 웹훅 수신함·재전송 서비스**

① **한 줄 요약**  
GitHub 등의 웹훅을 받아 저장하고, 전달 대상이 실패하면 재시도하거나 사람이 재전송할 수 있는 서비스입니다. MVP는 GitHub 이벤트 일부와 사전 승인한 전달 대상만 지원합니다.

② **실제 사용자나 트래픽이 생길 근거**  
자신의 저장소와 배포 파이프라인을 첫 사용처로 연결할 수 있습니다. 동료 팀이 웹훅 연동을 개발할 때 요청 이력 확인과 실패 재처리 용도로 제공할 수도 있습니다.

GitHub는 실패한 웹훅을 자동으로 재전송하지 않습니다. 따라서 전달 실패를 확인하고 복구하는 구체적인 용도가 있습니다. 다만 자신의 저장소만 연결했다면 개인 도구 이용으로 정직하게 설명해야 합니다. [GitHub 실패 웹훅 처리 문서](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)

③ **Spring 기술 포인트**

- 요청 원문을 이용한 HMAC 서명 검증
- delivery ID를 이용한 중복 수신 처리
- DB 저장 완료 후 빠르게 응답하는 수신 API
- DB 작업 테이블을 이용한 비동기 전달·지수 백오프
- 팀별 권한, 재전송 감사 기록, payload 보관 기간 관리

GitHub도 빠른 응답과 비동기 처리를 권장합니다. [GitHub 웹훅 권장 사항](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)

④ **배포·운영 시나리오와 이력서 예시**  
전달 대상이 5xx를 반환하거나, 저장 직후 프로세스가 종료되는 상황을 재현합니다. 재시도 폭주와 특정 대상의 장애가 다른 대상에 미치는 영향도 측정할 수 있습니다.

> “실사용 저장소 5개를 연결하고 수신부터 전달까지의 지연을 측정했다. 별도 장애 훈련에서 전달 대상 복구 후 적체 이벤트 300건을 재처리했다.”

보장 범위는 명확해야 합니다. **이미 수신·저장한 이벤트의 재처리**와 서비스가 내려가 수신하지 못한 이벤트의 복구는 별개입니다. 재시도 과정에서 전달이 중복될 가능성도 설계에 포함해야 합니다.

⑤ **Oracle 프리티어 리스크**  
큰 payload, 무한 재시도, 요청 원문 로그가 디스크와 CPU를 소모할 수 있습니다. 크기·재시도 횟수·보관 기간 제한이 필요합니다. 전달 URL을 자유롭게 받으면 내부망 접근에 악용될 수 있으므로 MVP는 승인한 HTTPS 목적지로 제한하는 편이 좋습니다.

⑥ **흔한 정도와 차별성**  
신입 프로젝트에서는 비교적 덜 흔하고 백엔드 설계 설명에 적합합니다. 반면 첫 사용자 확보는 모임 신청 서비스보다 어렵다고 봅니다. 실제로 연동을 사용하는 팀을 구하지 못하면 테스트 요청만 많은 프로젝트가 될 수 있습니다.

**2~3개월 안에 완성하기 위한 공통 운영 구성**

처음에는 **Java + Spring Boot, PostgreSQL, 간단한 웹 화면, Docker Compose, Nginx** 정도로 시작하는 것을 권합니다. A1 한 대에서 운영하면서 배포 순간에 두 앱을 띄울 여유를 남기는 구성입니다.

- **CI/CD:** CI에서 ARM64 이미지를 만들고 커밋별 태그로 배포합니다. 새 앱의 준비 상태를 확인한 뒤 트래픽을 전환하고 기존 요청을 마무리합니다. 앱 롤백이 가능하도록 DB 변경의 호환성도 유지합니다. Spring Boot는 준비 상태 확인과 graceful shutdown 기능을 제공합니다. [Actuator 문서](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html), [종료 처리 문서](https://docs.spring.io/spring-boot/reference/web/graceful-shutdown.html)
- **관측:** 요청 오류율·p95 응답 시간·메모리·디스크·작업 적체·백업 최신성을 기록합니다. 서버 전체 중단 감지는 외부에서 수행합니다.
- **백업·복구:** DB 백업을 자동화하고 보관 기간을 제한합니다. OCI 외부에도 사본을 두고 별도 환경에서 복구합니다. DB 복원 시간과 OCI 서버 전체 재구축 시간은 구분해서 기록합니다.
- **보안 유지보수:** 의존성 취약점 점검, 실제 패치 배포, 비밀키 교체, 인증서 만료 확인을 운영 기록에 남깁니다. 관리용 Actuator와 DB 접근은 제한합니다.

일정은 **1~2주차 사용자 확보·범위 확정, 3~5주차 MVP 배포, 6~8주차 실제 이용과 수정, 9~12주차 복구 훈련·성능 개선** 정도가 적절합니다. 장애를 기다릴 필요는 없습니다. 훈련임을 밝히고 원인, 영향, 탐지 시간, 복구 시간, 재발 방지 조치를 남기면 됩니다.

단일 서버에서 앱을 교체하며 요청을 유지한 경험과 서버 장애까지 견디는 고가용성은 구분해서 설명해야 합니다. 가동률 역시 측정 기간과 측정 방법을 함께 제시하는 편이 좋습니다.

**최종 1순위는 ‘정원제 스터디·동아리 모임 신청과 대기자 자동 승격’입니다.**

도입을 결정할 운영자가 명확하고, 정기 모임을 확보하면 반복 이용이 생깁니다. 외부 API의 승인이나 데이터 품질에 대한 의존도도 낮습니다. 구현 범위는 작게 유지하면서 동시성, 알림 누락, 배포 중 처리, 백업 복구를 모두 경험할 수 있습니다.

시작할 때 가장 먼저 할 일은 **운영자 한 명에게 다음 두 번의 모임에서 실제로 사용하겠다는 약속을 받는 것**입니다. 그 약속을 확보하면, 흔한 예약 소재라도 면접에서 설명할 수 있는 자신의 운영 경험으로 만들 가능성이 가장 높습니다.
