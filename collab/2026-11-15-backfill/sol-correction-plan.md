2026-11-15. 읽은 범위: PRD FR-C1, `agy-result.md`의 기존 실측과 §5, 검수 코드 `c76edad`의 BackfillCollector/CollectionRuns/RecruitmentClient/ParsedPage/PostingIngestor/V3, 기존 공식 명세. Claude의 새 수정안이나 agy의 진행 중인 쿼리 검증 결과는 읽지 않았다. 앱·DB·기존 기록·브랜치·env 변경과 실제 API 호출은 하지 않았다.

## 판정과 미확정 사실

22,733건·37회·재실행 0회는 **기존 월별 쿼리에서 받은 집합의 완결성과 재개**를 측정한 결과다. 월 걸침 0건/진행 1건이라는 관측상 FR-C1의 시작일 기준 3년 전체를 완료했다고 볼 수 없다. 정기 수집으로 일부를 나중에 보충하거나 임의 미래 마감 상한을 두는 방식은 수정안이 아니다.

[공식 목록 명세](https://www.data.go.kr/data/15125273/openapi.do)는 두 날짜를 시작일 기준 조회 범위로 설명하고 둘 다 선택 항목으로 둔다. 이 설명만으로 실제 종료일 필터의 의미를 확정하지 않는다. **주된 최소안은 시작 하한만 보내고 종료 조건·ongoingYn을 생략한 단일 페이지열을 읽어, 시작일 상한은 로컬에서 적용하는 것**이다. 단, 이 요청이 마감일이 멀리 있는 공고까지 포함하는 상위집합이라는 확인은 agy의 제한된 검증을 기다린다. 생략된 종료일에 서버 기본 상한이 있다면 이 안으로 COMPLETE를 만들면 안 된다. 그 경우 날짜 조건 자체를 생략한 공식 목록 전체 페이지열 등 실제 상위집합 계약을 먼저 확인해야 한다. 확인 전 다른 API 호출을 추가하거나 임의 날짜를 정하지 않는다.

## 가장 작은 완전 수정

1. **월 반복을 단일 전체 조회로 교체한다.** BackfillRange는 로컬 목표 `[2023-11-15, 2026-11-15]`를 고정하는 용도로 유지한다. 원격은 위에서 확인한 한 요청 조건으로 pageNo=1..N, numOfRows=1000을 읽는다. 종료는 로컬 채택 건수가 아니라 **원격 raw received == 원격 totalCount**로 판단한다. 월별 보고가 필요하면 채택된 시작일로 집계하며 월별 HTTP 조회를 되살리지 않는다.
2. **raw 완결성 검사와 목표 범위 반영을 분리한다.** JSON을 한 번 전부 파싱해 봉투·모든 행·페이지 내부 중복을 검증한다. 이어 raw totalCount 일관성, 기대 페이지 크기, 이전 페이지와의 **모든 raw SN** 중복을 반영 전에 검사한다. 그 뒤 같은 파싱 결과에서 `from <= begin <= to`인 행만 골라 기존 최초 적재 upsert 경로에 넣는다. 범위 밖 정상 행은 오류가 아니며 DB에 쓰지 않는다. 범위 밖 행이라도 malformed/중복이면 페이지 전체를 거부한다. 원격 total/received/고유 수와 로컬 채택/inserted/changed를 서로 덮어쓰지 않도록 공개 계약도 갱신한다. 정기 applyRegular의 의미는 바꾸지 않는다.
3. **전체 조회 세대별 페이지 체크포인트를 둔다.** 체크포인트 키는 조회 전략 버전 + 목표 기간 + scan generation + pageNo다. raw total/received/SN 집합과 선택된 목표 SN 집합을 구분해 남긴다. raw가 1,000건이고 목표가 0건인 페이지도 정상 체크포인트 후 다음 페이지로 간다. 범위 밖 raw SN도 다음 페이지 중복 검사에 포함한다. 재개는 동일 조회 세대의 연속 완료 페이지와 그 집합만 사용하며, 서로 다른 재시작 세대의 “최신 페이지”를 번호별로 섞지 않는다. `restart-pages`는 새 세대로 1페이지부터 시작하고, 과거 페이지 기록은 보존한다.
4. **구형 완료와 새 완료를 명시적으로 구분한다.** 기존 completedMonth/range_from·to만으로 새 적재를 skip하지 않는다. 구형 월별·명령 COMPLETE는 당시 받은 집합의 이력으로 유지한다. 새 전략의 전체 페이지 검증과 목표 SN 집계를 마친 **동일 목표 기간의 완료 스캔**만 새 슬롯에서 HTTP 0회 재사용한다. total 변경/중복/실패가 있으면 새 완료를 만들지 않고 받아들인 페이지까지 기록한다.
5. **V4는 최소 additive 메타데이터로 쓴다.** 예를 들어 collect_run에 조회 전략 버전(nullable: 기존은 legacy), scan 식별자, 선택 SN 집합을 추가하고 새 조회용 부분 인덱스를 둔다. 기존 total_count/received/unique_count/received_sns는 새 전략에서 raw 기준으로 사용하고, 목표 고유 수는 별도 선택 집합의 크기로 얻으면 같은 수치 열을 더 복제할 필요가 없다. period_from/to는 로컬 목표, 원격 종료 조건 부재는 전략으로 명시한다. 기존 V1~V3·22,733개 공고·회차·api_budget/api_attempt를 삭제/초기화하거나 과거 COMPLETE를 실패로 바꾸지 않는다. M2 마이그레이션은 이 V4 이후 **V5부터** 예약하고 설계/후속 테스트 PR도 이 순서에 맞춘다.

페이지 반영과 체크포인트 사이에서 죽으면 그 페이지를 다시 받되 기존 멱등 upsert로 복구한다. 상세 DONE·최초 출처·기존 변경 관측 규칙은 유지한다. 원격 페이지가 실행 중 바뀌면 total/중복 등 탐지 가능한 변경에서는 멈춘다. 원천이 스냅샷 토큰을 제공하지 않으므로 같은 건수를 유지한 채 데이터가 교체되는 모든 경우까지 원격 스냅샷 일관성을 보장한다고 쓰지는 않는다.

## 실제 재실행의 완료 증거

검수 후 별도 승인된 실행에서 raw total/received/unique, 목표 received/unique, 신규 삽입·기존 갱신, DB 목표 기간 건수를 따로 기록한다. 기존 22,733과 합친 DB 건수를 새 원격 수신 수라고 쓰지 않는다. 월 걸침·종료일 이후 마감·현재 진행·목표 밖 미래 시작의 포함/제외를 SN·건수 표본으로 확인한다. 옛 41회와 이후 계약 검증 시도는 그대로 보존하며 새 시도만 api_attempt 증분으로 센다. 새 슬롯 1회 재실행의 HTTP 0회 및 코드/품질 표본까지 확인한 뒤 FR-C1 완료를 판단한다. 본 제안은 적재 완료 기록이 아니다.
