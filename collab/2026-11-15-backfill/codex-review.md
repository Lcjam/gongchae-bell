# 실제 최초 적재 검수 · codex

판정: **부분 적재, FR-C1 미완료.** 2023-11-15~2026-11-15를 시작일 기준으로 빠짐없이 채워야 한다. 월 경계 누락을 별도 백로그로 미루거나 정기 수집이 일부 진행 공고를 가져올 것으로 대체하지 않는다.

## 확인한 증거

- agy의 실제 보고는 37개 월/37 HTTP, 22,733행, 재실행 0 HTTP, 전체 예산 41이다. root도 영속 PostgreSQL에서 예산 41, 공고 22,733, 월을 걸쳐 시작·마감한 행 0, OPEN 1, BACKFILL COMPLETE 76행을 읽기 조회로 확인했다.
- 공식 목록의 앞선 497행 표본에는 기간 내 시작했으나 11월 15일 후 마감하는 진행 공고가 있다. 월별 적재가 최근 시작 공고와 월을 걸치는 과거 공고를 포함하지 못한 점은 시작일 기준 전체 이력 요구와 맞지 않는다.
- [공식 명세](https://www.data.go.kr/data/15125273/openapi.do)는 두 날짜 인자를 선택 항목으로 두고 둘 다 "채용공시 시작일 기준" 조회 시작/종료일이라고 설명한다. root가 직접 확인했다. 현재 관측은 이 설명과 어긋나므로 실제 필터 의미는 제한된 공식 API probe로 검증해야 한다. 원천 구현의 의미를 문서 이름만으로 확정하지 않는다.

## 필요한 수정 경계

1. 원천이 실제로 제공하는 누락 없는 페이지 집합을 먼저 확인하고, 시작일 기준 목표 기간의 반영을 그 수신 완결성과 구분한다. 임의 미래 상한으로 보장하지 않은 자료를 완료로 취급하지 않는다.
2. 기존 정상 공고와 시도 기록은 보존한다. 새 수집 방식이 기존 월 COMPLETE·페이지 SN 스냅숏을 그대로 재사용해 skip하지 않게 한다. 필요하면 방식 버전을 분리한다.
3. 원격 페이지 총수·raw SN 중복/완결성, 범위 안 공고의 반영·고유 수, 재시작 체크포인트와 같은 명령 재실행 경계를 테스트한다. 범위 밖 시작일이 정상적으로 내려올 수 있는 넓은 질의라면 명시적 로컬 선별 계약이 필요하다.
4. V1~V3는 영속 DB에 적용됐으므로 변경하지 않는다. 새 메타데이터가 필요하면 V4를 이 수정에 우선 배정하고 아직 미착수인 M2의 시작 번호를 미룬다. 기존 앱과 호환되는 추가 변경이어야 한다.
5. 수정 후 실제 누락분을 적재하고 기간·페이지·고유 수·월 경계/진행 공고·코드 품질 표본·호출 예산을 다시 대조한다. 기존 부분 적재의 명령 COMPLETE는 당시 질의에 대한 결과일 뿐, 제품 전체 이력 완료의 증거로 재사용하지 않는다.

현재 #11 병합과 M2 구현은 이 필수 수정의 검증을 기다린다. root는 구현하지 않고 완료된 제안·diff·테스트·실측을 검수한다. 실제 API probe는 agy 한 명이 기존 클라이언트와 영속 예산 경로에서 최대 3 HTTP 시도만 담당한다.
