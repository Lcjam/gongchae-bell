## C1 · 관리 링크 재발송과 해지가 경합하면 고정 응답 대신 500

`SubscriptionService.java:274-277`의 ACTIVE 구독 SELECT에는 부모 잠금이 없다. SELECT 직후 다른 요청이 해지 DELETE를 커밋하고, 이어 `ledger.createSync`가 자식 notification을 INSERT하면 FK 위반이 발생한다. 이 생성 트랜잭션은 `deliver`의 예외 처리보다 앞이므로 ACCEPTED로 마무리되지 않는다. agy R-1과 같은 발견이다.

부모를 먼저 잠그는 순서를 유지하면서 SELECT~INSERT를 해지와 직렬화할 것. `FOR KEY SHARE`/`FOR SHARE` 중 실제 상태 전이 계약에 맞는 최소 잠금을 선택한다. 단순히 모든 DB 오류를 삼키는 것으로 해결하지 않는다. 격리 PG의 두 트랜잭션 경합으로 고정 응답·오발송 0·FK 오류 없음/삭제 후 0행 처리를 검증한다.

## C2 · 복원 대장 파일 누락을 정상적인 빈 대장으로 처리

`ErasureJournal.java:66-68`은 경로가 존재하지 않으면 `List.of()`를 반환한다. `ErasureReapplyCommand.reapply`는 이를 성공/삭제 0건으로 처리한다. 복원 마운트 누락이나 경로 오타가 나면 이미 해지한 구독이 복원 DB에 살아 있는 상태에서 재적용 완료로 보일 수 있다. 손상된 줄만 거부하는 것으로 fail closed를 충족하지 못한다.

복원에서 대장 부재는 실패로 처리하고 DB 삭제를 시작하지 않을 것. 신규 운영의 정당한 빈 파일 준비와 복원 시 파일 부재를 구별한다. 기존 empty 파일은 유효한 빈 대장으로 다룰 수 있다. 누락·잘못된 경로·손상된 끝줄 각각에 대해 성공 로그/정상 종료가 없고 DB가 변하지 않는 검증이 필요하다. 운영자가 먼저 확인하라는 설명만으로 대체하지 않는다.

## C3 · 최초 파일 생성의 디렉터리 fsync가 공유 잠금 밖에 있음

`ErasureJournal.java:48-61`: A 프로세스가 새 파일을 만들고 파일 force 후 60행에서 OS 잠금을 풀지만 디렉터리 force 전 멈출 수 있다. B 프로세스는 이미 존재하는 파일을 보아 `created=false`이고, 잠금을 얻어 자기 줄을 force한 뒤 디렉터리 force 없이 반환/DB DELETE 커밋한다. 그 시점에는 디렉터리 엔트리 내구성이 아직 확보되지 않았다. JVM 내부 동기화는 blue/green의 서로 다른 JVM을 막지 못한다.

첫 파일의 디렉터리 내구성까지 공유 OS 잠금 안에서 보장할 것. 항상 부모 디렉터리를 잠금 안에서 force하는 등 작은 수정이면 충분하며, 새 파일 여부를 잠금 전에 관측한 값만으로 생략하지 않는다. POSIX 배포 경로와 Windows 예외를 문서와 일치시키고, 잠금 해제보다 디렉터리 force가 먼저라는 실행 순서/실패 전파 검증을 남긴다. 이번 수정에 대장 압축·보관 정책 도구까지 추가하지 않는다.

## C4 · 동기 25초 예산에서 제어 가능한 DB 대기 경로가 빠짐

`SyncSender.java:15-19`는 가입 트랜잭션·풀·잠금·SQL·정리를 모두 예산에 포함한다고 적었으나, `SubscriptionService.java:113-119,269-277,325-337`의 선행 rate_limit/가입·복구 트랜잭션과 `RateLimiter.acquire`에는 lock/statement/transaction 제한이 없다. 같은 대상의 INSERT/UPDATE를 다른 트랜잭션이 잡고 있으면 행 잠금을 25초 넘게 기다릴 수 있다. Hikari 5초는 연결 획득 제한이므로 이를 막지 못한다. Discord 성공 후 저장 트랜잭션과 `SyncSender.end:128-129`도 같은 점검 대상이다.

또한 agy M-1처럼 루프 바깥 MIN_START 통과 후 풀 대기로 잔여 시간이 CLEANUP 이하가 되면 76행의 boundWaits가 1ms로 떨어지고 정상 종결 대신 SENDING이 남는다. R 전 잔여 예산 재확인도 없어 HTTP를 시작할 시간이 없는 상태에서 SEND_TOTAL/attempt를 예약할 수 있다.

기존 구조 안에서 모든 동기 경로의 제어 가능한 DB/풀 대기를 같은 단조 시계 예산으로 제한하고, 트랜잭션 진입 후·R 전·HTTP 직전 잔여 시간을 다시 확인할 것. 최종 정리 몫과 unknown/환불 없음·펜싱 계약을 보존한다. 이미 소진된 예산으로 새 HTTP/예약을 시작하지 않으며 DB 장애 때 무조건 정상 종결을 보장한다고 과장하지 않는다. 가상 타이머의 tx 진입 경계와 격리 PG의 실제 선행 rate_limit/가입 행 잠금 경합 검증을 함께 남긴다. 예산 보장이 없는 구간을 문서에서만 삭제해 범위를 축소하지 않는다.

## C5 · Discord 전송 직전 DNS 사전 검사가 전송 timeout 밖

`HttpTransports.java:120-124`의 `guard.allows`는 동기 `InetAddress.getAllByName`을 호출한 다음에야 제한된 HTTP exchange에 들어간다. 느린 resolver에서 이 호출이 오래 걸리면 전달받은 timeout을 전부 쓰고도 동일한 원래 timeout으로 HTTP를 새로 시작한다. 고정 호스트/TOCTOU의 수용된 한계와 별개로, 코드가 시작하는 대기 시간을 제한한다는 동기 계약이 깨진다.

사전 DNS 검사와 실제 HTTP가 하나의 전달된 전송 예산을 사용하게 하고, DNS 대기 소진 시 이후 HTTP를 시작하지 않을 것. 허용 주소 전부 검사·리다이렉트 금지·실패 시 차단을 유지한다. 느린/멈춘 대역 resolver로 반환 시간과 HTTP 0회를 확인한다. 실제 DNS 장애를 일으키거나 공급자를 호출하지 않는다. 새 라이브러리나 범용 작업 프레임워크는 필요하지 않다.

## C6 · 긴 Retry-After를 파싱 실패로 버려 조기 재시도

`HttpTransports.java:59-64`는 유효한 `86400` 이상을 null로 반환한다. 호출자는 null을 기본 2초/4초 backoff로 해석하므로 공급자가 하루 기다리라고 해도 즉시 재시도한다. agy R-2를 필수 수정으로 수용한다. 유효한 큰 대기 값은 안전하게 상한 처리하거나 '요청 안에서 기다릴 수 없는 긴 대기'로 보존하여 추가 HTTP를 종료한다. NaN/무한대/잘못된 문자열과 구분하고 Resend/Discord의 파싱 대역 테스트를 보강한다.
