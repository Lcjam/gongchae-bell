# 성능·자원 측정 독립안 · Codex

2026-11-20. 다른 에이전트의 이번 #18 독립안을 읽기 전 작성했다. GitHub #18 현재 본문과 PRD §6·§7을 직접 읽었다. 목표 수치는 실측 뒤 정하고 외부 API·발송을 부하 경로에 넣지 않는다.

## 가장 작은 측정 경로

기존 G4 외부 HTTP runner의 표본 구조를 재사용하거나 표준 라이브러리만 쓰는 작은 별도 runner로, 공개 HTTPS의 홈·목록·신입/지역 등 고정 필터·실제로 존재하는 상세·기관 각 경로를 고정한다. body를 저장하지 않고 UTC 시각·case·status·elapsed_ms·오류 종류를 원자료로 남긴다. 존재하는 sn/기관은 실행 전 조회 결과로 고정하고 redirect 처리와 기대 상태를 명시한다. 평균만으로 p95를 대신하지 않으며 표본 수와 nearest-rank 같은 집계법을 기록한다. 실패 표본을 p95에서 조용히 제외하지 않는다.

동시성 1로 짧게 워밍업 후 측정하고 필요하면 2와 4까지 늘리는 것은 **설정 제안**이다. 방문자 영향이 없는 상한·총요청 수·실행 시간을 먼저 리뷰한다. 무제한 루프나 지속 rate 확대는 없다. 각 case의 n과 실제 분모, DNS/TLS 포함 여부·keepalive·client 위치를 남긴다. HTTP 요청 자체가 page-view 통계를 바꾸는 것도 시험 트래픽으로 기록한다. 큰 DB hash/덤프를 매초 만들어 부하를 왜곡하지 않는다.

실제 VM의 docker stats를 일정 간격으로 동시에 기록하고 RSS/cgroup 메모리·CPU 정규화 기준을 명시한다. disk 사용량/여유와 데이터 볼륨 크기는 구간 전후에만 수집한다. 호스트 CPU·메모리도 포함해 컨테이너 수치만으로 A1 전체 여유를 과장하지 않는다. 다른 CI/backup 작업의 겹침과 배포 SHA·이미지·시간·데이터량·collector/alerts 플래그를 함께 기록한다.

## 세 구간과 실제/대역의 경계

1. 평상시: 운영 공개 URL을 낮은 제한 부하로 측정한다. 앱과 DB source 및 데이터량, 수집/알림 비활성 상태를 표시한다.
2. 수집 중: 반복 real API를 부르지 않는다. 격리 복원 데이터+fixture 수집으로 API 없이 DB/웹 경합을 측정하거나 나중에 정상 정기 수집 한 회차에 관측을 붙인다. 둘은 다른 실험으로 표기하며 fixture 결과를 실제 공급자 네트워크 비용까지 포함한 운영 수집 결과라고 쓰지 않는다. snapshot 등 실제 복원 전제가 아직 없으면 그 구간은 미완료로 남긴다.
3. blue/green 겹침: 다음 정상 승인 배포의 실제 두 색 overlap 창을 관측한다. 요청이 두 앱으로 분산됐다는 보장은 없으며 공유 DB와 메모리 자원 중첩의 관측으로 기록한다. 배포 없이 두 색을 임의로 중복 가동해 sender/collector 중복 작동 위험을 만들지 않는다.

CPU/RAM이 높거나 readiness/외부 상태가 악화되면 생성 부하만 먼저 중단하고 공개 서비스의 건강을 확인한다. 자동 서비스 재시작·DB 변경·수집 플래그 변경을 부하 스크립트의 부수 효과로 넣지 않는다.

## 장애 훈련

성공 G4 후 수동 rollback 기록은 실패 유도 abort의 증거가 아니다. 공개 사이트를 끊는 대신 외부 시험 runner의 한 경로에만 통제된 실패를 주어 G4_FAIL→abort→이전 색 복귀를 검증하는 작은 훈련안을 별도 검토할 수 있다. 실제 deploy 상태·upstream·양색 readiness·pending 없음·데이터 보존을 확인해야 한다. 장애 유발 방법과 영향/실패 시간 상한은 3자 검토 후 확정하며 아직 실행 배정이 아니다. 별도 collector 경보 훈련은 감시 경로 시험이고 배포 실패 rollback을 대체하지 않는다.

원자료와 집계, 실행 명령·조건·제약을 저장소에 남기고 각각 독립 원인/재발 방지안을 작성한 뒤 root가 훈련 표시 포스트모템을 종합한다. 근거 기반 목표는 결과를 읽은 다음 정한다. 이번 문서의 숫자는 측정 계획 제안이며 실측이 아니다.
