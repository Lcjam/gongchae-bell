## 주제를 고르는 기준

트래픽이 거의 없는 개인 프로젝트는 운영할 거리가 생기지 않는다. 그래서 기준을 이렇게 잡았다.

1. **트래픽이 적어도 문제가 저절로 생기는 구조**: 외부 API나 사이트에 의존하고, 스케줄 작업과 알림 발송이 있으면 상대가 바뀌거나 죽을 때 실제 장애가 난다. 이력서에 쓸 "사건"이 억지로 만들지 않아도 생긴다.
2. **실사용자 몇 명이라도 확보할 수 있는 경로**: 본인이 속한 집단(취준생, 학교, 스터디)의 실제 불편을 푼다.
3. **데이터가 쌓이는 구조**: 쌓여야 백업, 복구, 마이그레이션, 인덱스, 쿼리 개선이 진짜 일이 된다.
4. **흔한 CRUD 클론 피하기**: 쇼핑몰, 게시판, 영화 예매, 선착순 쿠폰은 신입 포트폴리오에서 너무 흔하다.

## 후보

### A. 채용/공고 수집 + 키워드 알림 서비스 (1순위)
- **요약**: 공공기관 채용(잡알리오 등 공식 API), 개발자 채용 RSS, 학교 공지 같은 소스를 주기적으로 수집해 중복을 제거하고, 구독 키워드에 맞는 공고를 이메일, 디스코드, 텔레그램으로 보낸다.
- **실사용 근거**: 본인이 지금 취준생이다. 본인, 스터디원, 동기가 첫 사용자가 되고 커뮤니티에 공유하기 쉽다.
- **Spring 포인트**: `@Scheduled`/Spring Batch, 소스별 수집기 인터페이스, 재시도와 서킷브레이커(Resilience4j), 멱등 수집(해시 기반 중복 제거), 발송 이력과 실패 재발송(아웃박스 패턴), Flyway, 테스트컨테이너.
- **운영 시나리오**: 소스 사이트 구조나 API가 바뀌면 수집 실패율이 오르고 알림이 오며, 이를 대응한 회고를 남긴다. 발송 실패가 쌓이면 재처리한다. 공고 데이터가 쌓이면서 검색 쿼리가 느려지면 인덱스를 손본다.
- **이력서 문장 예시**: "외부 수집 소스 7개의 실패율을 Grafana로 추적하고, 소스 스키마 변경 장애 3건을 평균 N분 안에 감지·복구" / "알림 발송을 아웃박스 패턴으로 바꿔 서버 재시작 중 유실 0건"
- **리스크**: 크롤링 약관과 법적 문제가 있으니 공식 API, RSS, 공개 데이터를 우선한다. 소스가 적으면 단조롭다.
- **차별성**: "채용공고 크롤러" 자체는 흔하다. 하지만 **수집 신뢰성과 운영 지표**를 중심에 두면 흔하지 않다.

### B. 동기들 포트폴리오 서버용 업타임 모니터 + 상태 페이지
- **요약**: URL, 포트, SSL 만료를 주기적으로 검사하고, 장애가 나면 알림을 보내고, 공개 상태 페이지를 제공한다.
- **실사용 근거**: 주변 취준생 대부분이 포트폴리오 서버를 갖고 있고, 면접 중에 서버가 죽어 있는 걸 무서워한다. 사용자를 모으기 쉽다.
- **Spring 포인트**: 대량 주기 점검(Java 21 가상 스레드), 알림 중복 억제와 에스컬레이션, 시계열 데이터 보존과 다운샘플링, 멀티테넌시.
- **운영 시나리오**: 감시 서비스 자신을 Micro 인스턴스에서 다시 감시한다. 오탐을 줄이려고 다중 지점에서 확인한다.
- **리스크**: Uptime Kuma 같은 완성된 오픈소스가 있다. "왜 직접 만들었나"에 답할 근거가 필요하다.
- **차별성**: 중상. 운영 도메인 자체라 면접에서 대화가 잘 이어진다.

### C. 스터디/동아리 운영 백엔드 + 디스코드 봇 (출석, 과제 인증, 벌금 정산)
- 실사용자 확보가 가장 쉽다. 다만 기술적 운영 거리가 적어서 A나 B에 비해 약하다.

### D. 선착순 예약/티켓팅 (동시성 + 부하 테스트)
- 수치(TPS, p95)는 잘 나온다. 하지만 실사용자가 없어 운영 경험이 합성 부하에 그치고, 신입 포트폴리오에서 매우 흔하다. 비추천.

## 주제와 무관하게 깔고 갈 인프라 기본형

- **A1 (2 OCPU/12GB) 1대**: Docker Compose로 Nginx(또는 Caddy), Spring 앱 blue/green 2개, PostgreSQL 또는 MySQL, (필요하면) Redis, 관측 스택을 올린다. 관측 스택은 Prometheus, Grafana, Loki를 직접 올리거나 Grafana Cloud 무료 플랜으로 보내 메모리를 아낀다.
- **Micro 1GB 1대**: 바깥에서 본 서버를 감시하는 용도. 같은 서버가 자기 자신을 감시하면, 서버가 죽을 때 알림도 같이 죽기 때문이다.
- **CI/CD**: GitHub Actions에서 테스트, arm64 이미지 빌드(JAR는 아키텍처와 무관하니 베이스 이미지만 멀티아치면 된다), 레지스트리 푸시, SSH 배포, 헬스체크, Nginx upstream 전환, 실패하면 자동 롤백.
- **백업**: 매일 DB 덤프를 Object Storage에 올리고, 월 1회 복구 리허설을 해서 RTO와 RPO를 실측한다.
- **문서**: 장애 회고(포스트모템)를 `docs/incidents/`에 쌓고, 배포 이력과 아키텍처 결정 기록(ADR)을 남긴다. 이 문서들이 포트폴리오의 핵심 증거가 된다.

## 1순위: A

외부 소스에 의존하기 때문에 **억지로 만들지 않은 장애**가 생긴다. 취준생 본인이 첫 사용자라 **실사용**이 보장된다. 수집, 정제, 발송 파이프라인이라 백엔드 역량(배치, 멱등성, 재시도, 이벤트)을 고르게 보여 준다. B는 운영 서사가 가장 강한 대신 기존 오픈소스와 비교당하는 부담이 있어 2순위로 둔다.
