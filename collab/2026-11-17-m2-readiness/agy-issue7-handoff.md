## 2. 코드 대조에서 드러난 `#7` 착수 전 기술적 주의·모순점 (구체 반례)

1. **`DeliveryLedger.recoverAsync()`의 `FAILED` 종결 시 `notification_item` 미반환 (`08cfdac3:188-215`)**:
   - **모순/공백**: 계약 `12 §4`는 "`FAILED`로 끝난 비동기 작업은 그 작업의 `notification_item`을 같은 트랜잭션에서 삭제해 다음 이메일 묶음이 다시 고를 수 있게 하고, `UNCERTAIN`은 남긴다"고 고정했다. 그러나 `08cfdac3`의 `DeliveryLedger.recoverAsync()`(`191-205`행)는 `attempts >= 3` 또는 `23시간` 만료로 `FAILED` 종결할 때 `notification`만 갱신하고 `notification_item`을 지우지 않는다.
   - **반례**: `EMAIL_DIGEST`가 `CONNECT_FAILED` 2회 뒤 3회차 `R` 후 크래시로 `SENDING` 방치 → `recoverAsync()`가 3회차 `UNKNOWN_CRASH` 처리 시 `UNCERTAIN`이므로 보존이 맞으나, 만약 1회차 전 크래시 후 `23h` 만료로 `FAILED`/`EXPIRED`(시도 0회, unknown 0건) 종결되면 `notification_item(NEW)`이 남아 **다음 날 묶음에서도 해당 공고가 영구 누락**된다. `#7`에서 `FAILED` 전이 시 동일 TX 내 `DELETE FROM notification_item WHERE notification_id = :id` 추가 필수.
2. **Hikari 풀 기본 10개 vs 워커 2연결(`A + R`) 교착 위험 (`application.yml`, `12 §3:59`)**:
   - **반례**: 현재 `application.yml`은 `connection-timeout: 5000`만 두고 `maximum-pool-size`는 기본값 `10`이다. `#7`이 비동기 발송을 스레드 `5`개 이상으로 병렬 실행하면, 워커 5개가 동시에 `TX2` 연결 `A`(`FOR SHARE`) 5개 + 웹/수집 연결과 겹쳐 풀 10개를 점유한 상태에서 모두 `R`용 연결 `B`를 기다리며 5초 후 풀 타임아웃(`SENDING` 방치)으로 자기 교착에 빠질 수 있다. `#7` 워커 동시성은 `1~2` 스레드로 제한하거나 `pool >= 2 * workers + 여유분`을 설정·테스트로 강제해야 한다.
3. **`PostingIngestor.write()`의 `OPEN` vs `CLOSED`/`CHECK` 상태와 `applyRegular` 인자 (`000dce5:61, 139`)**:
   - **반례**: `PostingIngestor.write()`(`139`행)는 정기 수집에서도 `end_date < today` 또는 `ongoingYn='N'`인 신규 행을 `status = 'CLOSED'`로 `INSERT`할 수 있다. outbox 훅이 `insert(...) == true`만 보고 `status`를 거르지 않으면 이미 마감된 공고로 `DISCORD_NEW`가 생성된다(이후 `TX2`에서 탈락 `CANCELLED` 낭비 또는 기준 모순). 또한 `CatalogRepository.findClosingSoon`(`08cfdac3:82`)은 `p.status = 'OPEN'`만, `findJobs("open")`은 `OPEN`/`CHECK`를 본다. `#7`은 `NEW`/`D-3` 공고 유효 상태를 `OPEN`(또는 `OPEN/CHECK` 합의)으로 명시하고 `CLOSED` 신규 적재분은 outbox에서 제외해야 한다. 아울러 `PostingIngestor.applyRegular(runId, body, observedAt)`는 `slot` 문자열을 받지 않으므로 `collect_run.slot` 조회 또는 시그니처 연계를 정해야 한다.
4. **`13-3`("`R` 전 자식 DML 금지")과 탈락 `notification_item` 삭제 시점 충돌 주의**:
   - **반례**: `TX2` 시작 직후 `R` 전에 `DELETE FROM notification_item`을 실행하면 `13-3`을 위반해(`A`가 `notification`/`item`에 미커밋 쓰기/잠금을 잡은 채 `B`의 `R` 진입) `recoverAsync`/`unsubscribe`와 잠금 경합을 일으킨다. 따라서 `A`의 `R` 이전 단계는 메모리에서만 적격 항목·본문·`payload_sha256`을 계산하고, 탈락 `notification_item` 삭제는 `R` 직후 `lockReserved()` 아래(`!anyUnknown`일 때, `notification -> item` 순서) 또는 `R` 없이 `NO_ITEMS`로 종결할 때만 수행해야 한다.
5. **대기(`SENDING`) 없는 `DeliveryLedger` 메서드 보완 필요 (`08cfdac3`)**:
   - `DeliveryLedger.finish()`는 항상 `finished_at = :now`를 써서 종결 상태(`CHECK` 제약)로만 전이한다. `#7` 비동기 워커의 시도 간 `2s/4s`/`429`/`SEND_CAP`/`QUOTA_DAILY` 대기를 위해 `claimed_at = NULL, status = 'RETRY', next_attempt_at = :nextAt`으로 돌리는 펜싱된 메서드(예: `retry(...)`)와 `created_at` 조회(`23h` 수명 검증용) 추가가 필요하다.
6. **`V5` `notification_item` 30일 후 `notification_id = NULL` 및 `disabled_reason` 화면 노출 확인**:
   - `AlertsMaintenance`가 종결 `notification`을 30일 뒤 삭제하면 `ON DELETE SET NULL`로 `notification_item.notification_id`가 `NULL`이 되어도 `(subscription_id, sn, kind)` 중복 방지는 유지된다(`V5:68`, `12 §8`). 반면 `manage.html`(`08cfdac3`)은 `DISABLED` 상태만 표시하고 `disabled_reason`(`WEBHOOK_404`)을 아직 노출하지 않으므로(`erd.md:77` "사용자가 사유를 볼 수 있는 기간"), `#7`에서 `WEBHOOK_404` 비활성화 구현 시 `ManageView`/`manage.html` 사유 표시 정합을 함께 점검할 것.
