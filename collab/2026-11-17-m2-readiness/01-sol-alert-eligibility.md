# #7 현재 유효 공고의 OPEN/CHECK 경계 · sol 독립안

2026-11-17. **알림 자격은 네 경로 모두 `OPEN AND end_date >= KST 오늘`로 제한하고 CHECK를 제외하는 안을 제안한다.** CHECK를 CLOSED로 바꾸거나 목록에서 감추자는 뜻은 아니다. 이는 기존 문서에서 명시적으로 확정된 경계가 아니라, 아래 상충하는 근거를 조율자가 결정할 수 있도록 제시하는 해석이다.

## 확인한 현재 의미

`CLAUDE.md`, PRD FR-C3/FR-A4와 계약06·12·13·14를 읽었다. 앱 코드는 불변 `000dce5`와 PR13 `08cfdac3`의 `git show`만 읽었다. 오늘 다른 에이전트의 독립안·교차검토는 읽지 않았다.

| 근거 | 실제 판정 |
|---|---|
| PRD FR-C3(56행) | 마감일 경과 또는 ongoingYn=N만 마감. 완전 수집에서 마감 전 누락은 CHECK(확인 필요)이며 마감이 아님 |
| 두 커밋 `PostingIngestor.java:133` | 관측된 행은 `end < today` 또는 ongoingYn=N이면 CLOSED, 아니면 OPEN |
| 같은 파일 `:174` | 완전 스냅샷에서 빠진 기존 OPEN/CHECK는 마감 전이면 CHECK, 마감일 경과면 CLOSED. 실패·빈 응답·건수 불일치는 이 반영에 진입하지 않음(`:61`) |
| 두 커밋 `CatalogRepository.findClosingSoon`, `:89` | 홈 마감 임박은 **OPEN만**, 현재 마감일이 오늘~오늘+3일인 행 |
| 목록 `searchJobs` | 기본/`open`은 **OPEN+CHECK**, 현재 마감일≥오늘. main `:145`, PR13 `:126`. `check`는 별도 선택 가능 |
| PR13 `CatalogRepository.java:163` | 공용 `appendConditions`는 NCS·지역·고용·채용구분·제목 조건만 공유. status·sort·page는 구독 조건이 아님 |

따라서 “목록 open과 홈 마감 임박은 같은 술어”라는 전제로 결정하면 안 된다. 목록은 불확실한 공고도 **확인 필요 표시와 함께 탐색**하게 하고, 홈은 진행 중 공고만 능동적으로 추천한다. FR-C3는 CHECK를 마감으로 단정하지 말라는 요구이며, CHECK의 발송 포함 여부까지 명령하지는 않는다.

## 네 경로의 제안

| 경로 | CHECK | 적용할 경계 |
|---|---|---|
| ① 정기 신규 outbox | 제외 | 완전 정기 수집의 **진짜 신규 insert**이며 OPEN·미마감이고 활성화 하한 이후 처음 관측된 공고만. 관측된 신규 행은 현재 수집 코드상 OPEN 또는 CLOSED라 CHECK 포함 여부는 이 순간 결과를 바꾸지 않음 |
| ② 이메일 미발송 NEW 선택 | 제외 | 최초 적재 제외·활성화 후 첫 관측·현재 OPEN·현재 미마감·채용 조건 일치·NEW 중복키 부재를 모두 만족 |
| ③ D-3 선택 | 제외 | 현재 OPEN이고 **현재 저장된 end_date = 실행일(KST)+3일**. 오래된 생성 시점 마감일로 고르지 않음 |
| ④ TX2 현재 자격 재검사 | 제외 | 생성과 동일한 공고 자격 및 현재 구독 ACTIVE·알림 종류·채용 조건을 재계산. D-3도 현재 마감일과 실행일 기준 자격을 다시 검사. R 뒤 HTTP 직전 재검사도 계약14대로 유지 |

CHECK→OPEN 재등장은 첫 관측이 아니다. `PostingIngestor`의 기존 행 갱신(`:233`)은 `first_seen_at`·`from_backfill`을 다시 쓰지 않으며, 최초 insert(`:222`)만 두 값을 만든다. 따라서 재등장을 Discord NEW outbox 생성 계기로 삼지 않는다. 최초 적재 공고나 가입 전 공고도 재등장으로 NEW가 되지 않는다. 이메일은 원래 활성화 후 처음 관측됐으나 **아직 미발송이고 중복키가 없는** 공고가 나중에 OPEN으로 돌아오면 기존 NEW 선택 계약으로 다시 후보가 될 수 있다. 이는 신규 시각을 초기화하거나 재알림을 추가하는 정책이 아니다.

`(구독, 공고, 종류)` 중복키에 마감일·수집 회차·재등장 날짜를 끼워 넣지 않는다. 이미 보낸 D-3는 마감일 연장 뒤에도 같은 종류의 새 항목을 만들지 않는다. 현재 마감일이 바뀌어 D-3가 아니면 지금 보내지 않고, NEW는 현재 미마감인지 다시 확인한다. payload 날짜를 batch_key 기준으로 결정적으로 만드는 계약12는 **현재 자격을 과거 날짜로 고정하라는 뜻이 아니다**. ADR-0003도 만회 D-3는 실행일 기준으로 제한한다.

## 두 정책이 놓치는 것과 선택 이유

**OPEN만 포함하면 일시 누락의 D-3 기회를 잃는다.** 예를 들어 공고가 실제로 계속 진행 중인데 D-3 일일 선택 시점의 마지막 완전 스냅샷에서 빠져 CHECK가 되고, 다음날 D-2에 돌아오면 D-3 알림은 없다. Discord NEW도 생성 뒤 TX2 전에 CHECK가 되면 취소될 수 있고 재등장이 새 NEW를 만들지 않는다. 이는 가능한 실패 사례이며 발생 빈도나 원인에 대한 외부 사실은 추정하지 않는다. 기존 당일 만회·23시간 수명에도 D-3 소실 한계가 있으므로 이 안 역시 완전한 알림 보장을 약속할 수 없다. 보완하려고 lookback·재등장 알림·추가 실행을 넣지 않는다.

**CHECK까지 포함하면 철회됐을 수 있는 공고를 알린다.** 공고가 마감 전 철회되어 목록에서 빠졌지만 명시적인 ongoingYn=N을 받지 못했다는 가정에서는 CHECK와 과거 마감일이 남는다. OPEN+CHECK 정책은 이 행을 이메일 NEW 또는 D-3로 내보낼 수 있다. “마감 아님”은 “지금 지원 가능함을 확인함”과 같지 않다. 반대로 CHECK 포함안은 FR-C3와 목록 기본 open에 더 직접적으로 맞고 일시 누락에 덜 민감하다는 장점이 있다.

나는 기존 MVP의 **능동 알림은 홈의 OPEN 경계에 맞추는 편이 더 일관적**이라고 판단한다. 구독은 목록의 상태를 저장하지 않으므로 목록 open을 그대로 복제해야 한다는 계약도 없다. 목록에서 불확실성을 보존하는 것과, 확인되지 않은 공고를 발송 대상으로 승격시키는 것을 구분할 수 있다. 다만 일시 누락의 기회 손실을 수용하는 제품 선택이므로 root의 최종 결정으로 명시해야 하며, CHECK 제외가 PRD에 이미 확정됐다고 보고하지 않는다.

## unknown 계약은 그대로 유지

OPEN→CHECK로 자격이 없어지면 **payload가 같아도** 현재 대상 집합이 달라진다. 이전 unknown이 있으면 item을 감사·중복 방지용으로 보존하고 새 예약/HTTP 없이 UNCERTAIN으로 종결한다(계약13 §2·14 항목2). CHECK→OPEN으로 돌아와도 보존 item을 지워 새 NEW/D-3를 만들지 않는다. unknown이 없을 때의 조건 탈락 항목 삭제·확실한 실패 항목 반환은 계약12·13의 기존 규칙을 따르고, 그 조작을 R 전 자식 DML로 옮기지 않는다.

대상 집합·현재 자격이 일치한 뒤에도 **공급자 요청 전체의 결정적 payload hash**가 같아야 같은 키로 재시도한다. 예를 들어 NEW의 현재 마감일 연장은 여전히 미마감이라 대상은 같을 수 있지만 payload가 바뀌면 unknown 뒤 재전송은 중단한다. D-3의 마감일 연장으로 D-3 자격 자체가 사라지면 hash 검사 전 대상 불일치로 중단한다. 모든 선행 시도가 확실한 거절일 때만 새 키·현재 payload를 허용한다. OPEN/CHECK 정책 어느 쪽을 택해도 이 순서를 완화할 이유는 없다.

이 문서는 경계 제안만 남겼다. 앱·테스트를 실행하거나 수정하지 않았고, 설정·DB·실제 API·브라우저·계정·개인정보에는 접근하지 않았다. 불변 소스 읽기 외 실행 검증은 하지 않았다. 구현이나 새로운 필터·설정·재알림·lookback은 추가하지 않았다.
