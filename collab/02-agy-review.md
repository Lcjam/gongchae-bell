### (2) 외부 서비스 동작 및 연동의 허구·과장 검증

#### ① agy(나)의 iCal(Google/Apple Calendar) 봇 트래픽 주장의 치명적 허구
- **1라운드 agy 주장**: *"구글/애플 서버가 2~6시간 주기로 24시간 요청하여 사용자 50명만 모여도 일평균 8,000건의 인바운드 트래픽이 발생하고, 이를 ETag 304로 방어했다."*
- **실제 공식 동작 명세 확인**:
  - **Google Calendar의 웹 캘린더(.ics) 갱신 주기는 공식적으로 약 12~24시간(심하면 48시간)**입니다 (Google Calendar Help - Use calendar feeds). 사용자가 임의로 주기를 단축할 수 없으며, 심지어 다수 사용자가 동일 URL을 구독하면 구글의 중앙 프록시가 하루 1~2회만 가져와 캐싱합니다.
  - Apple Calendar는 클라이언트 앱 설정에서 15분~1시간 주기가 가능하나, 이는 사용자가 로컬 기기에서 앱을 켜두었을 때만 발생합니다.
- **결론**: 사용자 50명이 고유 URL을 등록해도 구글 서버 기준 하루 인바운드 요청은 **50~100건에 불과**합니다. "일평균 8,000건 폴링 트래픽"은 **외부 플랫폼의 메커니즘을 제대로 확인하지 않고 만들어낸 명백한 수치 과장이자 허구**였음을 인정하고 전면 철회합니다.

#### ② 공공 API (온통청년, 잡알리오 등) 연동 조건
- **실제 조건**: 공공데이터포털(`data.go.kr`) 및 온통청년 API는 회원가입 후 [활용신청 ➡️ 승인/인증키 발급] 절차(영업일 1~3일)가 필요하며, 테스트 계정은 일일 1,000~10,000회 호출 제한이 걸려 있습니다. 또한 사전 예고 없는 야간 점검 및 주말 500 에러, 응답 XML 스키마 변경이 잦습니다.
- **평가**: Codex는 온통청년 API의 심사 절차를 정확히 인지하고 데이터 수집과 실사용 수요 검증을 분리했습니다. 반면 Claude는 외부 API의 불안정성을 "장애 회고의 기회"로 삼은 방향성은 좋았으나, 쿼터 제한 및 사전 승인 지연에 대한 방어책이 다소 누락되었습니다.

## 3. 다른 에이전트 안의 약점·과장 지적 및 자체 철회/수정 사항

### (1) agy(나) 1라운드 안의 철회 및 자체 반성
1. **Ampere A1 스펙(4/24) 전면 철회**: 신규 비유료 테넌시 기준인 **2 OCPU / 12GB RAM**으로 인프라 설계를 전면 수정합니다. 12GB 안에서 Blue/Green 배포용 Spring Boot 2대(각 1.5GB Heap), PostgreSQL(2GB), 관측 스택(2GB)을 운영하는 **"메모리 예산 설계(Memory Budgeting)"**를 핵심 운영 스토리로 전환합니다.
2. **iCal 구글 캘린더 트래픽 허구 철회**: 12~24시간 주기의 구글 크롤러 동작을 간과하고 "일평균 8,000건 트래픽"을 주장한 것은 명백한 허구였습니다. 트래픽 방어 서사를 철회합니다.
3. **주제 3 (음성 녹음 피어리뷰) 비현실성 인정**: 브라우저 오디오 레코딩, WebM 인코딩, OCI Object Storage Presigned URL 업로드 파이프라인은 2~3개월 안에 1인이 프론트엔드와 백엔드를 모두 완성하기에 지나치게 범위가 넓어 탈락 처리합니다.

### (2) Claude 안의 약점 및 과장 지적
1. **OCI Email Delivery 기본 작동 전제의 치명적 결함**: Claude A는 알림 수단으로 "이메일"을 제시했으나, OCI Always Free는 서비스 한도상 24시간 메일 발송량이 `0`으로 잠겨 있어 실제 배포 시 즉시 장애가 납니다. Discord/Telegram 웹훅으로 설계해야 안전합니다.
2. **다중 소스 수집의 공수 과소평가**: "외부 수집 소스 7개의 실패율을 Grafana로 추적"한다고 기술했으나, 1인 개발자가 2~3개월 안에 7개나 되는 서로 다른 크롤러/API 파서를 작성하고 유지보수하는 것은 유지보수 지옥(HTML 셀렉터 변경 대응)에 빠져 백엔드 운영 실습이라는 본질을 망칩니다. 소스는 검증된 2~3개로 압축해야 합니다.
3. **유휴 회수 방어의 비현실적 안일함**: "JVM과 DB를 띄우면 메모리 20%는 넘으니 괜찮다"는 주장은 위험합니다. OCI는 CPU p95와 네트워크도 함께 검사하므로, 상시 트래픽이 없으면 인스턴스가 강제 회수될 수 있습니다. 확실한 방어책인 PAYG 전환을 누락한 것은 약점입니다.

### (3) Codex 안의 약점 및 과장 지적
1. **Codex 1 (스터디 모임 신청)의 치명적인 "운영 사건 빈곤"**:
   - Codex는 1순위로 모임 신청을 추천했으나, **이 프로젝트는 일주일에 모임 신청 10분을 제외하면 나머지 6일 23시간 50분 동안 서버에 아무런 일도 일어나지 않습니다.**
   - 외부 의존성도 없고 주기적인 배치도 없어, "배포 및 유지보수/운영 경험을 구체적인 수치와 사건으로 말한다"는 본 과제의 핵심 목표(4번 조건)를 달성하기 어렵습니다. 면접관에게 보여줄 로그, 슬로우 쿼리, 알림 발송 실패 등의 '살아있는 사건'이 턱없이 부족합니다.
2. **Codex 4 (웹훅 수신함)의 치명적인 실사용자 확보 불가능**:
   - 엔지니어링 깊이는 가장 훌륭하나, **동료 개발팀이 신입의 불안정한 개인 서버를 거치도록 GitHub 웹훅 URL을 변경해 줄 이유가 전혀 없습니다.** 결국 본인의 토이 저장소 2~3개만 물려놓게 되며, 이는 "실사용자가 있는 서비스 운영"이라는 전제를 위배하고 자작 테스트 도구로 전락합니다.
3. **장애 훈련의 인위성**:
   - 실서비스에서 발생하는 자연스러운 외부 이슈(인증 만료, 서드파티 다운, 포맷 변경) 대신 "인위적인 장애 주입 훈련"에만 서사가 치우쳐 있어 면접관에게 '작위적인 연출'로 보일 위험이 있습니다.

## 4. 최종 순위 및 융합 통합안

### [최종 순위]

- **최종 1순위**: **[운영 감시 도구] 취준생 동기 포트폴리오·홈서버 외부 헬스체커 & SSL 만료 알림 (Claude B + agy 2)**
  - **선정 이유**: 
    1. **사용자 온보딩 허들 0**: 동료 취준생에게 "너 포트폴리오 URL만 등록해 둬, 죽으면 디스코드로 알려줄게" 한마디면 30~50개 엔드포인트를 당일 확보할 수 있습니다.
    2. **자연 발생하는 24시간 실전 운영 사건**: 취준생들의 AWS/OCI 무료 서버는 빈번하게 다운되고, Let's Encrypt 인증서는 90일마다 만료 위험에 처하며, 네트워크 지연이 수시로 발생합니다. 내가 억지로 장애를 만들지 않아도 매일 진짜 장애 알림과 시계열 데이터가 발생합니다.
    3. **백엔드 핵심 기술 검증**: Java 21 Virtual Threads를 활용한 대규모 논블로킹 I/O 처리, 시계열 RDB 파티셔닝, 소켓 레벨 SSL 인증서 만료일 파싱 등 면접관이 신입에게 기대하는 '네트워크와 인프라를 이해하는 백엔드 개발자'의 역량을 완벽히 증명합니다.

- **최종 2순위**: **[수집+알림] 공공 API 기반 청년 취업정책 및 채용공고 멱등 수집 알림 (Codex 2 + Claude A)**
  - **선정 이유**: 온통청년, 잡알리오 등 공식 오픈 API를 활용하여 크롤링 법적 분쟁을 없애고, Spring Batch와 아웃박스 패턴을 통한 데이터 신뢰성 및 장애 복구 역량을 증명하기에 가장 교과서적인 주제입니다.

### [3사 융합 통합 개선안] "DevPulse" (동기 인프라 감시 + 취준 알림 파이프라인)

세 에이전트의 강점(**Codex의 트랜잭션 정합성/아웃박스 패턴**, **Claude의 외부 의존 장애 회고/바깥 감시 아키텍처**, **agy의 가상 스레드 대량 I/O 및 인프라 최적화**)을 결합한 통합 개선안을 제안합니다.

```
                          [외부 감시용 Micro 인스턴스 (1GB)]
                                       │ (1분 주기 핑)
                                       ▼
[동료 사용자들] ──> [OCI Ampere A1 (2 OCPU / 12GB RAM)]
 (URL 등록)          ├─ Nginx (리버스 프록시 / SSL 종단)
 (정책 구독)          ├─ Spring Boot 1 (Blue) ──┐ (Zero-Downtime 전환)
                     ├─ Spring Boot 2 (Green) ─┘
                     │    ├─ [모듈 1] Virtual Thread 헬스체커 (1분 주기, 100+ 서버 검사)
                     │    ├─ [모듈 2] 공공 API(온통청년/잡알리오) 배치 수집 (1시간 주기)
                     │    └─ [모듈 3] Outbox 패턴 기반 Discord 웹훅 알림 발송기
                     ├─ MySQL 8.0 (시계열 핑 로그 일별 파티셔닝 + 공고 RDB)
                     └─ Prometheus & Grafana (JVM / 네트워크 / 장애 메트릭 수집)
```

#### ① 인프라 및 메모리 예산 설계 (2 OCPU / 12GB 완전 최적화)
- **A1 인스턴스 (12GB)**:
  - `Nginx`: 0.2GB
  - `Spring Boot App` (Blue/Green 무중단 배포를 위한 2개 컨테이너): 각 1.5GB Heap (합계 3~3.5GB)
  - `MySQL 8.0`: 버퍼 풀 2GB 설정 (총 2.5GB)
  - `Prometheus + Grafana`: 경량 시계열 메트릭 수집 (1.5GB)
  - `OS 및 여유 버퍼`: 약 4.3GB 확보 ➡️ **OOM Killer 방어 및 안정적인 Blue/Green 컨테이너 교체 보장**
- **AMD Micro 인스턴스 (1 OCPU / 1GB)**:
  - A1 메인 서버의 다운을 외부에서 감시하는 경량 Ping 데몬 구동 (Split-Brain 방지 및 외부 감시).

#### ② 핵심 백엔드 기능 구성
1. **Virtual Thread 기반 헬스체커**:
   - 100개 이상의 등록된 동료 포트폴리오 URL을 1분 주기로 검사. 블로킹 I/O 대기 시간을 Java 21 가상 스레드로 극복하여 스레드 풀 고갈 방지.
   - `SSLSocketFactory`를 통해 만료 D-7일 사전 감지 알림.
2. **공공 API(온통청년·잡알리오) 멱등 수집 배치**:
   - 1시간 주기로 신규 공고 수집. 해시 기반 중복 체크 및 변경 감지(Upsert).
   - Resilience4j Circuit Breaker를 적용하여 공공 API 서버 점검 시 메인 서비스 격리.
3. **Transactional Outbox 패턴 기반 Discord 알림 발송**:
   - OCI의 이메일 제한을 피해 Discord/Telegram 웹훅으로 발송.
   - 서버 재시작이나 일시적 네트워크 장애에도 알림이 유실되지 않도록 DB Outbox 테이블과 지수 백오프 재시도 큐 구현.

#### ③ 이력서에 쓸 수 있는 결정적 실측 문장 예시
- *"Ampere A1(12GB) 환경에서 JVM 힙, RDB 버퍼 풀, 관측 스택의 정밀 메모리 예산을 수립하고 cgroup OOM 추적 체계를 구축하여, 3개월간 메모리 릭 없이 가동률 99.95% 달성"*
- *"Java 21 Virtual Threads를 도입해 120여 개 외부 엔드포인트의 1분 주기 헬스체크 블로킹 I/O를 경량화함으로써, 기존 플랫폼 스레드 풀 대비 메모리 점유율을 58% 절감하고 응답 판정 지연을 p95 1.1초로 통제"*
- *"공공 API 수집 파이프라인에 Transactional Outbox 패턴과 지수 백오프 재시도를 적용하여, 외부 API 504 게이트웨이 타임아웃 장애 14건 발생 상황에서도 알림 유실 0건 달성"*
