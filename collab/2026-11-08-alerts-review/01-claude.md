# 알림 요구사항 리뷰 1라운드 · claude 독립 검토

> 대상: `docs/prd.md` FR-A1~A7 (+ G7, §6, §7). codex와 agy의 01은 보지 않았다.

## 지적

| 등급 | FR | 문제 | 근거 | 바꿀 문구 |
|---|---|---|---|---|
| **차단** | A1, A3 | 확인 링크와 해지 링크를 **GET 요청 하나로 처리하면**, 메일 보안 스캐너가 링크를 미리 열면서 **남이 누르지 않은 확인이나 해지가 실행된다** | 스캐너와 프리페치가 GET으로 링크를 연다는 실무 보고 ([suped](https://www.suped.com/email-deliverability/answers/how-should-one-click-unsubscribe-links-handle-get-vs-post-requests), [suped/Defender](https://www.suped.com/knowledge/email-deliverability/technical/how-can-i-prevent-microsoft-defender-from-triggering-unwanted-one-click-unsubscribes)). 벤더 블로그 출처이고 RFC 원문은 확인하지 않았다 | "확인과 해지 링크의 GET 요청은 **확인 화면만** 보여 준다. 실제 상태 변경은 화면의 버튼(POST)으로만 한다" |
| **차단** | A7 → A1 | 아무나 남의 이메일을 입력해서 **확인 메일을 반복 발송시킬 수 있다.** 그러면 괴롭힘에 쓰이고 발신 도메인 평판이 떨어진다. 지금은 Should라 출시에서 빠질 수 있다 | 설계상 위험 (외부 출처 불필요) | FR-A1에 Must로 추가: "확인 메일은 같은 수신 주소와 같은 IP 기준으로 발송 횟수를 제한한다(초기값은 ADR). 이미 구독 중인 주소라도 같은 응답을 돌려줘서 구독 여부가 드러나지 않게 한다" |
| **차단** | A6 | 개인정보 요구사항이 추상적이다. 처리방침 필수 기재 항목, 수집 시 고지 항목, 14세 미만 처리, 파기 시점이 없다 | 개인정보보호법 제30조(처리방침 기재 사항), 제15조(수집·이용. 2023년 개정으로 계약 이행 근거가 넓어졌다: [보안뉴스](https://m.boannews.com/html/detail.html?idx=124648)), 제22조의2(만 14세 미만 아동은 법정대리인 동의). **이메일 알림이 계약 이행 근거에 해당하는지는 해석 미확인** | "구독 화면에 수집 항목(이메일), 목적(알림 발송), 보유 기간(해지 시까지)을 고지하고 동의를 받는다. 만 14세 이상 확인 체크를 둔다. 해지하면 즉시 삭제하고, 백업에서는 보관 기간(14일)이 지나면 사라진다는 점을 처리방침에 적는다. 처리방침에는 제30조 기재 사항과 발송 위탁 서비스를 적는다" |
| 권장 | A2 | "디스코드 웹훅 주소 형식만 허용"이 모호하다. 또 디스코드 구독자는 이메일이 없어서 **관리 링크를 받을 곳이 없다** | 웹훅 URL은 `/api/webhooks/{id}/{token}` 형태다 (공식 문서 페이지는 직접 확인하지 못했다. 제3자 자료 기준) | "https, 호스트 `discord.com` 또는 `discordapp.com`, 경로 `/api/webhooks/{숫자}/{토큰}`만 허용하고 리다이렉트는 따라가지 않는다. 관리 링크는 등록 완료 화면과 테스트 메시지에 함께 보낸다. 중복 등록 판별용으로 URL의 해시를 따로 저장한다(암호문끼리는 비교할 수 없다)" |
| 권장 | A3 | 관리 토큰을 어떻게 저장하고 유출을 막는지가 없다 | 설계상 위험 | "관리 토큰은 해시로만 저장한다. 관리 페이지는 `Referrer-Policy: no-referrer`로 둔다. 이메일 구독자는 관리 링크를 다시 받을 수 있다" |
| 권장 (**사용자 결정**) | A4 | **새 공고 알림을 매시간 보내면** 구독자 한 명이 하루 최대 24통을 받을 수 있다. 발송 작업도 두 종류가 된다 | 설계상 판단 | **대안: 하루 1회 오전에 묶음 1통**(새 공고 + 마감 임박을 한 메일로). 장점: 발송 작업 1종, 메일 수 하루 1통, 발송 한도와 스팸 위험 감소. 단점: 새 공고가 최대 하루 늦게 간다. 공고 접수 기간 분포는 데이터로 확인하지 않았다 |
| 권장 | A5 | "영구 실패가 연속되면"의 횟수가 없다. 이메일 반송을 감지하는 방법은 발송 서비스에 따라 다르다 | 디스코드 에러 코드 10015(Unknown Webhook)는 미확인 | "디스코드가 웹훅 없음(404)을 돌려주면 즉시 비활성화한다. 그 밖의 영구 실패는 N회 연속(초기값 ADR)이면 비활성화한다. 이메일 반송 감지 방식은 발송 서비스 ADR에서 정한다" |
| 권장 | A1, A3 | 메일 클라이언트의 "구독 취소" 버튼(List-Unsubscribe)이 없다 | RFC 8058 원클릭 해지는 POST 방식이고 DKIM 서명이 필요하다 ([autospf](https://autospf.com/blog/one-click-unsubscribe-rfc-8058-compliance-guide-gmail-yahoo-rule/), 벤더 출처) | Should: "`List-Unsubscribe`와 `List-Unsubscribe-Post` 헤더를 넣는다" |
| 권장 | A1, A5, A4 | 수용 기준에 검증할 수 없는 표현이 있다: "일정 기간", "연속되면", "중복 완화" | — | 초기 설정값을 적는다: 확인 링크 유효 시간, 미확인 구독 삭제 시점, 실패 횟수 (값과 근거는 ADR). "중복 완화"는 **지표로 바꾼다**: "발송 기록에서 (구독, 공고, 종류)가 중복된 건수를 운영 지표로 본다" |

## 그대로 둬도 되는 것
- 더블 옵트인, 확인 전에는 발송하지 않기
- 웹훅 등록 시 테스트 메시지 성공을 활성화 조건으로 두기
- 웹훅 URL 암호화 저장, 로그 마스킹
- (구독, 공고, 종류) 유니크 제약, DB에 먼저 기록하고 발송
- 디스코드 429에서 `retry_after` 지키기
- 해지 즉시 발송 대상에서 빼기
- G7 목표를 기준선 측정 후 설정
- FR-A7의 이메일당 구독 수 상한을 Should로 두기
