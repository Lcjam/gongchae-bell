# 알림 요구사항(FR-A1~A7) 1라운드 검토 보고서 (agy 독립안)

> **검토 대상**: `docs/prd.md` §5 알림 (FR-A1~A7) 및 관련 맥락(G7, §6 보안·발송, §7, §9)  
> **원칙**: 이메일 발송 서비스 선정(ADR)은 제외하고, 보안·개인정보·정합성·외부 사실·범위·수용 기준 검증 가능성에 집중함.

---

## 1. 개선 지적 사항

### 1. [차단] FR-A2: SSRF 방어 규격 미흡 및 리다이렉트 취약점
- **문제**: "디스코드 웹훅 주소 형식만 허용"이라는 모호한 표현만으로는 SSRF(서버 측 요청 위조)를 막기 어렵습니다. 특히 HTTP Client가 3xx 리다이렉트를 자동 추적할 경우, 악의적인 도메인이 OCI 내부 메타데이터 엔드포인트(`http://169.254.169.254/opc/v2/...`) 등으로 요청을 우회시켜 인스턴스 자격 증명을 탈취할 수 있습니다.
- **근거**: OWASP Server-Side Request Forgery Prevention Cheat Sheet; Discord Developer Portal (공식 웹훅 도메인은 `https://discord.com/api/webhooks/...` 및 레거시 `https://discordapp.com/api/webhooks/...`뿐임).
- **바꿀 문구 제안**:
  > "웹훅 URL은 프로토콜(`https://`), 도메인(`discord.com` 또는 `discordapp.com`), 경로(`/api/webhooks/숫자/문자열`)를 정규식으로 엄격히 화이트리스트 검증한다. 발송 HTTP Client는 3xx 리다이렉트 추적을 강제 비활성화(Follow Redirects = false)하고 사설 IP 대역 연결을 차단한다."

---

### 2. [차단] FR-A3: 이메일 봇의 프리패치(Prefetch)로 인한 자동 해지 위험
- **문제**: 이메일 본문의 해지 링크를 사용자가 클릭하지 않아도, 기업용 백신/스팸 필터 및 메일 클라이언트(Outlook, Apple Mail 등)의 보안 크롤러가 링크를 사전 방문(GET)하면서 **사용자 의도와 무관하게 구독이 즉시 자동 해지**되는 장애가 발생합니다.
- **근거**: RFC 8058 (Signaling One-Click Functionality for List Email); 메일 보안 솔루션의 URL Prefetch 동작 특성.
- **바꿀 문구 제안**:
  > "모든 이메일에는 해지 링크가 포함되며, 링크(GET) 접속 시 즉시 해지되지 않고 '구독 해지 확인' 페이지를 띄운 뒤 확인 버튼(POST)을 누르거나 원클릭 해지(RFC 8058 POST) 요청이 수신될 때 해지된다."

---

### 3. [차단] FR-A1, FR-A6: 한국 개인정보보호법 필수 법정 고지사항 누락 및 파기 시점 모호
- **문제**:
  1. 법 제15조 제2항의 4대 필수 고지사항(① 수집·이용 목적, ② 수집 항목, ③ 보유·이용 기간, ④ 동의 거부 권리 및 불이익)을 명시하고 동의받는 절차가 수용 기준에 없습니다.
  2. FR-A6의 "해지하면 이메일을 파기한다(또는 정한 기간 뒤)"라는 문구는 법령상 허용되지 않는 모호한 규정입니다.
- **근거**: 대한민국 개인정보 보호법 제15조(개인정보의 수집·이용), 제21조(개인정보의 파기).
- **바꿀 문구 제안** (FR-A1 및 FR-A6):
  > (FR-A1) "신청 화면에 개인정보 수집·이용 필수 고지 4개 항목을 명시하고 필수 체크박스 동의를 받아야 신청된다."  
  > (FR-A6) "수집된 이메일은 구독 해지 시 즉시 영구 파기(DB 삭제)한다. 더블 옵트인 미확인 신청 건은 신청 후 24시간이 경과하면 스케줄러를 통해 자동 영구 파기한다."

---

### 4. [차단] FR-A5: 동기식 발송 환경에서 '이메일 반송(Bounce)' 실시간 감지 불가
- **문제**: "영구 실패(웹훅 삭제, 이메일 반송)가 연속되면 구독을 비활성화하고..."라고 되어 있으나, 일반적인 SMTP/발송 API는 발송 요청 성공(250 OK / 200 OK)만 알려줄 뿐, 실제 메일함 부재 등의 **하드 바운스(Hard Bounce)는 비동기 반송 메일 수신이나 공급자 웹훅을 통해서만 확인**할 수 있습니다. 별도 반송 웹훅 수신기를 구축하지 않는 한 "이메일 반송"은 런타임에 즉시 감지할 수 없습니다.
- **근거**: RFC 5321 (SMTP), 주요 트랜잭셔널 이메일 서비스의 Bounce 처리 사양.
- **바꿀 문구 제안**:
  > "영구 실패(디스코드 404/Unknown Webhook, 이메일 발송 API/SMTP 5xx 연속 3회 실패)가 발생하면 구독을 비활성화하고 사유를 남긴다. (비동기 이메일 수신 거부/반송 웹훅 수신은 MVP 범위에서 제외하며, 필요시 수동 처리한다.)"

---

### 5. [권장] FR-A7: 남용 방지(Rate Limiting)의 우선순위 상향 (Should ➡️ Must)
- **문제**: 비회원 이메일 입력 폼이 아무런 요청 제한 없이 공개되면, 악의적인 스크립트에 의해 **타인의 이메일로 수만 건의 확인 메일을 쏟아붓는 메일 폭탄(Mail Bombing) 발신지로 악용**됩니다. 이는 도메인 평판을 즉시 추락시키고 발송 쿼터를 소진시킵니다.
- **근거**: OWASP Top 10 API Security - Unrestricted Resource Consumption; Spamhaus 메일 평판 가이드라인.
- **바꿀 문구 제안**:
  > 우선순위를 **Must**로 상향.  
  > "동일 IP 기준 분당 신청 5회 제한, 동일 이메일 기준 확인 메일 재발송 쿨다운 1분을 강제한다 (인메모리 버킷 또는 DB 기반 경량 제어)."

---

### 6. [권장] FR-A4, FR-C5: Blue/Green 배포 중 Outbox 발송 워커의 동시 중복 발송 방지
- **문제**: FR-C5에 "배포 중에도 같은 알림 작업은 1회만 실행된다"고 되어 있으나, DB에 쌓인 Outbox 레코드를 두 인스턴스가 동시에 폴링해 외부 API로 전송할 경우의 방어 메커니즘이 수용 기준에 없습니다.
- **근거**: Transactional Outbox Pattern; Spring Data JPA 비관적 락(`SELECT FOR UPDATE SKIP LOCKED`) 또는 조건부 상태 전이(`UPDATE ... SET status='SENDING' WHERE status='PENDING'`).
- **바꿀 문구 제안**:
  > "발송 워커는 Outbox 테이블 조회 시 조건부 상태 갱신(`PENDING` ➡️ `PROCESSING`)을 통해 소유권을 선점한 단일 인스턴스만 발송을 수행하여 배포 겹침 구간의 동시 발송을 원천 차단한다."

---

### 7. [권장] §6 이메일 발송 / §7 완료 기준: RFC 8058 List-Unsubscribe 헤더 명시
- **문제**: §7에 "발송 메일이 스팸함으로 가지 않는 것을 확인했다"가 있으나, 2024년 개정된 Gmail/Yahoo 가이드라인에 따라 일괄/알림 발송 시 헤더에 `List-Unsubscribe`가 없으면 스팸으로 자동 분류될 위험이 큽니다.
- **근거**: Google Workspace Sender Guidelines (2024); RFC 8058.
- **바꿀 문구 제안**:
  > (FR-A3 또는 §6에 추가) "발송되는 모든 알림 이메일 헤더에 `List-Unsubscribe` 및 `List-Unsubscribe-Post`를 포함하여 메일 클라이언트의 원클릭 해지를 지원한다."  
  > (§7 검증 문구) "발송 메일이 스팸함으로 가지 않는 것" ➡️ "주요 수신사(Gmail 등) 테스트 계정에서 SPF/DKIM 통과(Pass) 및 정상 수신함을 확인했다"로 검증 가능하게 변경.

---

### 8. [선택] FR-A3: 구독 '조건 변경' 범위 축소 검토
- **문제**: 이메일/웹훅 구독 후 "조건 변경"을 지원하려면 필터 수정 화면 및 검증 로직이 추가로 필요합니다. 1인 개발 관점에서 공수를 줄이려면 "기존 구독 해지 후 신규 구독 신청"으로 유도해도 충분합니다.
- **바꿀 문구 제안**:
  > "관리 링크에서 현재 구독 중인 조건을 조회하고 [해지]할 수 있다. (조건 변경은 해지 후 재신청 안내로 갈음하여 화면 복잡도를 낮춘다.)"

---

## 2. 그대로 둬도 되는 것 (유지 권장 사항)

- **FR-A1 더블 옵트인(Double Opt-in) 기본 채택**: 로그인 없는 환경에서 타인 이메일 오입력 및 무단 도용을 원천 방지하는 가장 안전한 설계입니다.
- **FR-A2 웹훅 등록 시 테스트 메시지 발송 검증**: 잘못된 URL이나 접근 권한 없는 채널을 즉시 걸러내어 유령 구독이 쌓이는 것을 방지합니다.
- **FR-A2 웹훅 URL 암호화 저장 및 화면/로그 마스킹**: 토큰이 포함된 Discord URL의 유출을 막는 충실한 보안 요구사항입니다.
- **FR-A4 발송 묶음 정책(정기 수집 회차당 1건, 마감 임박 일 1회 묶음)**: 외부 발송 호출량을 극적으로 절감하고 디스코드 레이트 리밋 충돌을 최소화하는 훌륭한 엔지니어링 판단입니다.
- **FR-A4 DB 유니크 제약 기반 중복 완화**: 분산 환경의 네트워크 단절 특성을 인정하고 실질적인 DB 레벨 멱등성을 확보했습니다.
- **FR-A4 디스코드 429 응답 시 `retry_after` 준수**: 디스코드 공식 API 가이드라인을 정확히 반영했습니다.
